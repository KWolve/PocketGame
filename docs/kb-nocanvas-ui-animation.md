# 非画布 UI 动画（原生控件做动画）+ SysApp 进/退时机 + 真机动画验收

> 2026-09-18 入库（来源：在某 V85X 工程的**屏保大时钟**上做"砖块数字 + 走跳动画 + 数字当金币弹出"时实测）。
> 起因：工程铁律是「**非游戏页禁止自定义绘图**」，所有动效只能用原生控件做；而"动画"这件事在
> 原生控件体系里怎么做得不漂、怎么验得准，此前 knowledge 里没有成体系的口径。
> 检索词：非游戏做动画/不用画布做动画/自定义绘制禁用/原生控件动画/setPosition 动画/setVisible 动画/
> 动画飘移/冻帧/掉帧动画/绝对时钟动画/dt 累加/SysApp/屏保生命周期/onUI_init 什么时候调/onUI_quit/
> 退屏保定时器停/进屏保时机/动画验收/抓帧比动画慢/slow 慢放重播/QA 指定相位/校时导致卡点不准。

## 0. 一句话口径

**非游戏页做动画 = 「静态图片资源 + 原生控件（`setPosition` / `setVisible`）+ 相位由绝对时钟推导」。**
三条硬约束：
1. **不写一行画布绘制代码**（图片烘焙在生成阶段做，运行时只改控件几何/显隐）；
2. **相位不许用"每帧累加 dt / 帧计数器状态机"推** —— 必须每帧从**绝对时钟**算出相位（下文 §1）；
3. 只有"必须与某个事件**严格对齐**的一小段"才允许用帧计数器（§2）。

## 1. ★★ 相位必须由绝对时钟推导（累加式会漂，且和"跳帧优化"一起会冻帧）

```cpp
/* 每帧：由"距目标事件还有多少毫秒"反推此刻该长什么样 —— 位置是它的纯函数 */
static void nowPhases(long *msToEvent, int *hh, int *mm, int *ss) {
  struct timeval tv; gettimeofday(&tv, NULL);
  time_t t = tv.tv_sec; struct tm lt; localtime_r(&t, &lt);
  *hh = lt.tm_hour; *mm = lt.tm_min; *ss = lt.tm_sec;
  long ms = (long)(60 - lt.tm_sec) * 1000 - (long)(tv.tv_usec / 1000);  // 距下一分钟整点
  if (ms < 0) ms = 0;
  *msToEvent = ms;
}
/* 纯函数：给定相位 -> 帧号 + 坐标；返回 false = 此刻不该显示 */
static bool pose(long msToEvent, int *frame, int *x, int *y);
```

为什么**不能**累加：
- 定时器被挂起 / 系统卡一下 / 掉几帧，累加式相位就**永久偏**（越跑越歪，且不报错）；
- 若同时还有"帧指纹跳帧"（比较上一帧输出、没变就跳过 `update`）这类优化，
  累加式动画会出现"跳过 update ⇒ 时间不推进 ⇒ 指纹永远相同 ⇒ **永久冻帧**"的死循环。
  实测踩过：连续两次 QA 都读到同一个毫秒值、累计实绘不涨。
  ⇒ 要能跳帧，动画必须改成**绝对时钟**（毫秒相位由系统时间推导，与"画了几帧"无关）。

绝对时钟推导的额外好处（都是实测省下来的）：
- 掉多少帧都**自己对齐**，长时间跑也不漂；
- 任意时刻都能**无状态地**算出画面 ⇒ 恢复/重进页面时直接对齐，不会补播"跨过去的那几秒"。

## 2. 帧计数器的唯一合法用途：与事件严格对齐的"短动作"

例：撞砖那一刻要把旧数字当金币"飞出去 + 横向压扁（模拟旋转）"，整段 12 帧 × 50ms = 600ms。
这一段**起点就是那个事件本身**（数字变化被检测到），所以用帧计数器反而更稳、也便于放慢抓帧。
判据：**起点是事件、终点是"演完为止"、与时钟无绝对关系** → 可以用帧计数器；
**起点/终点要落在某个时钟刻度上**（如"头正好顶到砖块的那一刻就是整分"） → 必须用绝对时钟。

## 3. 原生控件能做的动画手法（按可用性排序）

| 手法 | 做法 | 注意 |
|---|---|---|
| 位移 / 缩放 | `setPosition(LayoutPosition(x,y,w,h))` | 图片会**按控件盒缩放** ⇒ 改宽度就是横向压扁（"金币旋转"就是这么做的）；**尺寸不同的中间态会看出拉伸**，别用在需要保持比例的地方 |
| 换图（帧动画） | N 张图**同位置重叠**的 N 个控件，按相位 `setVisible` 只留一个 | ✅ 首选。**不要**运行时 `setBackgroundPic` 换图：那时**不保留 alpha**，透明底会变白方块 |
| 折叠 / 翻页 | 把图**切成上下半张**（生成阶段 crop），运行时压上半张高度 = 翻页 | 原生控件**没有裁剪文本能力**，所以数字/文字必须"画进图片再切" |
| 渐显 / 半透明 | **带 alpha 的 PNG 挂 `button.picTab`**（JSON 背景色 alpha 链路不可控） | 想整屏淡入淡出 = 叠 N 张 alpha 递增的整屏黑图做序列帧（成本：N 张 480x800，约 20KB/张） |
| 旋转 | 原生控件**不支持**旋转 ⇒ 用"预烘多角度图 + 换图"，或用横向压扁近似"转" | 真旋转只能上画布（= 游戏页才允许） |

## 4. ★★ SysApp（屏保 / 状态栏 / 输入法）的进/退时机

做"进屏保要干嘛、退屏保要复原"这类逻辑时，下面两条是**实测**的框架行为（不看会写出"退出侧永远不执行"的 bug）：

1. **退屏保后框架会把本页定时器停掉**（`performScreensaverOff` → `unregisterGlobalTouchListener` /
   `unregisterProtocolDataUpdateListener` / `unregisterKeyListener` → `onUI_quit` → **之后再没有本页 tick**）。
   ⇒ **"退出侧要做的事"（复原状态）只能挂 `onUI_quit`**；写成"每拍按 `isScreensaverOn()` 收敛"在
   退出这一侧**根本走不到**（血案：进屏保调暗背光能生效，唤醒后亮度**永远停在暗的那一档**）。
2. **SysApp 实例跨"进/退屏保"复用** ⇒ `onUI_init` **不是每次进屏保都跑**（只在进程内**第一次**显屏保时跑）。
   ⇒ **"每次进屏保都要做"的事（如调暗）要挂"刚进屏保的那一拍"**（tick 里 `!sReady` 那个分支）。
3. 进程若在**屏保显示中**被自愈重启，内存里的状态全丢 ⇒ 凡是"改了全局状态、退出要复原"的，
   都要**把复原凭据落盘**，开机时自愈恢复一次（见 §5 的亮度例子）。

> 进/退屏保本身由框架负责（超时自动进、触摸/按键自动退），应用侧不需要写"超时计时"；
> 但 ⚠️ 实测框架**不读** `EasyUI.cfg` 的 `screensaverTimeout`，必须用 API 显式设
> （`EASYUICONTEXT->setScreensaverTimeOut(30)` + `setScreensaverEnable(true)`）。

## 5. 配套模式：改了全局状态（背光/音量）必须"可复原 + 自愈"

以"屏保调暗背光"为例（真实需求），踩坑后的定稿做法：
- 进屏保：读当前背光 cur → 算 dim 值（**绝不超过 cur**，下限取 `min(下限, cur)`，否则用户本来调得很暗时会被"下限"**调亮**）→ `setBrightness(dim)`；
- **把 `cur` 落盘**（`/data/xxx.dat`，退化到 `/tmp`）；退屏保时 `setBrightness(cur)` 并**删掉凭据**；
- 开机自愈：启动时若发现有"未收尾的凭据"，先把用户值恢复回去（覆盖"屏保中被重启"的路径）——
  否则新进程会把"已经调暗的值"当成用户值记下来，**永远暗着**。
- 判据必须是**回读**（`getBrightness()` 打印出来），不是"我调用了 set"。

## 6. ★★ 真机动画验收：抓帧往返比动画还慢，所以必须让"应用可放慢 / 可重播 / 可指定相位"

| 事实 | 数值（实测） | 后果 |
|---|---|---|
| 一次抓帧往返（`cat /dev/fb0` + `adb pull`） | **1.2 ~ 2.4 s** | 600ms 的动画**连抓几十张都可能一张不中**（实测 26 连抓金币一帧没抓到） |
| 真实动画时长 | 0.3 ~ 0.7 s | 想抓"折到一半/飞到一半"必须放慢 |

⇒ 在**被测页自己的 QA 通道**里加三个旋钮（比"想办法抓得更快"划算得多）：
1. `slow <n>`：动画每 n × 帧周期推进一步（n=20 → 600ms 的动画变 12s，稳抓中间帧）；
2. `<anim>`：**一键重播整段动画**（否则只能等自然触发，验收周期不可控）；
3. `<anim> <ms>` / `enter <ms>`：**指定相位**开演 / 模拟"进入时的相位"。

> ⚠️ §6.3 那条是**踩出来的**：设备**会周期性校时**（实测同一小时内两次读"距整分"，
> 与 PC 时钟的差从 6s 变成 21s），所以"等 PC 到 `:59.0` 再下发进屏保"这种卡点**根本卡不准**；
> 时间相关的行为必须能在 QA 里**直接指定相位**。

配套的验收脚本套路（可照抄）：
- 连抓一批帧 → 每帧算**关键量**（元素 bbox / 与素材字模做 IoU 识别数字 / 某带平均亮度）→ 打成分行文本
  ⇒ 一眼看出"哪一帧里有目标元素"，再把那一帧留作证据图；
- 另做两张**素材与实拍的一致性**对照（图尺寸==控件盒、颜色/位置），比"看着对"可靠。

## 6.5 ★★ 用户说"卡"时怎么量：先分清「性能卡」还是「视觉台阶」

2026-09-18 实测（用户报"4 个数字变化时页面很卡"）：量完发现**逻辑侧完全无辜**，
真因是**帧率**（动画 20fps vs 面板 60Hz）。**三个判据一起看**，能一次分清：

| 量什么 | 怎么量（都不需要看屏幕） | 当时的实测值 |
|---|---|---|
| **本页 tick 间隔** | 每拍记 `gettimeofday` 毫秒，每秒打印"平均/最大" | 静止 50/51ms；最重场景仍 **49~51ms** ⇒ 定时器没被拖 |
| **本页单拍耗时** | tick 开头/结尾各取一次时间（含 `setPosition/setVisible` 的同步成本） | **≤1ms**（一拍照改了 **49** 个控件）⇒ 应用代码不是瓶颈 |
| **进程 CPU** | 采样 `/proc/<pid>/stat` 的 `utime+stime` 两次作差 | 静止 1.8% → 动画中 **4.2%** ⇒ 板上完全吃得下 |
| **面板刷新率** | `cat /sys/class/disp/disp/attr/sys`（会打印 `fps:` 与背光值） | **fps:60.9** ⇒ 60Hz 面板跑 20fps 动画 = **台阶感** |

判读口径：
- 前三个都正常 ⇒ **不是性能问题**，别再优化代码/搬线程；去查**帧率与曲线的离散度**；
- 帧率的"离散度"可以量化：慢放抓帧，量同一元素每帧的**宽度/位置序列** ——
  `88/50/18/50`（4 档跳变）就是台阶；`30/66/51/13`（连续过渡）就是平滑。
  这条比"看着顺不顺"可靠，也能作为修复前后的对照证据。

修复手法（本例）：时基 50ms → 25ms（20fps → 40fps）+ 把离散档位的运动改成**连续函数**
（旋转用 `cosf` 连续压扁、上升 ease-out、落下 ease-in）。代价实测：动画 CPU 4% → **10%**。
⚠️ 把时基调细后，所有"按拍数计"的时长要同步翻倍（闪烁周期、预热拍数…），
否则会静默变成一半时长；而 QA 的 `slow n` 语义是"每步 n × 帧周期" ⇒ 慢放倍数也会翻倍，
文档里的 `slow` 数值必须同步改（这类"参数隐含单位"最容易在调优时漏改）。

## 7. 反面清单（本项目实测踩过的）

- ❌ 累加 dt / 帧计数器做长时动画（会漂；配"跳帧优化"会冻帧）→ §1。
- ❌ 把"退出要复原"的逻辑写在 tick 里（退屏保后没 tick）→ §4.1。
- ❌ 依赖"进屏保时会调 `onUI_init`"（实例复用，不按次触发）→ §4.2。
- ❌ 运行时 `setBackgroundPic` 换透明图（变白方块）→ §3。
- ❌ 直接改 `data-x=-80` 想"从屏幕外进来"：**html2json 会把负坐标钳成 0** ⇒ 靠运行时 setPosition 才有效。
- ❌ 动画中途的**半透明**靠 JSON 背景色 alpha（链路不可控）→ 用带 alpha 的 PNG。
