# 游戏素材管线：PNG 运行时加载 + 60fps

> 起因（用户 2026-09-15）：*"游戏这样子绘制的效率太低了。通用的图标可以直接做成 png
> 图片存起来，然后直接加载起来。设计要做到 60fps，比如打地鼠的老鼠、地面、锤子、combo
> 都可以做成图片，只有动态的控件才考虑自己绘制。"*
>
> 一句话结论：**静态元素 = PNG 素材（改图只换文件），动态部分 = 代码绘制**。
> 打地鼠改造后 **21fps → 71fps**，2048 59fps；素材总共 148KB。

---

## 0. 先看结果（真机实测，2026-09-15）

| 项 | 改造前 | 改造后 |
|---|---|---|
| 打地鼠帧率（QA `fps`） | 21 次/秒 | **71 次/秒** |
| 2048 帧率（未改渲染，只受益于周期提升） | 30 次/秒 | 59 次/秒 |
| 打地鼠渲染代码 | 草地 60 行 + 洞/鼠/锤/光效 ≈ 200 行几何绘制 | 9 次 `blit` + 动态位移/淡出 |
| 打地鼠素材 | `PgWhackArt.h` 580KB（编进 .so，改图要重编重刷机） | 148KB PNG（改图只换文件） |
| 游戏内贴图缓存占堆 | — | 1091KB（退出游戏自动归还） |

## 1. 三层结构（加素材只动前两层）

```
① resources/images/game/<游戏>/*.png     ← 素材本体（1:1、带透明通道）
② src/core/PgGameArt.h                   ← **清单**：路径 + 尺寸 + 锚点（生成物，几 KB）
③ core/PgSprite.{h,cpp} + platform/PgSprite.cpp  ← 运行时加载 + 缓存（按路径）
```

- ① 由 `tools/gen_game_art.py` 生成（也可以直接放美术导出的图）。
- ② 只有"路径/尺寸/锚点"，**没有像素** —— 所以改图**不用重生成、不用重编**；
  只有改尺寸或改锚点才重跑生成器。
- ③ `pg::sprites().get(路径)` → 首次解码 + 缓存；`pg::sprites().clear()` → 归还堆。

### 三层的边界（别越界）

- **core 层不依赖 easyui**（工程纪律，见 `PgGame.h`）：所以解码器是**注入**的
  （`SpriteLoader` 接口），设备侧实现在 `platform/PgSprite.cpp`，PC/离屏验收没有实现
  ⇒ `get()` 返回 0，**游戏必须能降级**（`blit()` 里直接 `return`，只少画一个元素）。

## 2. 写一个游戏素材的完整流程

```bash
# 1) 在 tools/gen_game_art.py 里加烘图函数 + 写进 items 清单
# 2) 生成 PNG + 清单头 + 预览拼图
python tools/gen_game_art.py
#    自检会拦两类问题：空图、内容**贴到图片边界**（= 已被裁，运行时就是"少一块"）

# 3) 游戏里引用（锚点对齐 + 自动尺寸自检）
blit(c, gameart::kWhackMole, cx, cy);          // 静态贴
blitA(c, gameart::kWhackRays, cx, cy, alpha);  // 带整体透明度（淡出用）

# 4) 真机
./fun.exe launch && kill -9 $(ps|grep zkgui)   # 见 §5 的重启纪律
echo "14 1" > /tmp/pg_autostart                # 进打地鼠
echo "fps"  > /tmp/pg_autostart                # 测帧率
```

`blit()` 是游戏内的本地小助手（见 `PgWhack.cpp` 匿名 namespace），只做三件事：
**查缓存 → 尺寸自检（不符打一次日志）→ 按锚点贴**。

## 3. 硬规则（违反会"静默出错"，肉眼看不出）

1. **1:1，不许缩放**。`Canvas::drawSprite` 不做缩放/插值 —— 要别的尺寸就多出一张图。
   与"所有东西不能做拉伸"是同一条纪律（`tools/check_stretch.py` 管 UI 侧）。
2. **每张图必须在清单里声明锚点**（图内的参考点：洞中心 / 地鼠圆心 / **锤头中心**）。
   贴图写作 `drawSprite(*s, x - ax, y - ay)`。打地鼠的锤子三帧锚点**各不相同**
   （离线绕握把转出来的），用固定锚点会"换帧跳位"。
   ★ **锚点 = "这个元素在语义上钉在哪里"**，选错了元素就会飘：
   锤子最初用**握把**当锚点（握把落在触点、锤头探到上方约 70px，怕被手指挡住），
   用户 2026-09-15 要求"点击的时候锤头落点要直接到老鼠头上" ⇒ 改成**锤头中心**当锚点，
   三帧的锤头就**钉在触点不动、只有柄在摆**，看起来才是"照着点下去"。
   （旋转中心仍是握把 —— 挥动的支点在那里，**锚点与旋转中心是两件事**。）
3. **素材带透明背景**（RGBA PNG），不是烘底图 —— 逐像素 α 混合。
   ⚠️ 需要"遮挡"（洞口前沿盖住地鼠下半身）时，把**该不透明的部分画满**、
   其余留透明即可，不需要 masks（打地鼠的 `hole_front.png` 就是只保留下半的洞口）。
4. **内存**：贴图解码后占 `w×h×4`。整屏底图 480x540 ≈ **1MB**。
   本板只有 56MB 内存 ⇒ **必须在退出游戏时 `sprites().clear()`**
   （宿主 `exitGameToMenu()` 已统一调用，别再缓存 `const Sprite*` 跨场景用）。
5. **贴图路径是"资源相对路径"**（`images/game/whack/mole.png`），
   **由加载器自己拼资源根** —— 见 §4.2。
6. **失败只试一次**：解不开的路径记成坏路径，不重试（重试 = 每帧一次解码 = 帧率归零）。
   QA `spr` 能看失败计数。
7. ★★ **想上 60fps，贴图必须"整图不透明"**（2026-09-15 消消乐实测挖出来的，见 `docs/match3.md` §7）：
   memcpy 快路径要求**全部**像素 alpha == 0xFF，**一个** alpha<255 就退回逐像素混合。
   - **每格的图里带上它的底**：消消乐第一版是"透明糖果贴到凹槽上"，64 格 × 56×56
     = 20 万像素/帧全走慢路径 ⇒ render **17.7ms / 33fps**；把凹槽底烘进糖果图（变不透明）
     ⇒ **4.6ms / 58fps**。**这条对"每格/每 tile 一张小图"的场景普遍成立。**
   - `ImageDraw` 的半透明 `fill`（`rgba(色, 40)`）会**直接写入 alpha**（PIL 的 draw **不做**合成）
     ⇒ 整屏底图被判成非不透明、快路径静默失效。要"叠加"就写
     `lerp(底色, 叠加色, alpha)` 预混合（t 与 alpha 同为 0..256 语义，不透明底上视觉等价）；
     整屏/铺满类素材再加一道 `force_opaque()` **兜底 + 告警**（抹平 alpha 会把半透明叠加
     变成实心色块，那是个视觉 bug，必须让它出声）。
   - ⚠️ **不是 `resize(LANCZOS)` 的锅**：对照实验——整图全不透明时缩回后 `alpha<255` = **0**，
     有一块半透明 fill 时 = **112240**。别去怀疑重采样。

## 4. 实测踩到的四个坑（都很难凭直觉发现）

### 4.1 `BitmapHelper::loadBitmapFromFile` 的 `reqBpp` **必须传 0**

签名是 `loadBitmapFromFile(bitmap_t *&, const char *path, int reqBpp)`，名字像是"目标位深"，
**但实测不是**（QA `spr` 逐值试出来的，96x88 的 PNG）：

| reqBpp | bits | bytes | pitch | 含义 |
|---|---|---|---|---|
| **0** | 32 | 4 | 384 = 96×4 | ✅ 标准 32bpp ARGB8888 |
| 16 | 128 | 16 | 1536 | 每像素 16 字节 |
| 32 | 0 | 32 | 3072 | 每像素 32 字节 |

传 32 的**症状极隐蔽**：加载"成功"、尺寸也对，但像素位置全错 ⇒ 贴出来是花屏/全黑。

**格式结论（探针图 `resources/images/game/_probe.png` 验出）**：
`0xAARRGGBB` 小端（内存序 B,G,R,A）、**非预乘 alpha** —— 与 `Canvas` 的 uint32 完全一致，
解码缓冲可以**直接** `drawSprite`（`platform/PgSprite.cpp` 会逐行拷成紧凑缓冲）。

### 4.2 路径要自己拼 `resPath`（相对路径会失败）

`loadBitmapFromFile` 内部就是 `fopen`，**不做资源解析**；进程 CWD 不是资源根。
资源根写在 `EasyUI.cfg` 的 `resPath`，而且**调试/固化两套值不同**：

| 部署 | cfg 位置 | resPath |
|---|---|---|
| `fun launch`（调试） | `/tmp/EasyUI.cfg` | `/tmp/ui/` |
| `fun pack` + 刷机（固化） | `/res/etc/EasyUI.cfg` | `/res/ui/` |

⇒ 加载器读 cfg 取 `resPath`（先 `/tmp` 后 `/res`，与框架优先级一致），
**同一份代码两种部署都能找到素材**（`resRoot()`）。

### 4.3 `pitch` 可能不等于 `w*4`（所以 Sprite 有 `stride`）

当前解码路径实测是紧凑的（`pitch == w*4`），但 `bitmap_t` 的 pitch 是**字节**、
且受硬件对齐约束。所以：

- `Canvas::Sprite` 加了 `stride` 字段（**0 = 等于 w**，老的 `{px,w,h}` 聚合初始化依然有效）；
- 加载器**逐行拷贝**成紧凑缓冲（`memcpy(..., w*4)`），而不是整块 `memcpy`。

### 4.4 全透明图会被"整张不显示"

若某张 PNG 没有 alpha 通道，解码器可能给出**全 0 alpha**，
而 `drawSprite` 跳过 alpha=0 的像素 ⇒ 元素**完全不显示**、日志却一切正常。
加载器里加了兜底：alpha 全 0 且 RGB 有内容 ⇒ 补成全不透明 + 打 `LOGW`。

### 4.5 多帧动作：旋转必须在**放大的画布**上做（否则缺角）

**症状**（用户 2026-09-15 报"锤子缺了一个角落"）：锤子的某一帧缺一块，而且**只在某几帧**出现
（`up` 帧缺右边、`hit` 帧缺左边，`mid` 帧完好）—— 很容易被当成"美术风格如此"。

**根因**：PIL 的 `rotate()` **不扩展画布**，转到画布外的像素**直接丢失**；
原实现的"旋转后把内容包围盒居中"只能改善位置，**救不回已经丢掉的像素**。
实测（SS=4 的 480×480 工作画布）：`up` 帧右边丢 **39px**、`hit` 帧左边丢 **55px**
⇒ 缩到最终 120×120 就是 10~14 像素的缺口。

**正解**：先把图贴进 **3 倍大的画布**（锚点对齐到画布中心），在那里旋转（绝不裁），
再降到最终尺度、取"刚好装下内容"的居中窗口，最后按窗口偏移换算每帧的锚点
（见 `tools/gen_whack_art.py` 的 `make_frames()`）。

**⚠️ 顺带修正了自检的口径**：原来的自检是"内容有没有贴到图片四边" ——
**这个判据检不出被裁**（裁完自然就不贴边了）。要检的应该是**源侧**：
「旋转之后、裁剪之前，内容有没有超出工作画布」+「内容装不装得进目标尺寸」
（装不下就报错退出，那是"该调小缩放系数或加大素材尺寸"的信号，别默默裁掉）。

**通用纪律**：凡是"离线做几何变换再出素材"（旋转/斜切/投影），
一律 **先扩画布再变换**，并让生成器在**变换那一步**就检查边界。

### 4.6 core 层的日志要走钩子

`core/*` 不能用框架的 `LOGD`（不依赖 easyui）。所以有 `core/PgLog.h`：
宿主在 `onUI_init` 里 `pg::setLogSink([](const char *m){ LOGD("%s", m); })`，
core 里用 `pg::logInfo(...)`。**没这一步，"素材尺寸与清单不符"在设备上就是静默的**
（画出来只是差几像素）。

## 5. 帧率：怎么从 21 干到 71

三个手段，按收益排序：

1. **静态内容合并成一张底图**（−10 万像素/帧）
   草地 + 9 个洞口位置固定 ⇒ 生成器里直接合成 `bg.png`。
   原来每帧贴 1 张草地 + 9 张洞口；现在 1 张。
2. **整图不透明 ⇒ memcpy 快路径**（`Canvas::Sprite::opaque`）
   `SpriteBank::get()` 在**加载时**扫一遍算出 `opaque`（别每帧扫）。
   `drawSpriteA` 遇到 `opaque && 无整体淡出` 就逐行 `memcpy`，不逐像素算 alpha。
   实测 49fps → 58fps。
3. **主循环周期分档**（`mainLogic.cc`）
   `LOOP_MS = 33`（列表/工具页，省电） / `LOOP_MS_GAME = 16`（游戏内），
   在 `startGame` / `exitGameToMenu` 里用 `mActivityPtr->resetUserTimer(TIMER_LOOP, ...)` 切换。
   ⚠️ `resetTimer` 这类是 `mainActivity` 的成员 → 自由函数里要写 `mActivityPtr->resetUserTimer(...)`。

想再往上走只剩**脏矩形**（只重绘变化区域）—— 需要游戏侧上报"本帧改变了哪些矩形"，
本工程暂不做（当前帧率已有余量）。

## 8. ★★ 帧率诊断：先量再改（新增 QA `bench`）

素材化只解决"自己画的静态图形贵"，**帧率还有别的敌人**。所以先加了工具：

```bash
echo "bench" > /tmp/pg_autostart     # 2 秒后打印每帧耗时拆解
# → bench 144 帧  每帧均值 update=3us render=2600us present=15us 整个回调=2888us（帧间隔≈13961us）
```

**三个反直觉的实测结论**：

| 结论 | 数据 | 影响 |
|---|---|---|
| **`present()` 几乎不花时间** | 15us | 别再怀疑"上屏慢" |
| **整屏半透明遮罩 = 8ms** | 贪吃蛇 render 10.7ms，其中遮罩占 8.5ms | 所有游戏的 READY / OVER / PAUSED 都被拖到 **44fps** |
| **静止画面重绘纯属浪费** | 同上：遮罩内容一动不动 | ⇒ 跳过重绘即可（下面） |

**过程**（可复现的排错路径）：先量出贪吃蛇 render=10.7ms → 二分（只画底图 = 1.9ms，底图+食物 = 1.9ms）→ 定位到蛇身之外 →
再量发现**同一份代码 render 一会儿 2.2ms 一会儿 10.7ms** ⇒ 与游戏**状态**相关 → 锁定 `blendRect(全屏遮罩)`。
（顺带否掉了最初的两个猜测：天空渐变、整数除法 —— 都不是主因。**猜不如量**。）

### 8.1 修法一：静止画面只画一帧（收益最大）

`Game::stillFrame()`：默认 `state_ != GSTATE_RUNNING`（覆盖绝大多数游戏的覆盖层场景），
宿主在"仍是同一静止态"时**直接跳过 render + present**。

```cpp
// 覆盖层上还有动画的，必须覆盖它（否则特效会冻在半路）：
bool GameMines::stillFrame() const { return stillUnless(boomMs_); }   // 踩雷爆炸
bool GameWhack::stillFrame() const {
  if (swingMs_ > 0 || comboFxMs_ > 0) return false;   // 锤子回落 / 连击弹出
  if (idleMs_ < 300) return false;                    // 锤子切帧中
  return state_ != GSTATE_RUNNING;
}
```

⚠️ 加这个机制时**必须逐个游戏检查 `update()` 在非 RUNNING 时是否还在推进计时器**
（`if (over_) return;` 之前的那几行），凡是推进了又画出来的，都要列进 `stillUnless`。
本次核对出 7 个：2048 / 俄罗斯方块 / 打飞机 / 小鸟 / 贪吃蛇 / 扫雷 / 打砖块。

✅ 验收：状态切换必须重绘（抓屏逐帧比对，不能出现"卡住"）。

### 8.2 修法二：`blendRect` 查表（顺带收益）

`x / 255` 看起来是瓶颈（Cortex-A7 没有硬件除法），**实际编译器早把常量除法优化成乘法移位** ——
改成 256 项查表只省了 23%（10.7 → 8.2ms）。仍然值得留着（大面积混合都有收益），
**但它不是主因**，别指望靠它到 60fps。

### 8.3 全量实测（v1.23.0，14 款游戏）

| 游戏 | 静止/READY | 进行中 | | 游戏 | 静止/READY | 进行中 |
|---|---|---|---|---|---|---|
| 2048 | 99 | 59 | | 打砖块 | 99 | 71 |
| 俄罗斯方块 | 99 | 58 | | 打地鼠 | 99 | 71 |
| 打飞机 | 99 | 78 | | 记忆翻牌 | 99 | 63 |
| 小鸟 | 99 | （自动结束） | | 五子棋 | 99 | 67 |
| 贪吃蛇 | 99 | （自动结束） | | 数字华容道 | 99 | 57 |
| 扫雷 | 99 | 57 | | 推箱子 | 99 | 66 |

> ⚠️ 上表是**固化版**（flash）的数。同一台设备跑**调试版**（`fun launch`，/tmp tmpfs 占 RAM）
> 时消消乐只有 **51~58fps** —— 差别不在渲染代码，而在内存压力
> （`Shmem 12.2MB / MemFree 5.5MB` → `1.2MB / 23.7MB`，主循环间隔 18.8ms → 16.7ms）。
> **量帧率前先确认跑的是哪一版**（`cat /proc/meminfo` 看 `Shmem`），否则会把内存问题当成渲染问题。

改动前：静止态 **44~58fps**（受遮罩拖累），瓶颈游戏（贪吃蛇 40 / 小鸟 44）。
**全部 ≥57fps，多数 ≥60**。剩下 57~59 的几款是"每帧重画几十~几百个小方块/格"（如扫雷 256 格、
消消乐 64 格底图+糖果），要继续提升得把格子也素材化/合并（收益约 +3fps，性价比低，暂不做）。

> ★★ **消消乐这一轮（2026-09-15）把素材化的一条隐形前提挖出来了**，见 `docs/match3.md` §7：
> **贴图必须"整图不透明"才走 memcpy 快路径** —— 带透明像素 = 逐像素 alpha 混合。
> 消消乐第一版 64 格**透明**糖果 ⇒ render **17.7ms / 33fps**；把**格子底烘进糖果图**
> ⇒ **4.6ms / 58fps**。推论：**"每格一张小图"的场景，图里要带上它的底**。
> 另一半是 `ImageDraw` 的半透明 `fill` 会**直接写入 alpha**（PIL 的 draw 不做 alpha 合成）
> ⇒ 底图被判成非不透明、快路径静默失效；正解是 `lerp(底色, 叠加色, alpha)` 预混合
> （**不是** `resize(LANCZOS)` 的锅 —— 有对照实验，整图不透明时缩回后 alpha 伪影 = 0）。
