# 流媒体"换源 / 换台"的竞态，与自动验收钩子的三个时间陷阱

> 🔍 **检索导引（命中条件）**：用户问「**换台/切频道之后再也播不出来**」
> 「**连续切了几个源之后全都报"打不开"**」「**写了个批量自检脚本，整批全 FAIL，但手动点同一个明明能播**」
> 「**优雅停止之后马上起新流失败**」「**日志说启动完成、界面却永远没反应**」
> 「**adb logcat 突然什么都读不到了**」「**PC 上探测通的地址，板子上放不出来**」
> 且场景为 **嵌入式流媒体（HLS / HTTP 流 / RTSP）在 FlyThings / EasyUI 一类的工程里做批量自检 / 换源**
> → **本篇就是答案**。
> 相关：`../v85x/online-audio-visualizer.md`（频谱取点）、`deploy-scene-map.md`（部署链条）

## 一句话

**"优雅停止"几乎都是异步的**：调用 `stop()` 只置一个请求，真正的收尾（关解码器、排空、
放线程）发生在另一个线程里。**"停止"与"起新流"之间必须有一个"等它真的停了"的状态**，
否则第二次起流会被直接拒掉 —— 表现就是**整批自检全部 FAIL，而手动单点同一项却正常**。
同理，自己驱动状态机的验收钩子**不能指望宿主的状态机会被顺带推进**。

## 0. 实测环境

| 项 | 实测值 |
|---|---|
| 平台 | 全志 V851s（FlyThings / EasyUI 2.9.0） |
| 流引擎 | 自建：ffmpeg 软解 + 自写 HLS 中继（拉清单/下分片/拼 TS）+ 常开 PCM 输出流 |
| 自检通道 | 文件式 QA（`/tmp/<页>cmd`，内容变化才执行） |
| 源 | 61 个在线电台（HTTP 直连 MP3/AAC + HLS m3u8） |

## 1. ★★ `stopForSwitch()` 只是"请求停止"，起新流前必须等它真的停

**现象**：批量自检脚本逐台起流，结果**整表 61 台全报"打不开"**，而且每台 **0.1 秒**就"出错"；
可同一台手动点播**明明在出声**。

**根因**：换源用的是"优雅停止"（`stopForSwitch()` 之类）——它只做两件事：
置停止请求标志、让收尾**按自然结束**走（避免触发"应用复位"）。真正的收尾在解码线程里，
要排空在途帧、关解码器、退出线程，**耗时几十到几百毫秒**。
这期间 `running()` 仍是 `true`；此时调用起流接口，会被**判为"已有任务在跑"直接拒绝**。

**正解（三件事一起做）**：

```cpp
// ① 起流前确认引擎空闲（做成状态机，不要死等）
if (player.running() && nowMs() - phaseMs < 2000) return;   // 还在收尾，下一拍再看
startStream(url);

// ② "很快就被拒"与"真的打不开"要分开记账
bool refused = (phase == ERROR && elapsedMs < 400);   // <400ms 报错 = 引擎还忙
if (refused && retry < 3) { stopStream(); waitIdle(); retrySameStation(); return; }
recordFail();                                          // 只有重试过才记"这个源坏了"

// ③ 第一台之前也要等（进去时引擎可能正被上一个源占着）
```

**实测对照**：

| 写法 | 结果 |
|---|---|
| `stop(); start(next);` 连着调 | 61 台 **0 秒全 FAIL**（每台 0.1s 出错） |
| `stop(); 等 running()==false（上限 2s）; start(next);` + 拒绝重试 | **61 台全 OK**，其中少数几台第 1 次被拒、重试后 0.9~1.0s 出声 |

★ **排查口诀**：**"整批全坏"几乎一定不是"源全坏了"，而是"批量流程自己的时序错了"。**
先对比"手动单点同一个"的结果 —— 能播就说明问题在流程，不在源。

## 2. ★ 自己写状态机时，别忘了"宿主的状态机是别人在推"

验收钩子常要自己走一个循环（起流 → 等结果 → 下一个）。**别把宿主的相位机关在门外**：

- 宿主里"真的开始播了"通常是由**主循环的相位机**判的（例：`positionMs() > 0` ⇒ 从"连接中"抬到"播放中"）；
- 而你的自检循环一旦接管了这一拍（宿主定时器里"走 A 就不走 B"），**相位机就不会被推进**；
- 于是你永远看到"还在连接中"⇒ **每台都"等出声超时"**，而其实声音早出来了。

**做法**：自检循环里**把相位推进那几行照抄一遍**（判据、失败判据都抄），
或者在设计上让自检"借用"宿主的相位机而不是绕过它。

**反面清单**（都实测踩过）：
- 以为"我的循环跑起来了，宿主那套判据自然会跟着更新"；
- 用"另一个状态机的字段"当自己的结论（它没被推进，字段就是死的）。

## 3. ★ 超时窗口别把"慢"判成"坏"；给可疑项留一条单独复测的路

**现象**：窗口设 6000ms 时，一个源被记为"打不开"；单独复测它**能播**，只是**要 7.2s 才出声**。

**做法**：
1. 超时阈值按"**最慢的正常样本**"留余量（实测 HLS 要 1.5~3.6s，个别直连源 7.2s ⇒ 窗口定 9s）；
2. 结论里区分"**打不开**"与"**慢**"（有条件的把"出声耗时"一起记进报告）；
3. **给每一项留"单独复测"的命令**（`<项> <n>`），不要只有"批量"这一条路 ——
   批量结果用来发现异常，单项复测用来定性。

★ 这条是通用原则：**评估工具本身不能把"慢"当成"坏"**，否则你会去修一个根本不存在的问题。

## 4. ★ 日志服务被高频噪声刷爆之后，会"整块卡住"

**现象**：`adb logcat -d` 从某一刻起**全空**（连内核/网络子系统的日志都没有），
应用自己的日志再也进不来；但**应用其实活着**（CPU 在涨、界面在画）。
本板日志缓冲只有**十几行**，而 WiFi 扫描一秒钟能刷十几行 ⇒ 应用级日志被挤掉/服务卡死。

**恢复**：`setprop ctl.restart zkswe`（重启应用）或重启设备；**恢复后日志会立刻正常**。

**排查纪律（本次最有价值的一条）**：
> 「界面没反应 / 命令没生效」这类"好像死了"的现象，**先做一次干净的重启 → 复现**。
> 本次的真相就是"设备状态卡住了"，同一个包重启后 `init ok` 一切正常 ——
> **一次干净重启比十轮猜测便宜**。

**旁证时别只信一种**：日志读不到时，用
① 进程 CPU 增量（`/proc/<pid>/stat` 的 utime+stime 差分）判"是否还在跑"；
② 抓屏判"画面在不在变"；
③ 落盘文件（让 QA 把结论写进 `/data/xxx.txt`，日志坏了也能取证）。

## 5. ★ PC 侧探流（"这个源能不能用"）的两个坑

1. **PC 上的 `http(s)_proxy` 会把流"改写"**：同一个 URL，走代理时首字节是随机数据、
   绕过代理才是 MP3 ⇒ 探针必须强制直连（`build_opener(ProxyHandler({}))`）。
   设备上通常没有代理，**直连才代表真机**。
2. **流前面常有一段非音频前缀**（实测某 CDN 的 MP3 同步头在第 6/15/144 字节）
   ⇒ 找同步头要**扫一段（前 8KB）**，并且**用"第二帧"确认**（按帧长算出下一帧位置、
   核对同步字）——只看头几个字节会把能播的源误判成打不开（本次误报 12 个源）。
3. 顺带：**`ICY 200 OK`** 这类 Shoutcast 响应，`http.client` 会当非法状态行报错，
   但设备的 ffmpeg 是认的 ⇒ 探针要自己用裸 socket 读，别把好源判死。

★ 最后一条总原则：**"能不能用"的结论一律以真机为准**（PC 能连 ≠ 板子能播：
DNS/IPv6/TLS 握手/解码器支持度都不一样）。PC 探针只负责把 100 个候选砍到 70 个。

## 6. 一页速查

| 现象 | 第一嫌疑 | 立即验证 |
|---|---|---|
| 批量自检整批全 FAIL，手动单点正常 | 起流前没等"真的停了" | 看失败耗时：<400ms 就是被拒（引擎忙） |
| 每项都"等出声超时" | 自查循环绕过了宿主相位机 | 自检里自己推一遍相位（`positionMs()>0`） |
| 个别项"打不开"，单独复测能播 | 窗口太紧，把"慢"判成"坏" | 把"出声耗时"记进报告，窗口留余量 |
| `adb logcat -d` 全空、应用还在跑 | 日志服务被高频噪声卡住 | `setprop ctl.restart zkswe` 后复读 |
| 界面完全不动、命令没反应 | 可能是设备状态卡住（不是新包坏了） | **重启 → 复现**，别先怀疑自己的改动 |
| PC 探针报"不是音频" | 走了代理 / 只看头几字节 | 强制直连 + 前 8KB 扫描 + 第二帧确认 |

## 7. 换板 / 换引擎对照清单

- [ ] 你的"停止"是同步还是异步？（读实现，别读文档；判据 = 什么时候 `running()` 变 false）
- [ ] 起流被拒时的**返回值/耗时**能不能区分"忙"与"坏"？（不能的话，先补可观测性再写批量）
- [ ] 谁在推进"连接中→播放中"？你的循环有没有把它挡在门外？
- [ ] 日志缓冲多大？噪声源（扫描/轮询）会不会把应用日志挤掉？
- [ ] 有没有"落盘报告"这条不依赖日志的取证路？
- [ ] 超时阈值有没有按"最慢正常样本"留余量？单项复测命令有没有？
