# 自定义 GUI 渲染五条路（在 FlyThings 上借开源渲染生态 / 自绘画面）

> **检索导引**：FlyThings 上怎么做自定义绘制 / 自绘控件 / canvas / 画布 / 仪表盘 / 指针表 /
> 想用 LVGL / cairo / SDL / nanovg / stb 画东西 / 离屏渲染成图再显示 / 直接写 /dev/fb0 /
> 能不能起 GTK/Qt / 视频层怎么叠加 / disp 图层 / releaseLayer / 一半用框架一半自己画 /
> 复杂动画性能不够怎么办。

## 0. 前提事实（三条，决定所有方案）

1. **应用是 Linux 进程 + 自绘 framebuffer**：框架自己在往 fb（`/dev/fb0`）画，
   **不是独占的** ⇒ 直接从别的线程往 fb 乱写会被框架重绘覆盖。
2. **V85X 有 disp 多图层**：视频/摄像头走独立硬件图层，可与 UI 层叠加（实测：
   **视频解码返回后必须 `releaseLayer`，否则黑屏**）。
3. **"软渲染"要说清是哪一段（2026-09-30 更正）**：**绘制进内存画布**那一段的代价取决于
   实现/面积（我们工程自研的 `src/core/PgCanvas.*` 就是自己的软件实现）；
   但 **内存画布 → 屏幕这一段是硬件合成** —— 平台在**内存拷贝(bitblt) / 透明 α 混合 /
   90° 旋转**上都提供能力（我方实证：`ZKTextView::setBackgroundBmp()` 挂画布 + `setInvalid()`
   触发刷新，「**控件->屏幕走硬件加速**」见 `src/platform/PgDisplay.h`；`misc::bitmap_rotate`
   支持 90° 整数倍）。⇒ **不要把"我们的实现是软件"说成"平台只能软渲染"**；
   平台做不到的是**任意角度旋转位图**（要自己逐帧算，先例 `components/vinyl`）。

## 1. 五条路总表

| # | 路径 | 能力 | 代价 | 验证状态 |
|---|---|---|---|---|
| ① | **框架内自绘**（ZKPainter / 自定义 view / canvas） | 与框架同层，控件级融合 | 软渲染性能上限；画布有规格限制* | ✅ 本工程已验证 |
| ②a | **预烘帧序列**（PC 离线渲好 → 图序列/贴图） | 视觉最好，运行时几乎零成本 | 只适合固定视角/固定逻辑 | ✅ 已验证（宠物精灵/视频转贴图） |
| ②b | **运行时离屏渲染**（cairo/SDL/LVGL 渲到内存 → 交框架显示） | 任意矢量/脚本化画面 | 每帧拷贝带宽；需自管缓冲 | ⚠️ **未验证**（需按 §3 自证） |
| ③ | **独立硬件图层**（disp layer / 视频层） | 性能最好，与 UI 并行 | 要管层的顺序/裁剪/释放 | ✅ V85X 已验证（releaseLayer 纪律） |
| ④ | **独立进程 + 独立图层** | 解耦最好（渲染崩了不拖 UI） | 帧传输（共享内存/文件）+ 生命周期管理 | ⚠️ **未验证** |
| ⑤ | **LVGL 整体接管 fb**（框架退为服务层） | 拿到开源 GUI 全生态与硬件加速 | **这不是"借用"，是迁移** | ⚠️ 未验证（战略选项，见方案对比文档） |

\* 画布规格限制（**2026-09-30 更正**）：动画计时必须用**绝对时钟**。
⚠️ 旧文写的「文字 `scale` 必须是常量（变量不生效）/ 画布宽 ≤448px」**是误记，已作废**：
二者都不是画布/引擎限制 —— `scale` 那条来自**我们的自研字库只预烘有限档**（档位需编译期常量，
超档位会走位图放大 = 拉伸，违反工程"不许拉伸"要求；**FlyThings 画布对 scale 本身无限制**）；
`448` 是**某工程 UI 的内容区宽**（480−2×16 的布局值）。详见 `devflow/render-extension-boundary.md`。

## 2. 逐条要点

### ① 框架内自绘（最安全，优先选）
- 适用：仪表指针、进度/电平条、简单矢量图、棋子/方块类小面积绘制。
- 本工程实证：8 款画布游戏（软渲染）、VU 表指针（用框架自带指针控件比"预烘 N 帧切 visible"省内存）。
- 判断线：**如果一帧的绘制面积 < 屏幕 1/4 且非全屏动画，走这条就够**；超了就上 ②/③。

### ②a 预烘帧序列（性价比最高）
- 适用：角色动画、状态切换、循环动效、从视频抽出来的贴图。
- 纪律（来自视频转贴图实战）：**先逐帧量清楚**（机位/背景/水印/主体是否被切）→ 抠像 →
  **一次统一缩放 + 固定画布 + 固定锚点**；帧间隔由源片反推。
- 注意：被边缘切过的帧只能用于"从边缘进出"。

### ②b 运行时离屏渲染（未验证，价值高）
- 形态：把开源渲染库渲到**内存画布**，再把画布交给框架显示（换图/贴图控件）。
- 选件建议（按嵌入式友好度排）：
  | 库 | 形态 | 说明 |
  |---|---|---|
  | **stb_image / stb_truetype / stb_image_write** | 纯头文件 | 零依赖，最适合嵌入式；解码/写字够用 |
  | **libpng / lodepng** | 静态库 / 单文件 | PNG 读写 |
  | **nanovg** | 源码 | 矢量绘制，可走 GL 或软后端 |
  | **cairo** | 静态库 | 矢量/文字最全，体积偏大 |
  | **LVGL（当库用）** | 源码 | 只借它的渲染器/控件层，不接管整套 |
  | SDL2 | 静态库 | **偏重**，除非已有移植 |
- 必须自证的判据：① 每帧拷贝的实际耗时（目标 ≤ 一帧预算的 1/3）；② 与框架重绘是否打架
  （抓屏连续两帧比对）；③ 内存峰值（tmpfs/堆）。

### ③ 独立硬件图层（V85X 视频/摄像头场景的首选）
- 实测纪律：**视频解码返回后必须 `releaseLayer`**；层配置漏关（格式区间）会导致黑屏。
- 抓屏陷阱：**fb 抓图看不到这一层** ⇒ 验收必须用截图工具的 video layer 通道，否则会误判"没画面"。

### ④ 独立进程 + 独立图层（未验证）
- 适用：视频预览、持续动画仪表、需要崩溃隔离的模块。
- 关键设计：帧传输走共享内存（避免文件 IO）；父子/看门狗关系要写清，否则"渲染进程死了 UI 不知道"。

### ⑤ LVGL 接管 fb（战略选项，不是"借用"）
- 含义：FlyThings 只留服务能力（网络/音频/硬件门面），UI 整层换成 LVGL。
- 触发条件：出现"框架渲染做不到的页面"且无法用 ①②③ 绕过，**并且**产品愿意承担迁移与验证成本。
- 与本文的关系：本文的 ①②③ **正是为了把这一天尽量推迟**——能绕开就不动架构。

## 3. AI 的决策树（照这个顺序问）

```
要画的东西是"静态画面/几张图切换"     → ②a 预烘帧序列
是"小面积逐帧绘制"（指针/方块/波形）   → ① 框架内自绘
是"视频/摄像头"                        → ③ 独立硬件图层（记住 releaseLayer + 用 video 层抓屏）
是"整个页面复杂动画/矢量、且①②③都顶不住" → 先评估 ⑤，同时试 ②b 离屏渲染
需要崩溃隔离/多模块并行               → ④（未验证，需先做 3 天原型）
```

## 4. 禁忌（硬红线）

1. **不要在框架进程里起 GTK/Qt 自己的 main loop** —— 会和框架抢 fb/事件；
2. **不要往 `/dev/fb0` 乱写** —— 框架在画，会被覆盖（要独占就先按 ⑤ 接管）；
3. **不要以为"浮层透明就穿透"** —— 框架里 `touchable=false` 的浮层照样吃触摸；
   要能点的按钮**每层祖先都要 `touchable=true`**；
4. **不要用 `diff==0` 判"画面没变"** —— 双缓冲/pan 会让你抓到旧帧（抓屏要取多张、看颜色数最多的那张）；
5. **不要在没自证判据前就说"这条路能行"** —— 未验证的路径必须产出判据文件。
