# 节奏钢琴 / 打鼓（下落式节奏 · 共用内核）

> 2026-09-16 新增，同日修一个**真机才看得出的"完全不下落"** 缺陷（v1.30.6）。
> 第 28/29 个应用、第 19/20 款画布游戏（slot 28 / 29）。
> 实现：`src/core/PgPiano.cpp`、`src/core/PgDrum.cpp`、共用内核 `src/core/PgMusic.h`；
> 素材：`tools/gen_instr_art.py`（PIANO / DRUM 段）；几何常量一起写进 `src/core/PgGameArt.h`。

## 1. 玩法与链路

| 项 | 节奏钢琴 | 打鼓 |
|---|---|---|
| 操作 | 8 条音轨（do..do'），音符落到判定线时点对应琴键 | 6 个鼓位（底鼓/军鼓/踩镲/低嗵/高嗵/吊镲），鼓点落地时敲鼓垫 |
| 判定 | Perfect ≤60ms / Good ≤130ms / OK ≤200ms，超出即 MISS（`music::judgeOf`） | 同左（共用内核） |
| 计分 | `base + combo*2`（加成封顶 200）；结算页给**准确率千分比** | 同左 |
| 起播 | 留白 `kLeadInMs = 1500ms`（音符先掉下来，给反应时间） | 同左 |
| 曲目 | 小星星 / 欢乐颂 / 玛丽小羊 / 划船歌（`deg` 字符串谱面） | 基础练习 / 摇滚节奏 / 迪斯科 / 鼓点独奏（8 分音符模式串） |
| 音量 | 8 个独立音高 wav（`SFX_PNO1..8`，由 `tools/gensfx.py` 合成） | 6 个鼓音（`SFX_DRM1..6`） |

数据流（两款一致）：

```
loadSong/loadChart  谱面字符串 -> notes_[{lane, atMs}]（atMs 单调递增）
update(dtMs)        nowMs_ += dt；过窗口未结算 -> MISS；全结算 -> celebMs_ 结算页 -> 自动重来
render(Canvas&)     noteScreenY() 算每个未结算音符的屏幕 y -> blit 音符 -> 再画琴键/鼓垫（在上层）
tapLane/hitPad      **触摸与 QA auto 走同一条路**：找该轨"离当前时刻最近且未结算"的音符判档
```

## 2. ★★ 血案：整数除法把"每毫秒几像素"算成 0 ⇒ 音符一个都不动

用户反馈原文：**「打鼓和节奏钢琴看不到音符掉落的动画。无法操作。」**

原写法（两款各一份）：

```cpp
const int pxPerMs = (kPianoJudgeY + kPianoNoteH) / music::fallMs(diff_);   // 416 / 1800
const int y = kPianoJudgeY - (notes_[i].atMs - mtAll) * pxPerMs;
```

- 钢琴：`416 / {2600, 1800, 1250}` —— **三档全部 = 0**（每秒只走 0.16~0.33 像素）
- 打鼓：`322 / {2600, 1800, 1250}` —— **同样全 0**

于是每个音符的 `y` **恒等于判定线**（钢琴 388、打鼓 296）。更要命的是：
音符被画在**琴键/鼓垫之下**，而琴键从 y=392 起、鼓垫从 y=302 起 ——
**刚露出的那 4~6px 也被上层盖住** ⇒ 屏幕上"完全没有下落动画"。

而逻辑侧一切正常：音符照样按时刻被自动判 MISS、曲终照样出结算页
（日志实录：`Piano: 打完 完美0 不错0 还行0 漏42 得分0`），
玩家没有视觉提示 ⇒ 主观感受就是"**没法玩**"。

### 修复（v1.30.6）

**先乘后除**，保留亚像素精度；算式只留一份实现（`noteScreenY` / `drumNoteScreenY`，
render 与 QA 共用，避免两处再走偏）：

```cpp
return judgeY - (int)((long long)(atMs - mtAll) * (judgeY + noteH) / fall);
```

`|dt|` 最大约几十秒 ✕ 416 ≈ 1e7，`long long` 足够；`fall <= 0` 时直接返回判定线（防除零）。

### 2.1 覆盖面：**三档速度 × 两款游戏 + 整曲结算**（都在真机 v1.30.6 上跑过）

三档的 `fallMs` 不同 ⇒ 截断量不同，必须逐档验一遍（用 `gdbg diff 1|2|3` +
隔 1s 两次 `gdbg q` 读 `disp` 行的 y）：

| 游戏 | 档位 | 实测（同一次运行内两次采样） | 与公式对照 |
|---|---|---|---|
| 钢琴 | 慢 2600 | `#0 y=414`（mtAll=166） | `388-(0-166)*416/2600 = 414.5` ✔ |
| 钢琴 | 中 1800 | `#1 y=53 → 309`（ΔmtAll 1107ms） | Δy = 1107×416/1800 = **256** ✔ |
| 钢琴 | 快 1250 | `#0 y=84 → 442`（ΔmtAll 1079ms） | Δy = 1079×416/1250 = **359** ✔ |
| 打鼓 | 慢 2600 | `#1 y=101 → 234`（ΔmtAll 1071ms） | Δy = 1071×322/2600 = **133** ✔ |
| 打鼓 | 中 1800 | `#1 y=16 → 212`（ΔmtAll 1091ms） | Δy = 1091×322/1800 = **195** ✔ |
| 打鼓 | 快 1250 | `#1 y=-114 → 175`（ΔmtAll 1124ms） | Δy = 1124×322/1250 = **290** ✔ |

音符间距也随档位成反比变化（钢琴一拍位移：慢 75px / 中 128px / 快 218px），
⇒ "快 = 掉得更快"在视觉上确实成立（打鼓按设计**只改下落速度、不改曲速**，
所以鼓点的 atMs 间距三档一致）。

整曲到结算页（`gdbg auto N`，与触摸同一条判定路）：

- 钢琴 `auto 42` → `P=42 G=0 O=0 M=0 score=6006`，
  日志 `Piano: 打完了 —— 完美 42 不错 0 还行 0 漏 0 最高连击 42 得分 6006` ⇒ 结算页（准确率 100.0%）。
- 打鼓 `auto 42`（节奏型只有 16 个音符）→ 日志 `qa drum auto: 谱面已走完`，
  全程 `Drum: 命中 #0..#15 dt=0ms -> 完美`、`score=1872`、combo 16。

## 3. ★★ 教训（已写进 `RULES-DETAIL.md`）

1. **几何算式必须用真值验一遍**：`a / b * c` 与 `a * c / b` 在整数下**不是一回事**。
   凡是"比例 < 1"的映射（像素/毫秒、像素/毫秒·次），先算比例必然截断成 0。
   判据不是"编译通过"，而是**把算式代入真值算一遍**（本例：416/1800 = 0）。
2. **画面位置被上层盖住时，"有 bug"看起来像"没实现"**：音符确实被 draw 了，
   只是永远停在判定线、还被琴键盖住。⇒ 排查"看不见"先量**像素分布**，别只看代码有没有画。
3. **QA 要暴露"同源的中间量"**：把 `y`（渲染实际用的那个值）打进日志，
   一次 `gdbg q` 就能判"动没动"，比逐帧抓屏比对省一个数量级。
   ★ 但算式**只能有一份**（render 与 QA 共用 `noteScreenY`），否则两处一起走偏更糟。
4. **验收要覆盖"每帧动的画面"**：上一轮验收只查到"进局 + 素材加载正常"就放行了 ——
   素材确实加载了、音符也确实 draw 了，**但没验"位移随时间变化"**。
   ⇒ 这类游戏的最小判据 = **同一局内两次采样（日志 y 或舞台像素）必须不同**。

## 5. 打鼓鼓垫改版（v1.30.7）：**单排 6 垫，各自正对上方那条轨**

**为什么必须改**（量化过程留在这里，因为它解释了"为什么颜色提示不能当映射"）——
鼓垫原按 `padRect(lane) = (pad_x0 + (lane%3)*pad_dx, pad_y0 + (lane/3)*pad_dy)` 排（**读序**：
先填上行三格、再填下行三格），而 6 条掉落轨是**一整条左→右的横扫**（`kDrumLaneW = 80`）——
两套坐标里"第 n 个"的含义不同：

| 音轨 | 音符落点 x | 原应敲鼓垫中心 x | x 偏差 | 该垫所在行 |
|---|---|---|---|---|
| L0 | 40 | 80 | 40 | 上行 y=358 |
| L1 | 120 | 240 | **120** | 上行 |
| L2 | 200 | 400 | **200** | 上行 |
| L3 | 280 | 80 | **200** | 下行 y=476 |
| L4 | 360 | 240 | **120** | 下行 |
| L5 | 440 | 400 | 40 | 下行 |

⇒ **4/6 条轨的 x 偏差 ≥120px（最大 200px = 屏宽 42%）**，且 L3~L5 还要再往下挪一行（180px）。
唯一的对应线索是颜色（音符与鼓垫同用 `DRUM_COL[i]`），而底图那排"轨头色标"画在 y=6..14、
**正好被顶部信息条（y=8..40）盖住** ⇒ 实际看不到。快档音符可见 ~1.0s、鼓点 680ms 一拍
⇒ 玩家每拍都要"查表" —— 这就是"不好操作"的来源。

**改法**（`tools/gen_instr_art.py` 的 DRUM 段 + `src/core/PgDrum.cpp`）：

- 垫子 150×112 → **74×112**，`pad_x0=3, pad_dx=79` ⇒ x = 3 + i×79，中心
  **40/119/198/277/356/435**，对上音轨中心 40/120/200/280/360/440（**偏差 ≤5px**）；
  `pad_dy` 删除（不再有第二行）。74px 仍比"真触摸实测可用"的钢琴键（60px）宽。
- 垫子画法：鼓皮从"按整图拉伸的椭圆"改成**居中的正圆**（直径 = 垫宽 − 14 = 60px）+ 木框 ——
  74×112 上拉伸的椭圆会变成竖长条，既不像鼓也不好认色；色环仍在圆心（身份标识）。
- 命中判定 `padAt()` 简化为**按列判**（列 ↔ 垫同下标，永不会"点 A 判成 B"）+ y 窗口
  （判定线稍上方起、到垫子下方名牌带为止）；**舞台上方的空中区域仍不判**（避免打空中音符的误触）。
- 鼓位名从"垫子内部左下角"移到**垫子正下方居中**（垫内位置被色环占了；名字排在它自己那条轨
  下面本身就是提示）。**仍是 `scale=1`** —— 别改成变量或换档位（会多出一档字形，见
  `RULES-DETAIL.md` §4 的"画布字库"：**字库档位必须是编译期常量**——这是**我们字库方案的约束**，
  不是 GUI 限制（`scale` 在 FlyThings 画布层无上限，2026-09-30 更正）；改完字库必跑
  `games_smoke.py --glyph`）。

## 6. 打鼓「入门」档（v1.30.9）：**只加在打鼓上**

给小孩与第一次玩的人：**下落更慢 + 判定窗口放宽**，其余（谱面、曲速、计分、连击）一律不变。

| 档位 | 下落时长 | 判定窗口（Perfect/Good/OK） | 备注 |
|---|---|---|---|
| **入门** | **3600ms**（音符在屏 ≈2.8s） | **100 / 200 / 300ms** | 新增 |
| 慢 | 2600ms | 60 / 130 / 200ms | 与加档前完全一致 |
| 中（默认） | 1800ms | 60 / 130 / 200ms | 与加档前完全一致 |
| 快 | 1250ms | 60 / 130 / 200ms | 与加档前完全一致 |

★ **为什么不做成"共用内核的第 4 档"**：`music::fallMs()` 是**钢琴与打鼓共用**的表，往里插一档
会让**钢琴也变**（需求只要打鼓）。所以共用内核只提供 "标准窗口"（`music::stdWin()`），
想另开一档的游戏把**自己的表**传进 `judgeOfWin()`：

```cpp
// core/PgMusic.h：共享内核只给"标准窗口"，不替任何游戏做决定
inline Judge judgeOf(dt);                       // 钢琴：标准三档（行为一字未变）
inline Judge judgeOfWin(dt, const Win &w);      // 想放宽的游戏传自己的表
inline const Diff4 &drumDiff(int d);            // 打鼓专用四档 {入门,慢,中,快}
```

`kDiffNames[] = {"入门","慢","中","快"}` 这类**文字留在 `PgDrum.cpp`**，不放共用头 ——
画布字库是按"哪个 .cpp 里出现的字面量"收字形的，放共用头会让档位归属不可控（`PgMusic.h` 顶部有说明）。
默认档 = `DRUM_DIFF_DEFAULT`(=2 中)，**档位不落盘**，所以加档不影响任何历史状态。

**验收（真机 v1.30.9）**：

| 项 | 判据 | 结果 |
|---|---|---|
| 下落确实更慢 | 同一次运行内两次 `gdbg q` 的 `disp` 行 | 入门每拍位移 **61px**（中档是 122px）⇒ 正好一半；代入公式 `296-(atMs-mtAll)×322/3600` 全部吻合 |
| 窗口确实放宽 | `tools/rhythm_tap.py … drum <节点> <迟敲ms>`（先标定 adb 往返再瞄准 +250ms） | 入门：迟 **271ms** 仍判 **还行**（标准窗口 200ms 会直接拒）；中档同样瞄准 +250ms → **空敲**（无命中） |
| 字库完整 | `glyphmiss`（在入门档显示着"入门"两字时跑） | `miss=0 fallback=0（字库完整）` ✔ |
| 文案宽度 | `tools/check_textwidth.py` | 0 处超宽 / 0 处贴边 ✔ |

⚠️ 真机计时的抖动：adb+pginj 的往返实测会漂 ±100ms（同一脚本两次跑能差这么多），
所以"精确偏移"类验收要**先标定再瞄准**，别指望写死的 sleep 值 —— 这条已写进 `tools/rhythm_tap.py`
的用法说明（第 5 个参数 = 故意迟敲的毫秒数）。

## 7. 已知遗留

- 两款游戏的难度窗口（60/130/200ms）是照本板触摸上报抖动定的，没有"低龄放宽"档位。
- ⚠️ 打鼓**起播留白（1500ms）内敲击只出声、不记日志**（`nowMs_ < kLeadInMs` 提前 return）——
  自动化验收敲快了会"看不到任何反应"，**先等 1.6s 再敲**。
- 打鼓垫子下方（y≈450..540）是空白鼓架色：垫子留在判定线正下方是为了"音符直接落进垫子"的
  视觉连续性，没有为了填满而把垫子下移。
