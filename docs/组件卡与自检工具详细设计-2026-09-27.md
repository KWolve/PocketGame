# 组件卡 与 selfcheck/bugreport 详细设计

> **日期**：2026-09-27　**承接**：`MCP优化与组件库提案-2026-09-27.md` 的第 3、4 点展开。
> **设计总则**：① 一切判据落文件（本板 logcat 缓冲只有十几行）；
> ② 一切"能用"的声明必须可证明（pass 带日期/板型，不许口头）；③ AI 与人读同一份数据（YAML/JSON + 渲染视图）。

---

## 1 · 组件卡（Component Card）

### 1.1 要解决的问题（全部实测过）

| 痛点 | 实测案例 | 卡片对应字段 |
|---|---|---|
| AI 不知道包里有什么能力 | `zkhardware` 只写"串口/GPIO/按键"，实际藏着蜂鸣器/背光/ADC/I2C/SPI/PWM 六类 ⇒ AI 想放提示音就去自己折腾 ALSA | `capabilities` |
| 拿到 API 拿不到坑 | `awh264player` description 为空、API 查询全空，头号崩点 `ZKMEDIA_H264_VBVSIZE` 不在签名里，绕了三大轮 | `pitfalls` |
| "能用"无法证明 | 框架播放器 `ZKMediaPlayer` 文档看着完整，在本板静音 | `verified_on` + `acceptance` |
| 找不到可抄的例子 | `libzkmedia.a` 用法只能读参考工程源码 | `examples`（必填） |

### 1.2 卡片 Schema（逐字段规范）

```yaml
id: zkhardware
version: 1.0.0            # 与包版本对齐；卡片本身可独立小版本迭代

capabilities:             # ★ 核心字段：AI 选型的第一入口
  - intent: [提示音, 蜂鸣, beep]        # ← 必须用"用户意图词"！AI 按意图检索，
    api: "HardwareManager::beep() / setBeepPWM()"   #   不是按类名检索
    note: "PWM 驱动，无需音频链路；与 PCM 流不冲突"
  - intent: [亮度, 背光, 熄屏, backlight]
    api: "BrightnessHelper 全套"
    note: "本板无 /sys/class/backlight 节点；亮度变化不出现在 fb 里"

pitfalls:                 # ★ 只收"不写就会错"的，不收风格建议
  - symptom: "调亮度后用截图验证，看不出变化"
    cause: "PWM 调光不改变 fb 像素"
    workaround: "用 setBrightness() 返回值/getBrightness() 回读验收"
  - symptom: "ZKMediaPlayer 播放正常但没声音"
    cause: "AO 自拼声卡设备，喇叭不在默认卡上"
    workaround: "改用官方 zk_audio_player；判据 /proc/<pid>/fd 的 pcmC?D?p"

examples:                 # ★ 必填 ≥1，否则不许上架（抄 Arduino 门槛）
  - project: "参考工程 clock-suite"
    entry: "src/apps/clock/alarm.cc"
    shows: "闹钟响铃走 beep()"

acceptance:               # 见 §2
  script: "selfcheck/zkhardware.sh"
  mode: auto              # auto = 机器可判 | manual-verify = 机器跑+人确认
  requires: ["真机", "蜂鸣器在位"]

dependencies:
  packages: []
  device: ["/lib/eyesee-mpp/*"]        # 设备侧运行时依赖
  exclusive: []                        # 独占资源声明（如"常开 PCM 流"）

verified_on:              # 验证矩阵的"行"
  - {board: V851s, firmware: v1.8x, date: 2026-09-20, result: pass, by: selfcheck}
```

**四条硬规则**：
1. `capabilities.intent` 用意图词（中文+英文别名），不用内部类名——AI 检索的是"我要做什么"；
2. `pitfalls` 数量不限但**每条必须有 workaround**，没有解法的坑不收（那是框架 bug，走缺陷单）；
3. `examples` 必填且 CI 校验路径真实存在（对应 MCP 清单 E3 的"引用存在性检查"）；
4. `result` 只允许 `pass / untested / na`，**untested 绝不许展示为"可用"**。

### 1.3 卡片怎么生产（半自动流水线，~1 小时/组件）

1. **机读部分自动生成**：从头文件解析 API 签名（MCP 清单 J1 建议 ② 的解析器直接复用）→ 填 `api`；
2. **AI 起草**：`intent` 词表、`pitfalls` 初稿（从工程 docs 的 kb-*.md 里挖，都是现成的实测记录）；
3. **人工审 30 分钟**：作者把关 pitfalls 的准确性和 examples 的代表性；
4. **真机回填**：跑 selfcheck → `verified_on` 自动写入（工具回填，不手抄）。

### 1.4 卡片的三种消费形态

- **MCP 工具返回**：`list_packages` 带卡摘要（capabilities 一行式）；`get_package_api` 附卡全文
  （= 拿 API 的同时拿到坑，对应 MCP 清单 J2）；
- **RAG 检索面**：`pitfalls[].symptom` 进索引——排障第一句话就是症状，这是命中率最高的检索面；
- **人读视图**：截图墙 + 卡片网页（真机截图由 selfcheck 跑完自动抓屏入库）。

### 1.5 试点组件（首批 10 个，坑都是现成的）

`zkhardware`（背光/蜂鸣器）、`awh264player`（VBVSIZE 崩点）、`zk_audio_player`（独占互斥/三条音频路径）、
`easyui-listview`（subItem 三条硬事实）、`easyui-seekbar`（setProgress 异步回调）、
`easyui-canvas`（scale 常量/448px）、`ime-inputmethod`（三层上限成对改）、`touch-inject`（MT-B 三铁律）、
`screensaver-policy`（30s 抢前台/timer 停）、`upgrade-pack`（superblock 纪律/md5 不可用）。
——这 10 张卡的素材全部在我们工程 docs/ 里，**制作成本主要是搬运和审校，不是重新发现**。

## 2 · selfcheck（组件验收脚本）

### 2.1 设计目标

把"这个组件在硬件上验证过"从**承诺**变成**可执行证明**。AI 集成组件后跑一遍，
得到 `pass/fail + 证据文件`，即证明"接对了"——这是"拿来就能用"的判定标准。

### 2.2 脚本结构（固定五段，全部可机读）

```
setup    → 环境准备（如 echo 'haapp' > /tmp/pg_autostart 进应用、唤醒屏保）
probe    → 硬件在不在？(读设备节点/回读 API)   不在 → result: na，不是 fail
exercise → 执行一遍能力（beep 500ms / 设亮度 30→80 / 起播 3 秒）
assert   → 读回判据（API 回读 / QA dump / 抓屏像素 / 心跳文件）
report   → JSON 落盘 /tmp/selfcheck_<组件>_<ts>.json + 人读摘要一行
```

**五条实现铁律**（全部来自实测教训）：
1. **判据落文件**，不靠 logcat（缓冲十几行，"定时器还在不在"看不出来）；
2. **`na` ≠ `fail`**：硬件不在位/平台不支持 → na 并说明原因，防止误判"组件坏了"；
3. **assert 用"只有新代码才有的判据"**：验版本别用 md5（squashfs 带 mtime，同参数两次差 32 万字节）；
4. **exercise 前先唤醒屏保**（30s 抢前台、屏保中 timer 停）；
5. `manual-verify` 模式显式声明（如蜂鸣器声音没有机器可读回执 → 脚本跑完提示"请人耳确认 Y/N"，
   结果里如实标 `manual`），**不许静默把"没验"当"过了"**。

### 2.3 输出格式（AI 消费协议）

```json
{
  "component": "zkhardware",
  "result": "pass",
  "checks": [
    {"name": "beep",        "result": "pass", "evidence": "/tmp/sc_beep.json"},
    {"name": "backlight",   "result": "pass", "evidence": "setBrightness(80) 回读=80"},
    {"name": "adc",         "result": "na",   "reason": "本板未引出 ADC 采样点"}
  ],
  "board": "V851s", "firmware": "v1.84", "date": "2026-09-27"
}
```

### 2.4 与现有工程的衔接

- selfcheck 内部走**应用内 QA 通道**（`/tmp/pg_*cmd`，免触摸、可脚本化）——基建我们已建好；
- `flythings_validate_project` 加一步：检测 Manifest 声明的包 → 有 selfcheck 的提示"集成后运行"（提案 T4）；
- 运行结果**自动回填**组件卡 `verified_on` 与验证矩阵（见 2.5）。

### 2.5 验证矩阵

```yaml
# matrix.yaml —— 组件 × 板型，一格 = 一次 selfcheck
zkhardware:    {V851s: pass@2026-09-20,  Z20: untested, T113: na}
awh264player:  {V851s: pass@2026-09-14,  Z20: untested}
```

- 回填纪律：**跑 selfcheck 即自动回填**（工具写，不手抄，杜绝"文档说 pass 实际没人跑过"）；
- 矩阵即卖点：对客户展示"这个组件在你要的板子上 X 月验证过"；对内部是回归防线的雏形。

## 3 · flythings_selfcheck（设备快照工具）

### 3.1 设计目标

**排障第一步从"猜"变成"读"**。现在每个案子开局都要重新摸 `/proc`、`getprop`、mounts、
event 节点——这些动作完全同质化，应该一条命令出全量快照。树莓派 `vcgencmd`/`pinctrl`/`raspi-config`
证明了这类工具的文化价值。

### 3.2 快照内容（九个分区，每项带健康判据）

| 分区 | 采集内容（全部只读） | 健康判据示例 |
|---|---|---|
| identity | 板型/序列号/固件版本/`/proc/uptime` | uptime<60s → hint:"刚重启，/tmp 已清" |
| display | 分辨率/图层/当前背光值 | — |
| input | event 节点清单 + 能力位摘要（MT-A/B） | 探测到 MT-B → hint:"注入必须用 pginj proto=b" |
| audio | 声卡清单/当前占用（pcmC?D?p）/SPK Switch | PCM 被占用 → hint:"zk_audio_player 独占" |
| storage | mounts（**/res 是否挂上**）/剩余空间/`/data` 用量 | /res 无 mtd 条目 → **ok:false**（superblock 血案判据） |
| network | 接口 running/关联/IP/wpa 状态 | 无 running → hint:"wpa REASSOCIATE" |
| service | zkswe 进程栈/QA 通道文件在否 | pg_autostart 缺失 → hint:"先 echo '<app>' 进应用" |
| runtime | 前台应用/屏保状态/心跳文件 | 屏保激活 → hint:"先唤醒再验收" |
| snapshots | 上次快照路径（自动 diff） | — |

### 3.3 两个关键设计

1. **返回 JSON，每项 `{key, value, ok, hint}`**——AI 只读 `ok:false` 和 `hint`，不用理解全部字段；
   hint 就是"下一步动作"，直接接进排障循环；
2. **快照可 diff**：固化前跑一次、固化后跑一次，工具自动标差异——"升级到底改变了什么"
   从人肉比对变成一条命令（对应固化的"固化完成≠结束"纪律）。

### 3.4 板型扩展

每个板型一个 profile（对应 `flythings_hardware_info` 的数据源）：声明本板有哪些节点、
哪些判据适用。新板接入 = 写一个 profile，selfcheck 逻辑全复用。

## 4 · flythings_bugreport（缺陷报告生成器）

### 4.1 设计目标

封闭框架的"最后一公里"：**源码在框架组手里，缺陷报告质量决定修复速度**。
现在我们口头描述 + 截图；AI 应该能把现场完整打包成"框架组拿单不需要追问"的单子。

### 4.2 流程（五步）

```
① 触发    用户说"报个缺陷 / 给框架组提单"
② 收集    selfcheck 快照 ×2（问题前后或与好设备对比）
          + logd 尾部（带绝对时钟时间线）
          + QA dump / 心跳文件 / 判据文件
          + 复现步骤（免触摸：QA 命令序列，框架组可原样重放）
          + 相关知识文档引用（"这与已入库的 XX 坑不同，因为…"）
③ 归因初判  AI 给出建议归因层：框架 bug / BSP / 应用侧误用（附依据）
④ 脱敏    序列号/IP 可选遮蔽（发外部分支时）
⑤ 打包    markdown 缺陷单 + 证据文件 zip
```

### 4.3 缺陷单固定模板（质量标准：**零追问**）

```markdown
## 标题：固化完成后 ~3 分钟设备自重启，mtd3 squashfs superblock 丢失
## 严重度：S1（量产风险级，/res 挂载失败，应用不可用）
## 环境：V851s / 固件 v1.84 / selfcheck 快照见附件（storage 分区 ok:false）
## 最小复现：① tools/upgrade_device.sh <ver> ② 等待报"完成" ③ 3 分钟后观察
## 期望 vs 实际：/res 保持挂载 | 实际 /proc/mounts 无 mtd 条目
## 判据：/proc/uptime < 30s 且 cat /proc/mounts 无 mtd（命令原样可重放）
## 时间线：14:02:11 报完成 → 14:05:23 重启 → 14:05:41 /res 缺失
## 初判归因：框架升级流程（写后未稳定落盘？）——应用侧已排除（理由：…）
## 附件：selfcheck_x2.json / logd_tail.txt / timeline.txt
```

### 4.4 三条质量铁律（全部是我们踩过的验收血案）

1. **必须对照"已知会失败的场景"**——报告里的判据要先证明"它在能区分对错的场景下真的会报错"
   （否则验收脚本自己会骗你：窗口太小、还原假通过）；
2. **时间线用绝对时钟**——"过了很久"不是证据，秒级时间戳才是；
3. **判据命令原样可重放**——框架组拿到单子复制粘贴就能复现，这是"零追问"的底线。

## 5 · selfcheck 与 bugreport 的配合

```
日常开发：selfcheck（单组件验收）→ 回填组件卡/矩阵
排障：    flythings_selfcheck（整机快照）→ hint 驱动排障 → 修不好 →
          flythings_bugreport（快照 diff + 时间线 + 可重放判据 → 框架组）
```

三件套形成闭环：**组件资产越滚越厚（矩阵）→ 排障越来越快（快照/hint）→ 剩下修不了的有高质量单子直达框架组**。
这就是"知识库足够完整，开源与不开源没差别"的工程化落地形态。
