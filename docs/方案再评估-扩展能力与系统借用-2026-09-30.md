## 〇、结论摘要（先纠正我上轮的一个定性错误）

我上轮把 FlyThings 归到"**闭源厂商套件**"这一格，据此得出"十行里九行开源栈占优"。**这个归类不准确**，
你的架构实际是第四类：**「Linux 底座 + 自研 2D GUI + 开放扩展点 + 硬件标准化层」= 可扩展的垂直整合**。

| 结论 | 内容 |
|---|---|
| ① 系统借用 | **成立且空间很大**。约束不是"能不能"，而是三条硬边界：musl/glibc 分叉、无包管理、只读 rootfs + 极小 tmpfs/`/data` |
| ② 做得更好 | **能力上已经具备，卡在"可发现性"和"可证性"**：扩展点散在 4 篇文档里没有总表、画布作画手册缺失、没有性能采集工具 ⇒ AI 不知道能扩展，也不知道扩展后快不快 |
| ③ MCP 优化 | 五件事：**扩展点总表 + 画布手册 + 效果路径规划 op + 性能采集 op + 渲染类 demos**。做完"差异化效果"这一行会从"落后"翻成"领先" |

**一句最关键的话**：你真正的护城河不是 GUI，是**硬件标准化层 + 验证装置**——
它恰好命中"国产 SoC 资料不全 + LLM 语料里没有板级真相"这个长期结构性缺口。
GUI 是交付载体，扩展点是差异化能力的出口，**三者的优先级应该是：硬件层 > 扩展点 > GUI 本身**。

## 一、你的六条架构主张，逐条评估成立度

| # | 主张 | 成立度 | 我的评估（含反证/条件） |
|---|---|---|---|
| 1 | **Linux 底座** | ✅ **完全成立** | 一切 userspace 库/协议/工具可用；dlopen、多进程、sysfs/procfs/dev 全开。**这是"借开源"的物理基础** |
| 2 | **自研 GUI 做 2D 图形加速基础组件库** | ✅ **成立（2026-09-30 二次更正，比我原判断好）** | 我原先写的"UI 层是 CPU 软渲染 / 加速仅图层通路"**又是归属错误**：那是**我们自己写的 canvas 实现**（`src/core/PgCanvas.*`）的代价，不是平台上限。平台实际提供：**内存拷贝(bitblt) + 透明 α 混合 + 90° 旋转**，且**内存画布→屏幕这一步走硬件加速**（我方代码实证：`src/platform/PgDisplay.h`「`ZKTextView::setBackgroundBmp()` 挂画布 → `setInvalid()` 触发刷新（**控件->屏幕走硬件加速**）」；`misc::bitmap_rotate` = 90° 整数倍）。⇒ "2D 图形加速"的说法**站得住**；真正做不到的是**任意角度旋转位图**（需自己逐帧算，如 `components/vinyl`） |
| 3 | **GameView/canvas 扩展 GUI 能力** | ✅ **成立，且比上轮评估的更高** | **2026-09-30 更正**：上轮引用的「`scale` 不能是变量、画布宽 ≤448px」**是误记，已作废**——`scale` 那条来自**自研字库只预烘有限档**（档位需编译期常量；**GUI 层对 scale 无限制**），`448` 是某 UI 的**内容区宽**（480−2×16）。⇒ 真正的画布限制只剩「绝对时钟」+「画布盖满面板」两条 |
| 4 | **自定义控件实现差异化效果** | ✅ **成立，但目前是"人肉能力"** | `devflow/custom-widget.md`（187 行，BaseView 两条实现路线 + Attr 适配器 + bitmap_t/Region + MessageQueueThread + 8 个可抄控件）质量很高，**但只此一篇、状态 `review` 且 `needs_evidence: true`**，且没有"我能扩展什么"的总表。⇒ **能力存在，AI 发现不了** |
| 5 | **标准化硬件 API 与图层，减少芯片差异 / 国产 SoC 资料不全** | ✅✅ **最强的一条，是真护城河** | 与我的独立结论一致：**板级真相不在任何模型的语料里**，LLM 会编 GPIO 引脚和 ADC 通道。谁把"每颗 SoC 的私有差异"吸收在一个稳定接口后面，谁就免掉了 AI 最贵的那类错误 |
| 6 | **标准化硬件模组，降低研发与量产难度** | ✅ **成立，且是开源栈给不了的价值** | 开源栈强在"知识免费"，弱在"物料与量产"。模组标准化属于供应链能力，LVGL/ESP-IDF 生态不具备同等的整机交付确定性 |

## 二、修正后的三方对比（把维度换成"能不能借 / 能不能扩 / 能不能证"）

| 维度 | FlyThings（修正后定性） | ESP32-P4 + LVGL | Linux + LVGL/Qt |
|---|---|---|---|
| **系统能力借用度** | **高**（Linux userspace 全开；受 libc/存储约束） | 低（RTOS，只能用它自己的组件生态） | **最高** |
| **扩展点开放度** | **中高**（自定义控件 + canvas + 图层 + 系统窗口；**但缺总表与示例**） | 中（LVGL 有 widget/draw unit 扩展，需自己接） | 中（上层自由，但底层要自己收口） |
| **硬件差异吸收度** | ★★★ **最高**（这正是它的设计目标） | 中（模组级统一，芯片级要自己处理） | 低（板卡组合发散，差异自负） |
| **AI 零样本可开发性** | 低→**中**（自建知识库在补，且 MCP 已能机读消费） | **最高**（语料海量） | 高 |
| **性能上限** | **中**（绘制进 canvas 的成本取决于我们的实现/面积；**canvas→屏幕是硬件合成**：bitblt/α/90° 旋转） | 中高（PPA 混合/缩放/旋转） | 高（GPU/VPU） |
| **性能可证性** | **低**（无帧耗时/掉帧采集工具） | 中（有 idf 侧 profiling） | 高 |
| **上游跟随 / 可修性** | 差（闭源、单厂商节奏） | 好 | 好 |
| **量产与物料确定性** | ★★★ **最高**（模组标准化 + 升级链路 + 量产验证） | 中 | 低（板卡组合自负） |

**读法变了**：上轮我说"九行开源占优"；修正后是 **"借/扩/证"三项里我们两项占优、一项（性能）落后、
"上游跟随"落后**。而"性能"与"跟随"都不是文档能补的——**别在文档上跟它们比，要在"可借用 + 可扩展 + 可证明"上比**。

> ★ 反过来说：**"个性化效果"这一行现在从"落后"变成"取决于可发现性"**——
> 因为开源栈里做差异化效果要自己写整套控件体系，而你已经有扩展面了。**只要把它做成 AI 可用的，这条就翻盘。**

## 三、"可以做到更好"的三个成立条件（缺一不可）

### C1 · 把"引擎限制"与"工程侧约束"分开写（**2026-09-30 因更正而缩水**）

> **更正**：C1 原来的两条依据（`scale` 不能是变量、画布宽 ≤448px）**都是误记**——
> 前者是**自研字库的档位约束**（**GUI 层 scale 无限制**），后者是**某 UI 的内容区宽**。
> ⇒ C1 不再是"解天花板"，而是"**把两类约束分清、各自写清**"：

- **引擎/画布层**：只写两条真限制（绝对时钟、画布盖满面板），**不要臆造上限**；
- **工程侧（我们的字库/素材方案）**：档位制、拉伸禁令、字库重跑链——**必须标明"这是本工程的约束"**，
  否则会被当成框架限制向上反馈（**本轮的 448/scale 就是这么错上去的**）；
- **落点**：在本文与 `extension-surface.md` 的限制条目上各加一列"**这条属于谁**（引擎 / 我们的工具链 / 本 UI 布局）"；
- 判据：新写的限制条目**必须能答出"谁定的"**；答不出就不写进去。

### C2 · 搞清"硬件加速到底覆盖哪一段"（**已因二次更正而缩小**）

> **更正**：C2 原来假设"只有图层能硬件加速、canvas 上屏幕是软拷贝"——**错的**。
> 平台在**内存拷贝 / α 混合 / 90° 旋转**上是提供能力的，**canvas→屏幕这一段就是硬件合成**。

- 所以 C2 不再是"求一个加速接入口"，而是**把已知能力用到位**：
  ① 先把"**哪些合成动作已有现成 API**"摸清（bitblt / α 混合 / 90° 旋转 / `setBackgroundBmp` 上屏），
  避免在应用里重复实现框架已经能做的事；
  ② 确实缺的只有"**任意角度旋转位图**"（`misc::bitmap_rotate` 只支持 90° 整数倍）⇒
  这类才需要自己逐帧算（先例 `components/vinyl` 已给 6~12ms/帧的实测）；
  ③ **外部渲染器占用图层**仍值得要，但它与"canvas 上屏已硬件加速"是两回事，不再当成主要瓶颈。
- 判据：同一个效果用"平台合成 API"与"自写软合成"各做一次，**量帧耗时差**（预期 API 快一个量级）。

### C3 · 让"更快"可测量
- 现状：**没有帧耗时/掉帧/内存峰值采集工具**。所以我们所有性能结论都靠"手感"——
  `perf` 类问题无法形成判据，AI 也无法自证"我优化有效"。
- 要做：`flythings_perf_probe`（见 §4-D）。
- 判据：任何"优化"提交都附**前后帧耗时对比**。

## 四、MCP 优化清单（让 AI 真正能扩展能力）

> 原则：**能力已经存在，问题在"可发现 / 可规划 / 可证明"**。所以下面的动作全是"把已有能力做成 AI 可消费的形态"，
> 不需要先改框架。

### A · ★★★ 新增「扩展点总表」`knowledge/uicontrols/extension-surface.md`

**为什么**：现在扩展能力散在 4 篇里（`custom-widget` / `custom-view-refresh` / `canvas-panel-coverage` /
`custom-render-paths`），AI 没有任何一处能回答"**我到底能扩展什么**"。这正是它去拿别的 GUI 框架类推的诱因
（`capability-boundaries.md` 已明令禁止类推，但**只禁止不给替代 = AI 只能放弃**）。

**内容模型（机读友好，一张表一个扩展点）**：

| 字段 | 含义 |
|---|---|
| `extension` | 扩展点名称（自定义控件 / canvas / disp 图层 / 系统窗口 / 全局弹框 / 独立进程渲染） |
| `can` / `cannot` | 能做什么 / **明确不能做什么**（AI 最需要后者） |
| `lifecycle` | 初始化/刷新/销毁口径（如自定义 view 必须整屏刷新） |
| `perfTier` | 实测档位（面积上限、帧率量级） |
| `minExample` | 最小示例（指向 `demos/render-*` 或工程内相对路径） |
| `evidence` | 判据（可执行命令） |
| `platforms` | 支持平台 |
| `seeAlso` | 串联其余 4 篇 |

**配套**：新 op `flythings_list_extensions`（或并入 `get_project_spec`），返回上表——
让 AI **不问也能拿到**，问也能拿到。

### B · ★★★ 新增 `knowledge/devflow/canvas-authoring.md`（画布作画手册）——**最大的知识缺口**

- 实测缺口：`绝对时钟` 在全库只命中 **1 篇**（就是我上轮写的那篇）、`448` 只命中 4 篇 ⇒
  **我们工程 8 款画布游戏 + 4 款节奏游戏的实操积累（软渲染循环、脏矩形、坐标/缩放纪律、
  帧预算、与框架重绘的关系）基本没入库**。这是"AI 扩展 canvas"最厚的一份素材，白放着。
- 骨架建议：
  ```
  0. 一句话 + 何时该用 canvas（vs 预烘帧 vs 图层）
  1. 渲染循环：绝对时钟 / 帧预算 / 掉帧降级策略
  2. 刷新口径：整屏 vs 脏矩形（★ 关联 custom-view-refresh 的实测结论）
  3. 坐标系与缩放纪律（scale 常量、画布宽 ≤448 的替代写法）
  4. 资源策略：预烘 vs 运行时绘制 的分界线（面积/帧率判据）
  5. 与框架共存：浮层/窗口/触摸的边界（哪些必须交给框架）
  6. 性能实测表（各面积 × 各写法的帧耗时）★ 需 C3 工具产出
  7. 反例（AI 常写错）：静态变量当画面时钟、每帧 new、局部 invalidate 只刷一块…
  ```

### C · ★★ 新增 op `flythings_plan_effect`（效果需求 → 推荐路径）

- 输入：效果描述 / 面积占比 / 是否逐帧 / 是否含视频 / 平台。
- 输出：**推荐路径（五条路之一）+ 判据 + 最小示例 + 该路径的已知限制 + 备选路径**。
- 价值：把我上轮的"五条路文档"升级成**可调用决策**——文档给人读，决策树要给 AI 调用。
- 落点：可以先用知识文档 + `map_control` 式的映射表做最小版，验证后再工具化。

### D · ★★ 新增 op `flythings_perf_probe`（性能可证）

- 采集：帧耗时分布（p50/p95/max）、掉帧计数、内存峰值、页面切换耗时；**判据落文件**。
- 与既有互补：`test_run` 管"画面对不对"，`perf_probe` 管"**跑得快不快**"。
- 约束：沿用本板纪律（判据落文件、不靠 logcat 全文匹配、别用 `diff==0`）。

### E · ★★ 补 `demos/render-*`（示例即文档）

- 现状：`demos/` 6 个**全是网络类**，渲染类 **0 个**。
- 建议五个最小工程，与五条路一一对应：`render-custom-widget` / `render-canvas-60fps` /
  `render-offscreen-blit` / `render-disp-layer` / `render-external-process`。
  每个含：可跑 UI + 判据命令 + 实测帧率/内存（**未验的要如实标 `untested`**）。

### F · ★ 把"三问"放到动作发生处

在 `html_to_json` / `ui_preview` / `map_control` 的 docstring 与 `extension-surface.md` 顶部写同一句：

> 做"差异化效果"前先答三问：**① 静态还是逐帧 ② 面积多大 ③ 有没有硬件层可用**——
> 答案决定走 canvas / 预烘帧 / 图层哪条路。**不确定就先调 `flythings_plan_effect`。**

### G · 门禁与体检接上

- `extension-surface.md` / `canvas-authoring.md` 入库即挂 **front-matter + ≥5 条检索问法**（沿用 v0.27.125 门禁）；
- `kb_health` 的 backlog（报 82 篇待补判据）**优先清"扩展点/渲染"这一组**——因为它们直接决定 AI 能不能扩展；
- 用 `no_hit` 日志验证：等"自定义/画布/效果/加速"类问法**零未命中**，说明扩展能力真的可发现了。

## 五、怎么知道"AI 能扩展了"（度量，别靠感觉）

| 指标 | 现状 | 目标 |
|---|---|---|
| 差异化效果需求中，AI **先说路径再动手**的比例 | 未知（无观测） | >90% |

| "自定义/画布/效果"类问法的 **no_hit 数** | 未统计 | 0 |
