> 需求（用户 2026-09-15）：*"游戏里面再帮我加一个消消乐。UI 效果要参考《开心消消乐》。
> 继续基于 FlyThings 这套代码来添加。"*

## 2. 玩法与数值

| 项 | 值 | 说明 |
|---|---|---|
| 棋盘 | 8x8，格 56px | 画布 480x540，棋盘 (16,46)-(464,494) 居中 |
| 糖果 | 7 种 | **颜色 + 形状双重区分**（圆/方/星/六角/钻石/心/条纹） |
| 操作 | 滑动 **或** 点两下 | 只允许相邻交换（对角不算）；再点同一格 = 取消选中 |
| 消除 | 3+ 同色横竖连线 | 交叉处一起消 |
| **特殊块** | **4 连 → 方向炸弹；5 连 → 彩虹球** | 见 §2.1（v1.23.0 新增） |
| 计分 | `颗数 × 10 × 连锁倍数` + 长连加成 | 长连 ≥4 每多一颗 +20；连锁 = 同一次操作内的第 n 波（1,2,3…） |
| 步数 | 每关 25 步 | **无效交换不扣步数**（滑回去，不扣不移位） |
| 过关 | 本关分 ≥ 目标 | 目标 = 600 + (关卡-1)×450（第 1 关 600，第 2 关 1050…） |
| 失败 | 步数用尽且未达标 | 点屏幕重试本关（分数不清零的是**总分**，本关分归零重来） |
| 死局 | 无可行交换 → **自动重排** | 保留场上糖果只挪位置，重排到"无匹配且有解"；**特殊块参与的交换永远算有解** |

### 2.1 特殊块（v1.23.0）

对齐参考产品的"连得越长奖励越大"：

| 生成 | 外观 | 效果 |
|---|---|---|
| 横向 4 连 | 横向白色箭头（叠在该糖果上，**保留糖果色**） | 被消除时**清掉整行** |
| 纵向 4 连 | 纵向白色箭头 | 被消除时**清掉整列** |
| 5 连及以上 | **彩虹球**（6 色扇区圆球，**无色**） | 与它交换 ⇒ **清掉对方那颗糖的全部同色**；被炸到 ⇒ 清掉场上最多的那种颜色 |
| 两个特殊块互换 | —— | **直接引爆**（玩家刻意组合，不要求形成连线） |

三条实现要点（都踩过坑，见 §7）：

1. **表示法是正交的**：`cell_` 仍是糖果颜色，另开一个 `power_` 数组记"它是不是特殊块"。
   不采用"特殊块 = 几个新种类值"：那样匹配/下落/洗牌/彩虹球判色全要额外特判。
2. **效果展开必须能级联**：炸弹清一行后，那一行里可能还有炸弹/彩虹球 ⇒ 要一层 `while`
   反复展开到不再增长（`trig_` 防互指死循环）。实测一次"落定后落进炸弹"就顺势炸了整行。
3. **特殊块会跟随下落**：`startFall()` 要把 `power_` 和 `cell_` **一起**搬运（炸弹该往下掉）。

设计取舍：参考产品是"关卡 + 目标 + 有限步数"，我们照这个骨架做，但**不做**充值/道具/
体力/社交（见 §5 能力对照）。

## 3. UI 结构与素材

视觉语言直接对齐参考产品：**清新花园底 + 木质棋盘框 + 浅色糖果凹槽 + 高饱和糖果 + 顶栏木牌**。

```
画布 480x540（ui/main.html 的 GameCanvas）
├─ bg.png      整屏静态：花园渐变 + 光斑 + 木框 + 8x8 浅色凹槽
├─ candy0..6   56x56（**含凹槽底的不透明整图**，见 §7 坑 1）
├─ sel.png     选中高亮框（金色圆角 + 四角加粗）
├─ burst.png   消除爆花（112x112，锚点=中心，整体 alpha 淡出）
├─ rainbow.png 彩虹球（56x56，**也含凹槽底** ⇒ 同样走 memcpy）
├─ mark_h/v.png 炸弹方向标记（56x56，**只有箭头不透明**，叠在糖果上）
└─ 代码绘制：交换滑动 / 下落位移 / 消除淡出 / 分数弹出 / 顶栏进度条 / 覆盖层
```

**素材数量的取舍**（v1.23.0 加特殊块时定的）：
- 方向标记只烘 **2 张**（横/竖），**不是** 7 色 × 2 = 14 张 —— 标记是中性色的，叠在糖果上即可。
- 标记原本是"代码画图元"（圆角条 + 4 个三角），实测带特殊块时帧率掉到 52fps：
  每格 6 次图元调用是**逐像素填充**；改成贴图后大部分像素 `alpha=0` 被直接跳过 ⇒ 几乎免费
  （render 4.6ms → 5.06ms → 优化后同口径对照见 §6 第 19 行）。
  → 结论：**反复绘制的固定图形一律出图**，哪怕只有几笔。

顶栏（画布内 y=4..40）：[第 N 关]  [本关分/目标 进度条]  [步 N]
HUD（原生控件，画布上方）：得分（总分 = 最高分存档）/ 最高分 / 关卡 / 步数
```

生成与素材纪律（与 `docs/game-art-pipeline.md` 一致）：

- **静态 → PNG，动态 → 代码**。底图一张顶掉 64 次凹槽绘制；糖果/选中/爆花单独贴（位置每帧在变）。
- **1:1，不缩放**。糖果图 56x56 == 格尺寸，锚点 (0,0) 直接对齐格。
- 素材自检：`check()` 拦"空图/内容贴边"；糖果是**故意铺满整张图**的，走 `opaque_full=True` 只查"有内容"。
- 预览拼图：`docs/shot_game_art_match3.png`（每次生成自动出）。

## 4. QA 命令表（免触摸验收）

主界面 QA 通道 `/tmp/pg_autostart`（内容**变化才执行**，所以每条加 `#序号` 注释）。

| 命令 | 作用 |
|---|---|
| `22 1` | 进入消消乐（slot 22）并置 RUNNING；`22 0` 进 READY |
| `-1` | 返回主列表 |
| `tap X Y` | 喂画布触摸（X,Y 是**画布坐标**）；用于 READY→RUNNING、点覆盖层继续 |
| `gscore` | 分数/状态总览（宿主提供） |
| `fps` / `bench` / `spr` / `glyphmiss` | 帧率 / 每帧耗时拆解 / 贴图缓存 / 缺字统计（宿主提供） |
| `gdbg board` | 打印 8x8 棋盘（每格一个数字，`-` = 空） |
| `gdbg state` | 打印 关卡/步数/本关分/总分/阶段/连锁/状态 |
| `gdbg swap r1 c1 r2 c2` | 走**与触摸完全相同**的交换路径（三消验收主力） |
| `gdbg shuffle` | 强制重排（验"无解重排"分支与合法性） |
| `gdbg moves n` | 设剩余步数（**验收钩子**：验"步数用尽"分支，不打 25 步） |
| `gdbg goal n` | 设本关目标分（**验收钩子**：验过关分支） |
| `gdbg level n` | 跳关（重置棋盘/步数/状态，**不改分数**） |

辅助脚本 `tools/match3_qa.py`：

```bash
# ① 从真机棋盘算出"下一步该点哪"（8x8 盲点几乎必然无效交换，必须算）
adb shell "echo 'gdbg board #n' > /tmp/pg_autostart"
adb logcat -d | grep 'Match3: board' | tail -8 | python tools/match3_qa.py --cmds

# ② 抓屏逐像素判画面（不是"肉眼看着像"）
python tools/match3_qa.py --pix docs/shot_match3_play.png

## 7. ★★ 踩过的坑（都是"看着没问题、量了才现形"）

### 坑 1：透明糖果图 → 帧率只有一半（33fps）

第一版糖果图是**透明背景 + 只烘糖果本体**，贴到凹槽上 —— 视觉正确，但真机
`bench` 给出 **render = 17698us/帧、fps 33**（对比打地鼠 71fps）。

根因：`Canvas` 的贴图快路径要求 **整图不透明**（`Sprite::opaque`，见 `core/PgSprite.cpp`）。
带透明像素的图走**逐像素 alpha 混合**，64 格 × 56×56 = **20 万像素/帧**全在慢路径上。

正解：**把凹槽底一起烘进糖果图**（`bake_candy` 里先 `_draw_slot` 再叠糖果），
每格变成一次 memcpy。→ render **17.7ms → 4.6ms**，fps **33 → 58**。
代价只是每张多几 KB 凹槽像素（7 张 × 12KB）。

### 坑 2：`ImageDraw` 的半透明 `fill` 直接写 alpha ⇒ memcpy 快路径静默失效

> ⚠️ 本条**合并并修正**了初版文档里"LANCZOS 会给不透明图留伪影"的**误判** ——
> 那个结论是错的，真正的根因在本条末尾的对照实验里。

改完坑 1 后帧率仍只有 33fps。原因是底图里那些"柔和的半透明叠加"：光斑
`d.ellipse(fill=rgba(色, 40))`、藤蔓弧线 `rgba(色, 90)`、棋盘投影、木纹线 ——
**`ImageDraw` 的 fill 是直接覆写像素**（PIL 的 draw **不做** alpha 合成），
所以图上真的留下了 alpha=40/90 的像素（实测一块半透明椭圆缩回后 = **112240** 个），
`Sprite::opaque` 判定失败 ⇒ 整屏底图每帧退回逐像素混合（那是 25 万像素的慢路径）。

**★ 对照实验（别误判成重采样的锅）**：同尺寸 RGBA 图各画一次再 `resize(LANCZOS)`：

| 画法 | 缩回后 `alpha<255` 的像素 |
|---|---|
| 全部用**不透明** fill | **0** |
| 其中一块用 `rgba(色, 40)` | **112240** |

⇒ `resize(LANCZOS)` 对 alpha 通道的卷积**不会**凭空造出半透明。
（这条实验值得记下来：否则下一个人会照着"伪影"去怀疑重采样，白绕一圈。）

**正解（两道一起做）**：

1. **主修法**：把 `rgba(色, alpha)` 改写成 `rgba(lerp(底色, 叠加色, alpha))` ——
   在不透明底上视觉等价（`lerp` 的 t 与 alpha 同为 0..256 语义），且天然不透明。
2. **兜底 + 告警**：`force_opaque()` 强制 alpha=255，并在强制**之前**数一遍
   `alpha<255` 的像素、有就告警。为什么必须告警：抹平 alpha 会把"半透明叠加"
   变成**实心色块** —— 那是个**视觉 bug**（内阴影会重得离谱），比性能问题更难查；
   告警把它从"静默的视觉错"变成"生成期就能发现的问题"。

判据：生成器输出里每条素材都过这道（`alpha<255 = 0`；`sel/burst/candy` 这类
**故意带透明**的元素图例外，它们不进 `force_opaque`）。

**顺带核实**：whack / snake / flappy 三张整屏底图**本来就是全不透明**（0 个）——
因为它们全程用不透明色绘制，所以它们的 71 / 99fps 没有这个隐患，**无需改动**。

### 坑 3：`gdbg level n` 跳关后游戏卡在 OVER

跳过"上一局刚结束"的场景时，`state_` 仍是 `GSTATE_OVER` ⇒ 新的棋盘摆好了但**整局已结束**，
后续 `gdbg swap` 被 `trySwap()` 的 `isPlaying()` **静默拦截**（日志里只有 "QA swap" 一行，
moves/分数都不动，极像"交换功能坏了"）。
⇒ QA 钩子改状态时**必须把状态机一起复位**（现已置 RUNNING 并打日志）。

### 坑 4（v1.23.0）：主动交换的彩虹球会被"再触发一次"

**症状**：`power 7 1 R` + `swap 7 1 7 2` 之后日志是**两条**清除记录 ——
`清掉颜色 4 的 7 颗` **加上** `彩虹球 (5,6) 被波及 → 清色 5（+14）`，
一次交换清了两种颜色（比参考产品强一倍）。

**根因**：彩虹球在"主动交换"路径里被 `buildRainbowClear()` 放进了被消除集合，
而它自己也在这个集合里 ⇒ `expandSpecials()` 又按"**被波及**的彩虹球"分支再展开一次。

**修法**：进清除流程前把这一格的 `power_` 摘掉（`power_[rr][rc] = PW_NONE;`）——
主动交换时它的效果**已经**由 `buildRainbowClear` 用掉了，不能再算第二次。

**教训**：当一个"物件"的效果既能被主动触发、又能被被动触发时，
**要把两个入口分清**；合成一个 `expandSpecials` 就必然出现"自己触发自己"。
（判据：这类 bug **只能靠日志条数**发现 —— 抓屏看画面只是"消得更多"，不会觉得异常。）

### 坑 5（v1.23.0）：方向标记用"代码画图元"会掉帧

标记最初是代码画的（2 次圆角矩 + 4 个三角 = 每格 6 次图元调用），
带 2 个炸弹时实测 **fps 52 / render 5.1ms**；改成"贴一张只有箭头不透明的 56x56 小图"后
同口径 render 回到 5.06ms、fps 57+。
原因：图元是**逐像素填充**，而贴图的大部分像素 `alpha=0` 会被 `drawSpriteA` 直接跳过。
⇒ **反复绘制的固定图形一律出图**，哪怕只有几笔（但**别按糖果色铺 14 张** —— 中性色标记叠上去即可）。

### 坑 6（v1.22.0）：画布文字会被覆盖层压暗，判据要反推遮罩

抓屏判画面的脚本第一版在"失败覆盖层"上误报（所有糖果色被判成红/绿）——
因为整屏半透明黑遮罩把采样色压暗了 66%。修法：用顶栏**木牌纯色区**
（画布 (200,10)，实测 RGB(140,96,56)）反推遮罩强度再还原采样色；
⚠️ 别取 (240,22)，那是进度条底槽 (70,44,24)，会把基准算错导致还原过度。
