# 系统只读分区禁区：**不可手工写 `/res`**（mtdblock / squashfs）

> 2026-09-19 入库（V85X 真机血案，代价 = 设备**卡 logo**、需要重刷才能恢复）。
> 适用：所有把应用资源放在**只读 squashfs 分区**的 FlyThings/EasyUI 设备。
> **一句话**：`/res` 只归**升级流程**管 —— 任何手工 `dd` / `mount` / `flash_erase` / 回写镜像
> 都可能把它擦成**空分区**，后果是**应用连自己的库都加载不了、开机卡 logo**。
>
> 检索词：`/res 挂不上` / `res 分区` / `mtdblock3` / `/dev/mtd3` / `squashfs 只读` / `卡 logo` /
> `开机卡住` / `应用加载不了 so` / `画面冻住但进程活着` / `手工刷 res` / `dd 写分区` / `mount res` /
> `升级卡住 / 升级要多久` / `固化判据` / `md5 校验` / `reboot 后没界面` / `注入没反应` / `自检通道不响应`

## 1. 铁律（先看这个）

⛔ **不可操作系统默认只读分区** —— 除非需求方**明确点名**要写某个分区：

- `/res` 及其实体：`/dev/block/mtdblock3`、`/dev/mtd3`、`/dev/mtdblock*`；
- 以及任何**非本工程目录**的分区 / MTD 设备。

**不许**的动作（全部实测有害）：

| 禁止动作 | 说明 |
|---|---|
| `dd ... of=/dev/block/*` / `of=/dev/mtd*` | 手工回写镜像 —— **看起来能成功**（回读 md5 一致），但绕过了升级流程 |
| `mount -t squashfs /dev/block/mtdblock3 /res` | 挂载由 init 负责；手工挂只会掩盖"分区已坏"的事实 |
| `flash_erase` / `nandwrite` / `ubiformat` / `ubiattach` | 直接动 MTD |
| `mkfs.*` / `blockdev --setrw` | 改文件系统 / 改只读位 |
| `rm` / `mv` / `cp` 到 `/res/...` | 只读分区，任何写都是错信号 |
| **升级途中 `reboot`** | **最危险**：会把"卸载 → 擦 → 写"打断在中间 |

✅ **唯一正路**：走框架自带的**升级流程**（出 `update.img` → 触发升级），
它自己完成「**卸载 → 擦 → 写 → 挂回**」。MCP 侧就是 `flythings_pack_upgrade`。

## 2. 为什么这么严：升级是一个"原子过程"

- `/res` 是**独立小分区上的 squashfs，挂载参数 `ro`**（实测约 2MB 级、基本写满），
  里面装的是**应用自己的库与资源**（如 `libzkgui.so`、`ui/*.ftu`、`font/*.ttf`、`ui/images/*`）；
- 升级 = ①卸载 `/res` → ②**擦**该分区 → ③写入新镜像 → ④**挂回**。
  ②到③之间，**`/res` 必然是空的**（读它就是"没有这个文件"）；
- 全过程**没有事务**：中途掉电/重启/重新触发 ⇒ 停在被擦空的状态。

判据（只读，随时可查）：

```bash
cat /proc/mtd                      # 看分区表（res 在第几个 mtd）
cat /proc/mounts | grep ' /res '   # 有这一行才算挂上
```

## 3. 血案复盘：中断擦写的三层后果

起因很"无辜"：**固化校验的判据窗口太短**，在窗口内读到 `/res` 的旧值 ⇒ 脚本误报"固化失败"。
为了"让它自己修好"，给脚本加了 **「重触发不成就 `reboot` 再验」** —— 那次 `reboot` 正好插在擦写过程中。

后果按严重度递进：

1. **分区被擦空**：`dd if=/dev/block/mtdblock3 bs=16 count=1 | hexdump -C` 是一整片 `0xff`，
   看不到 squashfs 的 `hsqs` 魔数；
2. **`/res` 挂不上** ⇒ 应用**连自己的 `libzkgui.so` 都加载不了**；
3. ★★ **症状极具误导性**：进程**活着、还在吃 CPU**，但**画面冻在最后一帧**、
   **所有自检/命令通道都不再被轮询**（看起来像"触摸坏了"或"界面卡死"）；
4. ★★ **死锁**：**升级处理逻辑本身在应用里** ⇒ 应用起不来就没人处理升级
   ⇒ 下发升级属性也没反应 ⇒ **卡 logo，只能靠 TF 卡 / 完整重走升级流程救**。

## 4. 症状识别表（先查这个，别猜界面/触摸）

| 现象 | 优先怀疑 | 查法 |
|---|---|---|
| 画面**冻住**、进程**在吃 CPU**、**所有通道不响应** | `/res` 没挂上 | `cat /proc/mounts \| grep ' /res '`（空 = 没挂） |
| 升级属性下发后毫无反应 | 同上（升级处理在应用里） | 同上 |
| `/res` 是空的 / `ls` 报 No such file | 分区没挂（或刚被擦） | `cat /proc/mtd` 确认分区在、再看挂载 |
| 想确认分区内容是否完整 | 别写，只**读** | `head -c 16 /dev/block/mtdblockN \| hexdump -C` 找 `hsqs` |

## 5. 正确恢复：**完整重走一遍升级流程**

- 重新出包 → 触发升级 → **等它自己走完**（实测 **4~10 分钟**，取决于编译产物大小）；
- 期间下列现象**都算正常，不是失败**：
  - `adb` 报 `device not found`（设备在重启/切换）；
  - `/res` 读不到、`ls /res` 是空的（正处于卸载/擦写中）；
- **不打断**：不要 `reboot`、不要重新触发、不要手工 mount/dd。

> 经验口径：**"再走一遍升级流程就好了"** —— 这是需求方的原话，也是唯一正确的处置。
> 情急之下手工 `dd` 回写即使"回读 md5 一致"，也只是把**不该我碰的分区**又碰了一次。

## 6. 判据怎么写（这一步最容易把"正常"判成"失败"）

自动校验"包有没有真的刷进去"时，四条纪律：

1. **比 md5，不比字节数** —— 只改素材不改代码时，`.so` 的**字节数完全相同**，比字节数会**假通过**；
   但要**分别**校验：核心库 + 至少一个**改过的素材**（"库对"不代表"图对"）。
2. **要等 `/res` 挂回来**再比 —— 升级期间读它是空的，不算失败；窗口给足（≥10 分钟）。
3. **绝不自动重触发** —— 每次重触发都**重新开始擦写**，只会把离线时间越拖越长
   （实测后果：脚本连续报"失败"，而设备每次其实都在正常升级）。
4. **绝不 `reboot`** —— 脚本里应当 grep 不到 `reboot`；需要重启是**流程自己**决定的。

## 7. 附带的一个通用教训

**任何"靠人记住"的红线，都要配一个"机器会报"的判据。**
本条的落地方式 = 宿主侧 `PreToolUse` 钩子（命中 `dd of=/dev/...`、`mount` 设备分区、
`flash_erase`、`mkfs` 等模式 → 直接拒绝执行），而不是只在文档里写一句"禁止"。
★ 且**拦机器也要先证明它真会拦**：拿一个已知危险样本喂它，确认真的被拒。
