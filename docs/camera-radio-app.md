> 版本：`v1.30.x`。两个应用都是**独立 ftu**（各带一个 Activity + 自己的屏保/按键/QA 通道），
> 与画布游戏（不新建 ftu）不同 —— 改动清单见 `RULES-DETAIL.md` §5.A「五处一起改」。

## 1. 网络收音机 `radio`（slot 30）

### 1.1 链路（**纯音频源**）

```
电台表(kBuiltinSta[] / /data/radio.txt)
   ├─ 直连 mp3/aac ─→ pg::StreamPlayer::startDecodeTest(url, 0)
   └─ HLS (.m3u8)  ─→ pg::Hls::start(url, play, n) → startDecodeTest(play, 0)
```

- `startDecodeTest(url, 0)` = 「**只解音频、不要画面**」。`PgStream` 里有 `if (!hasVideo)` 分支：
  跳过 MPP / 硬解 / 显示（`sDisp=0`），ffmpeg 软解 → 重采样 **22050Hz / 单声道 / S16** →
  写进**常开 PCM 流**（`PgAudio::streamOn/streamWrite`）。
- **换台必须用 `stopForSwitch()`**，不能用 `stop()` —— `stop()` 会置 `sNeedsReset`，那是给
  **主界面主循环**消费的；独立 ftu 页没人消费，会卡在"待复位"。
- 相位机：`0 空闲 / 1 连接中 / 2 播放中 / 3 出错`；判"真的出声了"用
  `pg::StreamPlayer::positionMs() > 0`（**位置毫秒在走 = 音频在流**），比看标志位可靠。

### 1.2 电台表

- 内置：SomaFM 3 台（直连 mp3）+ 央广 中国之声 / 经济之声 / 音乐之声（HLS m3u8）。
- 自加：`/data/radio.txt`，每行 `名称|地址`，`#` 开头是注释。
- 解析用 `parseStaLine()` 容错：行里带 `|` 就够，两边空格自动去掉；超长截断。

### 1.3 QA（`/tmp/pg_radiocmd`）

`radio <n>` 播第 n 台 · `radiolist` 列表 · `radiostat` 状态 · `radiosave 名称|地址` 追加保存 ·
`radiohint` 打印提示 · **`quit`（退出该页，见下）**。

> ★ **独立 ftu 页必须有 `quit`**（v1.30.8 补）：本页是独立 Activity，主界面那条
> `/tmp/pg_autostart` 管不到它 —— 以前脚本验收"进来之后出不来"，只能重启设备或人去点返回箭头。
> `quit`/`exit` 与返回箭头走**同一个函数**（`radioQuitAndCleanup()`：停引擎 + `closeActivity`），
> 所以 QA 退出的收尾状态与人工退出**完全一致**（这条纪律 = "QA 钩子必须走与真实操作同一条路"）。

### 1.4 电台表：7 台 → **61 台**（2026-09-18 逐台实测）

用户需求：「**把网络收音机的电台数量实测更新一下**」。原来的表只有 7 个"示例台"（3 个 SomaFM +
1 个 Radio Paradise + 3 个央广），是**拍脑袋写的**，而且电台 URL 的寿命很短（换 CDN / 下架 /
限流都会发生）⇒ 关键不是"多抄几个"，而是**"这表里到底有几个能听"这件事必须能一键复测**。

#### ① PC 侧粗筛：`tools/radio_probe.py`（新）

```bash
tools/radio_probe.py -i tools/radio_cand.txt --report docs/radio-probe.md   # 91 条候选
```

判据（**都是真去拉一段字节，不看清单里声明什么**）：
- 直连流：读前 16KB，在**前 8KB** 里找同步头，并且**用第二帧确认**（帧长算得出来、下一帧同步
  对得上）—— 只看头几个字节会把能播的台误判成打不开；
- HLS：拉清单 → master 取最低码率档 → 拉第一个分片 → 验同步字（TS/ID3/ADTS）；
- 顺带认 `ICY 200 OK`（Shoutcast，`http.client` 会当非法状态行报错，但**设备的 ffmpeg 是认的**）。

★★ **两个必须记住的坑**（本次各踩一次，合计误报 20+ 个台）：
1. **PC 上常常挂着 `http(s)_proxy`**（本机就有）：代理会把流转写成非音频字节
   （同一个 URL 走代理首字节是随机数据、绕过代理才是 MP3）⇒ 探针里用
   `build_opener(ProxyHandler({}))` **强制直连**（设备上没有代理，直连才代表真机）。
2. **流前面常有一段非音频前缀**（实测蜻蜓的流第 0 字节是随机字节、MP3 同步头在第 6/15/144 字节）
   ⇒ 必须**扫一段**再配"第二帧确认"，只看前 64 字节会误报。

结果：91 条候选 → **OK 76 / FAIL 15**。失败集中在"被墙或超时"（RTHK 4 个、法国台 3 个、
Café del Mar）和"该台已下架"（浙江之声 / 南京 / 天津相声 / 央广音乐之声 403…）。

#### ② 真机复测：QA `radioscan`（**以真机为准**）

PC 能连 ≠ 板子能放（DNS/IPv6/TLS 握手/解码器支持度都不一样，本项目在 RTSP 上栽过
"探测通、播放不通"）。所以给页面加了 `radioscan [每台ms]`：**逐台走真实播放路径**
（`radioPlayAt`，不另写一套探测代码），判据是**位置毫秒真的在走**（= 真出声），
结果写 `/data/radio_scan.txt`，并把"实测可播/实测打不开"直接标在列表行上。

★★ **写它时踩的两个坑**（都会让"整表 61 台全报打不开"，而同一台手动点明明在出声）：
1. **`stopForSwitch()` 只是"请求停止"，收尾是解码线程异步做的** ⇒ 连续 `stop→start` 会被
   `startDecodeTest` 直接拒掉（每台 0.1s 就"出错"）。
   ⇒ 起流前**必须确认 `running()==false`**（扫描做成"等空闲"状态机，最多等 2s），
   并且对"400ms 内就被拒"的台**重试**（这是"引擎正忙"，不是"这个台坏了"）。
2. **扫描期间不走 `tickRadio()`**（`onUI_Timer` 里扫描与相位机是二选一），而"真的出声了"正是
   相位机用 `positionMs() > 0` 判出来、把 `连接中` 抬成 `播放中` 的 ⇒ 少了这一句，
   `gPhase` 永远停在"连接中"⇒ 每台都"等出声超时"。扫描里必须自己推一遍相位。

### 1.5 播放页改版：大圆盘 + **30 段真 FFT 频谱**（2026-09-18）

用户需求：「**播放界面改成大气一些。参考手机 app，有个音乐播放的指针摆动或者 FFT 波形展示
播放状态**」。做法：**不用假动画** —— 频谱数据来自真正在出声的那条路。

```
PgStream（ffmpeg 软解 → 重采样 22050/单声道/S16）
   → PgAudio::streamWrite(pcm, frames)      ← ★ 在这里 pg::Viz::notePcm()
   → 常开 PCM 流 → 喇叭（耳朵听到的就是它）
```

`src/platform/PgViz.*`（新）：环形缓冲 → 每 30ms 取 512 点做 **Hann 窗 + radix-2 FFT**
→ **30 段对数分频**（60Hz~9kHz，取段内峰值）→ dB 映射（默认零点 **-70dB**、动态 50dB）
+ 快起慢落（0.55 / 0.13）→ UI 每拍读一次。CPU：一轮 ≈2.3 万次浮点、≤33 次/秒，
**实测动画中进程 CPU 只涨几个百分点**（同屏 30 个控件 `setPosition` 的成本也在里面）。

页面（`ui/radio.html` 的 `WinRadioPlay`）：

| 位置 | 内容 |
|---|---|
| y 100..340 | **大圆盘** 240x240（黑胶片 + 同心纹 + 暖橙标签 + 白音符，`tools/gen_radio_art.py` 生成） |
| y 348..452 | 台名（30px）/「分组 · 域名 · HLS 分片数」/ 已播时长（等宽大字 22px 青色） |
| y 454..462 | **总电平条**（320x8，按 RMS 改宽度） |
| y 464..596 | **30 段频谱柱**（`EqB00..EqB29`，柱宽 12、间距 4、满格 132px） |
| y 620..724 | 三个**圆形控制键**（上一个/停止/下一个，图 = 整个按钮面） |

★ 实现要点（照抄这三条就够）：
1. **柱子的初始盒 == 素材尺寸 12x132**（所以 `check_stretch` 过），运行时**只改高度**
   （`LayoutPosition(x, 596-h, 12, h)`）—— 素材按盒缩放，属于"运行时改尺寸"那一类；
2. **变了才 `setPosition`**（30 个控件每拍无脑写 = 重绘风暴，屏保页的教训）；
3. 连接中/停止时的"等待动画"由**绝对时钟**推导（来回扫描的一道波），
   不许用"累加 dt/帧计数"（宠物页冻死过两次）。

**真机验收**（`/tmp/pg_radiocmd` 的 `viz` 给数字、抓帧给像素）：
- `viz` 快照（播"中国之声(直连)"）：`电平=250 增益=-70dB 段数=30 FFT次数=255 已灌帧=1104034`
  `段=[203,203,235,234,237,233,233,224,214,206,193,187,165,155,148,158,144,132,131,118,113,114,...]`
  —— 低音重、高音轻，正是真实音乐的包络；
- **连抓三帧量柱高**（`2+i*16+6` 列的亮像素上沿）：`86 86 107 ... 131 132` → `88 88 93 ... 99 100`

#### ★ v1.33.1 追加：**幅度跟随系统音量**（用户需求「音频的幅度跟随系统声音调整最高幅度」）

**为什么需要它**：取点选在 **PCM 出口** ⇒ 音量是**下游**做的 —— 本板音量写的是 codec 的
**数字音量**，PCM 数据里**不含音量信息**（这也正是"静音后频谱不动"能成立的原因）。
于是"把音量调小、柱子还顶到天花板"看起来就不对。

**做法**：显示侧乘一个**系统音量系数**（不改 PgViz 的原始测量值）：

| 系统音量 | 系数 | 效果 |
|---|---|---|
| 100% | 255/255 | 满格（柱高上限 132px） |
| 28% | 71/255 | 柱顶 ≈ 1/3 |
| 0% / 静音 | **0** | 整排只剩脚底 8px 短桩 |

- "连接中"的等待扫描**不乘**这个系数（它表示"正在连"，不是音频幅度；否则音量调小后
  等待动画会比播放时的柱子还高，看着像坏了）；
- 取不到音量（`volumePercent() < 0`）时按**满**处理 —— 宁可显示满格，也别让频谱整屏消失；
- QA 旋钮：`vizfollow 0|1`（关掉做对照实验）、`vol <0..100>`（本页直接改系统音量）。

**真机验收（同一台、同一音量 28%、单变量对照）**：

| 状态 | `viz` 打的柱高 px | 抓帧实测柱高峰值 |
|---|---|---|
| 跟随**关** | `127,127,130,…,51` | **128 px** |
| 跟随**开** | `25,25,28,…,17` | **38 px** |
| 跟随开 + 音量 **0%** | 全 `8,8,8,…,8` | 频谱区亮像素 720（只剩短桩） |

⇒ `38 / 128 ≈ 0.30` 正好对上 28% 音量。证据图 `docs/shot_radio_vol_follow.png`（三态上下对照）。

★★ **实现口径（照 MCP 知识库 `uicontrols/pointer-fields.md`，不是猜的）**：

| 要点 | 做法 |
|---|---|
| 控件 | `<div class="pointer">`（html2json 认 `pointer`/`gauge`/`dial`）⇒ 生成 `ZKPointer` |

⚠️ **血案一条**：`needle_layer()` 一开始收的是 **dB**，`needle_layer(..., db=0.0)` 按

★★ **真双声道**：原来的频谱取点是**下混后的单声道** PCM ⇒ 拿不到左右差异。
现在在 `PgStream` 的音频解码处、**重采样之前**按声道取 RMS（`frameStereoRms()`，支持
FLTP/S16P/S32P/FLT/S16/S32）喂给 `PgViz::noteStereoRms()`；RMS 与采样率无关
⇒ **不用重采样、也不用 FFT**，成本只有几千次乘加。
`PgViz` 里做 **VU 弹道**（上升 55ms / 回落 320ms）：真表的针是"甩上去、慢慢落"，
不做弹道只会"抖"。0 VU 默认 = **-18dBFS**，QA `vu0 <dBFS>` 现场标定。

**QA**：`view 0|1`（频谱/表盘）、`vu0 <dBFS>`（标定）；`viz` 现在同时打
「原始段值 / 柱高px / **L/R 电平·dB·指针角度**」，并**再写一份 `/data/radio_viz.txt`**
（单行快照，见 §1.6.4 为什么必须有它）。

**② 0VU 零点：默认 −18 → −8 dBFS（实测数据，不是拍的）**
用 QA 把零点临时设成 `vu0 0`（读数即**绝对 dBFS**），逐台采样：

| 场景 | RMS（dBFS） |
|---|---|
| 最响的音乐台（Jazz Radio 爵士 / SomaFM The Trip） | −9 … −11 |
| 怀集音乐之声（连采 18 次） | 均值 **−10.5**，范围 −8.0 … −13.6 |
| 经济/环球/山东音乐（说话+音乐） | −14.7 … −16.2 |
| 安静台（美国公共广播、蓝调） | −22 … −24 |

⇒ −18 的零点会让**大部分台的针顶死在刻度末端**（实测确实如此：连抓 4 帧全在 +33.4°，
而刻度上限是 +34°）—— 表看着"坏了"，其实只是零点太低。
取 **−8** 后：音乐台停在 0VU 标记附近（±15° 内摆）、说话台落在中下段（−20°~−35°）、
最轻的台接近底部 —— 整条弧都用上了。

**③ 三个真 bug（都是"上机才暴露"的那类）**

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 台打不开/停播后**针冻在最后一个值**（实测僵在 −4.4dB 不动），看着像表坏了 | VU 电平是**解码线程**喂的，停流后没人喂 ⇒ `sVuLin` 保持最后值 | 新增 `pg::Viz::vuTick()`（**页面 100ms 那一拍**调）：静音 **400ms** 后按回落弹道归零；幂等。`noteStereoRms`/`vuTick` 两边都动 `sVuLin` ⇒ **都加锁** |
| 2 | 换到**打不开**的台时屏幕上还挂着**上一台的频谱柱**（像还在播） | `Viz::reset()` 只在 `radioStopTo()`（停止/退出）里调，**换台这条路漏了** | `radioPlayAt()` 里补 `pg::Viz::reset()` |

### 1.6 双指针 VU 表：几条"上机才知道"的规则

抽成判据，别的页面做指针/电平表可以直接照抄。

#### 1.6.1 表针"看着像坏了"的两种典型症
- **针不动（冻住）**：电平源停了 ⇒ 弹道变量保持最后值。**任何"由别人喂数的表"都要有回落兜底**，
  而兜底必须由**自己的定时器**推（不能指望数据源给你发"我停了"）。
- **针顶死在末端**：**零点标定错了**，不是数据坏了。先用一个"读数=绝对值"的口径
  （这里就是 `vu0 0` = 0VU 对齐 0dBFS）采一批真数据，再决定零点。**别用眼睛调表。**

#### 1.6.2 表针的回落要有"保持"段
只在 `dt > 400ms` 没收到数据时才回落。解码帧平时 20~46ms 一块，
不留保持段的话，正常播放里偶发的几十毫秒小停顿会让针乱抖（真表也不会那样）。

#### 1.6.3 换台/换源：**请求停止 ≠ 已经停止**
`stopForSwitch()` 只是登记请求，收尾（"解码器放空"）是异步的，实测 **~1500ms**。
这之前起新流会被拒绝。两种做法里**要选后者**：
- ✗ 在 UI 线程里 `while (running()) sleep(20)` —— 界面会僵 1.5s；
- ✓ **两段式**：请求时只登记，交给页面定时器等 `running()==false`（+超时兜底）再起。

★ 判据：**任何"停止 → 立刻开始"的序列，中间都必须有一个可观测的"已停止"状态**。
本页扫描路径一直这么做（`sScanWaiting`），正常换台漏了整整一版。

#### 1.6.4 本板日志不可依赖 ⇒ 快照要**同时落文件**
这板子的日志服务被 SSDP 之类的噪声刷爆后会**整块卡住**：`adb logcat -d` 只回最后一次
flush 的内容，`adb logcat` 流也只 flush 一次就断（本次实测：起一个常驻收集器，
3 秒后 841 行，之后**再也不增长**）。
⇒ 需要"数字证据"的 QA 命令一律**顺手写一个文件**（`/data/radio_viz.txt`），
读文件比抢日志稳得多。⚠️ 只在 QA 调用时写，**不要每拍写**（`/data` 在 NAND 上）。

#### 1.6.5 读表的像素工具：`tools/vu_angle.py`
从抓屏里量两只表的指针角度（`--csv` 出表格），**先按"径向覆盖率"粗定位、再用针尖坐标精修**
（小半径处 1px 横向偏差顶好几度 ⇒ 只用覆盖率只有 ±2°；精修后 <1°）。
搜索角限制在 **−95°~+62°**（刻度弧在上半圈）。
它和页面自报角度互相印证 —— 这就是"**验收判据要落到画面上**"的意思。

★★ **两条会把它整坏的坑（都是 2026-09-19 改版当场踩到的）**：
1. **命中必须限制在面盘矩形内**（`read_meter` 的 `face` 参数）。
   指针色 (30,26,20)±12 就是"很暗的暖黑"，而页面上的**按钮面 (22,22,24)、
   导航栏 (28,28,30)、提示条**全都落在容差里。老版铰点在面盘**内**、搜索盘整个在浅黄面上，

## 4. 台架：手边没有真 RTSP 摄像头时怎么验

现场若没有开 554/8554 的设备（本次实测：LAN 40 台、0 台开 RTSP），只能用合成源。
踩过的坑按顺序记在这里：

1. **`ffmpeg` 不能当 RTSP 服务端**。`-f rtsp -rtsp_flags listen` 在本板 PC 侧的 ffmpeg 里
   被忽略 —— 它仍然**主动去连** `tcp://0.0.0.0:8554` 并报 `Connection refused`。
2. **VLC 可以当 RTSP 服务端，但只支持 RTP/UDP**。客户端要 `RTP/AVP/TCP` 会拿到
   **`461 Unsupported transport`**。所以：
   - 板子侧探测**强制 TCP** 时，VLC 这种源**连 SETUP 都过不去**；
   - 板子侧播放走 ffmpeg 默认（UDP）时才能接上。
   → 这就是 §5 那条"探测与播放传输方式必须一致"的由来。
3. **VLC 的 `sdp=` 地址别写 `0.0.0.0`**：`sdp=rtsp://0.0.0.0:8554/xxx` 会让 DESCRIBE 返
   **500 Internal Server Error**；写成 `sdp=rtsp://:8554/stream`（主机名留空）就正常。
4. **VLC `--loop` + `--sout-keep` 会越跑越坏**：跑几轮之后连 PC 本地客户端都拉不到帧了
   （RTSP 控制连接还 ESTABLISHED，但 RTP 不来了）。**改用"一个长源"**，别靠 loop。
5. **VLC 转码出来的流参数集不全**：`#transcode{vcodec=h264}` 默认带 **84% 的 B 帧**，
   板子侧 ffmpeg 报 `Could not find codec parameters ... unspecified size`、`0x0`，
   `PgStream` 于是"推迟起播边读边解析 SPS"却一直等不到。
6. **裸流 `.h264` 喂 VLC 反而更差**：DESCRIBE 直接 500（VLC 拿不到 ES 信息）。
7. ⇒ **最后用 `tools/range_http.py` 起 HTTP 服务**（项目自带，**支持 Range**，必须绑具体网卡 IP，
   绑 `0.0.0.0` 会被 Windows 防火墙挡）：
   ```bash
   python tools/range_http.py 8099 <目录> 192.168.1.19
   adb shell "echo 'camurl http://192.168.1.19:8099/cam_test.mp4 #x1' > /tmp/pg_camcmd"
   ```
   这条把**摄像头页自己的**"起流 → 解码 → 首帧 → 收起底图 → PLAYING"整条路验完了；
   剩下没验到的只有"RTSP 传输层"本身（已单独证明：起流后板子
   `/proc/net/snmp` 的 `Udp: InDatagrams` 10 秒涨了 **1056**，说明 RTP 确实在收）。

## 5. 本项目顺带修掉的两个真问题

### 5.1 数独动作键溢出屏幕（**生成器改了没重跑**）

- 症状：第 5 个动作键「新局」**整体画在屏幕外**。抓屏字符画里 x 起点 460 > 画布宽 480。
- 根因：`tools/gen_instr_art.py` 的 `SUDOKU` 几何已改成 `act_w=88`，但**没重跑
  `tools/gen_game_art.py`** ⇒ `src/core/PgGameArt.h` 里还是旧的 **112px**
  （5×112 + 4×6 = 584 > 480）。
- 修法：重跑生成器 → `act_w=88 / act_n=5`（5×88 + 4×4 = **468 ≤ 480** ✓）。
- ★ **教训：改生成器里的几何常量后必须重跑生成器**；
  **编译通过、功能断言全对，都抓不到"画到屏幕外"** —— 只有看图能发现。

### 5.2 RTSP 传输方式前后不一致（**探测 TCP / 播放 UDP**）

- 症状：`probeFast()` 里 `av_dict_set("rtsp_transport","tcp")` 是写死的（当初为了"有些 IPC
  只在 TCP 上回包"），而**播放侧 `PgStream::openInput` 一个传输参数都没设** ⇒ ffmpeg 默认 **UDP**。
- 后果：**"探测报找到、播放却没画面"** —— 只认一种传输的摄像头必然掉一边。
- 修法（两边都加回落，方向相反、合起来覆盖两种）：
  - `PgFf::probeFast`：**TCP 优先 → 失败回落 UDP**，日志里打印实际用的 transport；
  - `PgStream::openInput`：**UDP（默认）失败 → 回落 TCP**。

### 5.3 `camgrab` / `streamgrab` 静默不落盘（**钩子挂错路**）

- 症状：QA 打了 `已安排抓帧 —— 下一次播放到第 30 帧时 dump`，但 `/tmp/pgframe.pgm`
  **永远不出现**。
- 根因：抓帧钩子只写在 `PgStream` 自己 `VO_SendFrame` 的**通用路**上；而实际在跑的是
  **HW 路**（喂包给 `PgH264Player`，显示在它自己的**解码回调**里完成）⇒ 钩子永远不被走到。
- 修法：抽出 `src/platform/PgGrab.h`（`grabTake()` / `grabWritePlane()`），
  **两条路都调**：
  - `PgH264::onDecodedFrame()` → `grabTake(s.framesDecoded)` + `grabWritePlane(data0, w, h, stride=w, "hw")`
  - `PgStream` 通用路 → `grabTake(nFrame)` + `dumpFrameY(*pf)`
  先跑到目标帧数的那条路落盘，请求只消费一次。
- ★ 一般规律：**"日志说做了、结果没有"的钩子，先确认它挂在"实际在跑的那条路"上**。

### 5.4 摄像头画面被"上一次转屏"带歪（**全局粘性状态跨应用泄漏**）

- 症状：摄像头画面**躺倒 90°**（日志 `PgStream: 旋转 -- 源元数据=未指定 手动=90° → 本次用 90°`）。
- 根因：`PgStream` 里的 `sRotManual` 是**全局粘性值**；主界面每次起播都会拿**存盘的偏好**
  去设它（`mainLogic.cc: setRotation(gHost->store.rotDeg())`），那是**网络电视页"手动转屏"**
  留下的。⇒ 用户在网络电视里转过一次屏，再进摄像头页就被一起转。
- 修法：`camStartStream` 起流前**显式** `pg::StreamPlayer::setRotation(0)`（**不转**）。
  ★ **注意不能用 auto**：`desiredRotation()` 在"源没元数据"时**兜底返回 90°** ——
  那是给**投屏 / 网络电视**定的（手机横屏源投到竖屏机，必须转 90° 才看得见）。
  IP 摄像头一律是**横屏源且不带旋转元数据**，套上这条兜底就变成"竖屏里放横着的画面"。
  摄像头要的就是**0°**（`fitRect` 按 480×700 等比适配、上下留黑），画面才是正的。
- ★ 规律：**全局/静态的"用户偏好"型状态，每个会用到它的页都要显式复位**，
  不能假设"上一个页会收尾干净"；这类泄漏不会报错，只会"画面莫名不对"。
  同理，**通用兜底值未必适用于每个页** —— 要用它的页要把语义想清楚再决定"跟随还是钉死"。

## 6. 2026-09-17：现场"扫不到摄像头"的完整排查（**不是跨网段，是三个真 bug**）

> 现场描述：「局域网摄像头扫不到，怀疑跨网段 / 网关没设，或者先用电脑模拟一个测一下」。
> 结论：**与网段无关**。设备 `192.168.1.63/24`、网关 `192.168.1.1` 都正常（ping 网关 2.8ms），
> 摄像头（**海康** IPC）就在**同一个 /24** 的 `192.168.1.163`。真因是下面三条。

### 6.1 病灶①：扫描里有两个**静默上限**（摄像头被"排队排在后面"丢掉了）

| 位置 | 原值 | 后果 |
|---|---|---|
| `PgLan.h` 的 `kLanMaxHost` | **40** | 设备 `/proc/net/arp` 里实测 **100 条**邻居 ⇒ 后 60 台**静默丢弃** |
| `PgLan.cpp` worker 阶段三 `total = n > 24 ? 24 : n` | **24** | 只有**前 24 台**做端口/指纹，其余在列表里"端口为空"，被摄像头页按 554/8554 过滤掉 |

- **`/proc/net/arp` 是哈希序，不是 IP 序** ⇒ "哪 40 台/哪 24 台进得来"是**随机的**。
  现场表现就是"时好时坏 / 明明有摄像头却扫不到"。
- 修法：`kLanMaxHost` → **128**；新增 `kLanMaxFinger = 96`；**两处满了都打 WARN**
  （原来是 `continue` 静默丢弃 —— 违反"静默失败必须消灭"）。
- 实测：`局域网 0~1 台` → **`局域网 92~97 台，其中 2 台开了 RTSP 端口`**（合成源 + 海康都进来了）。

### 6.2 病灶②：`PgFf::probeFast` 对**任何** RTSP 地址都秒挂（"点一下自动找地址"根本走不通）

- 症状：点任意一台摄像头，每条候选路径都在 **1ms 内**失败：
  ```
  PgFf: probeFast 打不开 'rtsp://192.168.1.19:8554'（transport=tcp）：Address not available (-99)，耗时 0ms
  PgFf: probeFast 打不开 'rtsp://192.168.1.19:8554/stream1'（transport=udp）：Address not available (-99)，耗时 1ms
  ...
  ```
  **连本机起的、`camurl` 能正常播放的合成源也一样** ⇒ 不是摄像头的问题，是探测自己的问题。
- 根因：`probeFast` 给字典塞了 `timeout`。**同名选项在 RTSP 解封装器里的含义是**
  > `timeout` — set maximum timeout (in seconds) to wait for incoming connections
  > (**-1 is infinite, imply flag listen**)

  设了非负值 ⇒ ffmpeg 把 rtsp 切到 **listen 模式**，去 `bind()` URL 里那个 `ip:port`；
  而对端地址当然不是本机地址 ⇒ `EADDRNOTAVAIL(-99)`，**瞬间失败**。
- 顺带第二个坑：`rw_timeout` / `stimeout` 单位是**微秒**，而调用方给的是**毫秒**
  ⇒ 实际超时只有 **3ms**，本就极易误判"打不开"。
- 修法（`PgFf.cpp::probeFast`）：
  - `to = timeoutMs * 1000`（毫秒 → 微秒）；
  - **RTSP 只设 `stimeout`**（它的语义才是"socket TCP I/O 超时"），
    `timeout` 只留给非 RTSP（http/tcp）。
- 实测：`probeFast 成功 'rtsp://192.168.1.19:8554'（transport=tcp，耗时 29ms）`，
  整轮探测 `found=1 用时 104ms`。
- ★ 规律：**同名 option 在不同 demuxer/protocol 里语义完全不同**，
  给 `avformat_open_input` 塞字典前必须确认这个 key 在**这条 URL 协议**下是什么意思。

### 6.3 病灶③：**任何 RTSP 摄像头开流都要卡 16.5 秒**（超过页面 15s 等待 ⇒ 必然 ERROR）

- 症状（摄像头页日志三连）：
  ```
  PgFf[ffmpeg]: Stream #0: not enough frames to estimate rate; consider increasing probesize
  PgFf[ffmpeg]: Could not find codec parameters for stream 0 (Video: h264): unspecified size
  PgStream: 打开成功 用时 16530ms 视频[0] codec=h264 0x0
  ```
  同时 `cameraLogic: 等第一帧超时 15001ms` ⇒ 界面上是 ERROR，
  **但其实码流一直在解、硬解回调在出帧**（`PgH264: 解码回调 #240`）—— 只是开流太慢。
- 根因链：直播流的 H.264 **没有容器头**，宽高只能靠
  (a) 软解探一帧，或 (b) 解析 SPS。
  - (a) 在本工程被**主动放弃** —— `PgFf.cpp` 为了把 `libzkgui.so` 从 14.5MB 降到 2.6MB，
    把 `avcodec_find_decoder` 打了桩，**H.264 一律返回 NULL**；
  - (b) RTSP/RTP 解封装**不会自动设 `need_parsing`**（RTP 自己就产出完整 AU）。
  ⇒ `avformat_find_stream_info` 里 `has_codec_parameters()` 永远为假，
    它会一直读包直到 `probesize`（默认 5MB）/分析时长上限才放弃 —— **16.5s 就是这么烧掉的**。
- **试过但无效**：给流设 `st->need_parsing = AVSTREAM_PARSE_FULL`（解析器确实建起来了，
  日志 `parser=有`），但该版本里 `has_codec_parameters` 看的是 `codecpar`，
  解析器把宽高写进 `internal->avctx`，两边不同步 ⇒ **仍然 0x0、仍然 16.5s**。留着无害，但不是解药。
- **有效的修法**（`PgStream.cpp::openInput`，在 `avformat_find_stream_info` 之前）：
  只要视频流的 `codecpar` **没有宽高**（= 直播流），就把探测预算收紧到
  `probesize 512KB` / `max_analyze_duration 3s`。
  **代价是 0** —— 宽高本来就要靠应用自己解 SPS
  （`PgStream: [HW] 从 SPS 解析到源尺寸 1280x720`），ffmpeg 多读那几 MB 一个有用信息都不多。
  ⚠️ 必须加 `width==0` 这个条件：**MP4/MOV 这类有容器头的源一个字都不许动**
  （正常路径保持原样）。
- 实测：`打开成功 用时 16530ms` → **`1512~1717ms`**；`第一帧已出 → PLAYING（2971~3118ms）`。
- ★ 规律：**"打开成功"这几行里其实含 `avformat_find_stream_info`** ——
  只盯着 `avformat_open_input` 会漏掉"分析阶段在空转"；凡是"开流莫名很慢"，
  先看有没有 `Could not find codec parameters ... unspecified size`。

### 6.5 台架：`tools/rtspsim.py`（**合成 RTSP 摄像头**，不用真 IPC）

现场用真摄像头验不方便（要口令、还会换来换去），所以补了这台"电脑当摄像头"的台架。
它把 §4 里"没验到的 RTSP 传输层"补上了：**真跑 DESCRIBE / SETUP / PLAY，按 RTP 发 H.264**。

```bash
# 用工程里现成的 720p 裸流当信号源（PC 侧绑具体网卡 IP，别绑 0.0.0.0 —— 见 §4.7）
python tools/rtspsim.py --bind 192.168.1.19 --port 8554 --file hd720.h264 --fps 25
#   --tcp-only   只认 RTP/AVP/TCP（逼客户端走 TCP，做对照实验用）
# 设备侧（摄像头页 QA 通道）
adb shell "echo 'camrescan #1' > /tmp/pg_camcmd"       # 应扫到 192.168.1.19:8554
adb shell "echo 'cam 0 #2' > /tmp/pg_camcmd"           # 探测 → 起流 → PLAYING
adb shell "echo 'camurl rtsp://192.168.1.19:8554/stream #3' > /tmp/pg_camcmd"  # 跳过探测直连
```

写这个台架时踩到的坑（都在脚本注释里）：
1. **RTP 头的 PT 在 byte1 的低 7 位，不在 byte0** —— 写错位置客户端会把流认成 PT=0（PCMU），
   与 SDP 里的 `96/H264` 对不上（自己写的客户端还测不出来，得看真机）。
2. `M`（marker）位要**每帧最后一个包**才置 1。
3. **UDP 模式也要发 RTCP SR**（`a=range:npt=0-` 时客户端会等它建时基）。
4. `struct.pack` 的格式串与实参个数**必须自己数一遍**（`BBH+6×I`：那个 `BBHIIIIII` 看着像 6 个 I，
   实际得配 9 个值 —— 多一个就 `expected 9 items for packing (got 10)` 把会话打死）。
5. Windows 防火墙：**绑具体网卡 IP**，别绑 `0.0.0.0`（沿用 `tools/range_http.py` 的经验）。
6. `tools/scannet.py` 是 PC 侧"扫某网段摄像头端口"的对照工具
   （`python tools/scannet.py 192.168.1.0/24`）—— **先确认网段里真有 554/8554**，
   再怀疑设备端，能省很多时间（本次就是它先定位到 `.163` 开 554）。

### 6.6 海康那台（`192.168.1.163`）现在怎么用

- 它需要 **Digest 鉴权**（`/Streaming/Channels/101` 回 `401` + `realm`），
  常见默认口令（admin/admin、admin/12345、abcd1234…15 组）**全部不通**。
- 探测表里**补上了海康的规范路径** `/Streaming/Channels/101`（主）与 `/102`（子），
  并排到**前 6 个**（第二轮的"默认口令"只重试前 6 条）。
  ★ 原来 14 条路径里**根本没有海康的路径** —— 国内最常见的 IPC 等于永远探不出来。

  然后进摄像头页 → 它排在第一行 → 点一下即播（已用合成源验过这条链路，见 §6.4 最后一行）。


### 6.7 进页等待 43s → 7.4s（**摄像头页专用精简扫描**）

修完 6.1~6.3 之后功能是全的，但**进页要等 43 秒**才把列表填满（92~97 台设备）。
原因是这一页复用了探针页的**全量**扫描，而它**只看 554/8554**。三处针对性收窄：

| 改动 | 省下 | 说明 |
|---|---|---|
| `Lan::startScan(..., camOnly=true)`：端口从 12 个缩到 **6 个**（554/8554/8000/34567/37777/5000） | 32.5s → 14.5s | 全量里的 **80/8080/9100/22 是"几乎每台机器都有"的通用口**，对它们做 HTTP HEAD 指纹才是单台耗时的大头；单台预算也从 700ms 压到 **350ms**（局域网 RTT 亚毫秒级） |
| 阶段三 **4 线程并行分片**（仅 camOnly） | 14.5s → **5.25s** | 每台只写自己的 `hosts[i]`，`probePorts/rtspDescribe/httpHead` 全是局部状态；这一段没人读 `/proc/net/arp`、没人改 `n` |
| **不发 SSDP**（`ssdp=false`） | −8.4s | 本页**从不读 `LanHost.ssdp` 字段**（只用 kind/vendor/ports/note）⇒ 那 8.4 秒纯白等 |

- **实测（86~89 台，同一网段）**：`开始扫描 07:56:41.365 → 扫描结束 07:56:48.725` = **7.4s**（原 43.0s），
  仍扫到 2 台摄像头，`列表重建` 日志从 **90+ 行降到 3 行**。
- ★ **探针页行为一个字不改**：并行/少端口/不打行日志全部挂在 `camOnly` 上；
  `startProbeAll()`（"深探端口指纹"按钮）**显式写回 `reqCamOnly=false`** ——
  这是个**粘性请求字段**，不写的话"深探"会被悄悄缩成 6 个口（按钮名与行为不符 = 静默失效）。
- 两个模式的分工（实测对比）：

  | 模式 | 触发 | 端口 | 单台预算 | 耗时 | 列表显示 |
  |---|---|---|---|---|---|
  | 精简（camOnly） | 进页自动 / 重新扫描 | 6 个 | 350ms | **7.4s** | `192.168.1.163 端口 554 8000` |
  | 深探（全量） | 「深探端口指纹」按钮 | 12 个 | 700ms | ~40s | `192.168.1.163 端口 80 554 8000` + `80:HTTP` |

- ★ **列表重建日志只在"条数变化"时打**：原来每探完一台 `gen` 就 +1、就 rebuild 一次，
  88~96 台会**重复打 90+ 遍**一模一样的两行 —— 本板日志缓冲只有十几行，
  刷爆之后真出问题反而看不见（进度由状态行显示，不需要靠日志）。

### 6.8 「账号登录」：在设备上直接输账号密码（2026-09-17 新增）

**为什么**：要 Digest 鉴权的 IPC（海康/大华…）自动探测拿不到 URL —— 不带凭据一律只回 `401`。
原来只能 `adb shell echo '名称|rtsp://user:pass@ip/路径' > /data/camera.txt`，
现场（用户手边没有电脑）根本用不了。

**链路**：
```
扫描页点「账号登录」→ 弹窗 WinCamPwd 填 账号/密码（自带 IME 键盘）
   → 拿这份凭据**再跑一轮路径探测**（不再试"常见默认口令"）
   → 命中哪条路径，就把**那条实测能播的完整 URL** 写进 /data/camera.txt（按 IP 去重）
   → 下次进页它就是"手动"条目、排在最前、点一下直接播
```
★ **为什么不硬拼"IP + 海康路径"**：各家路径不同，拼出来只是"猜的"；
用凭据探测一遍，落盘的一定是**实测通的**，什么牌子都通用。
★ **凭据用完即弃**：探测结束就清掉 —— 否则"接着点另一台"会悄悄拿上一次的密码去试。
★ **口令绝不进日志**：所有打印 URL 的地方统一过 `camMaskUrl()`（→ `:****@`）。

#### 实测（设备 20080411，固化版）

| 项 | 证据 |
|---|---|
| 弹窗 | `camlogin` → `打开账号密码弹窗（目标 192.168.1.163:554）`；抓屏见卡片 + 账号/密码框 + 取消/保存并播放 |
| **真实键盘输入** | pginj 点输入框 → `IME 打开：password=0 类型=0`（45 键全取到）；`pg_imecmd` 逐键 `k 21/23/38/18/37` → `IME QA: 文本(5) = 'admin'`；`done` → `cameraLogic: 账号框 5 字符`（IME 回调把字交回输入框，走的是**真实那条路**） |
| 符号可打 | 密码框敲 `ab@1` → `密码框 4 字符`（`imeTextType=ALL`，`@ : / . - _ #` 都在键盘上） |
| 成功链路 | 点「保存并播放」→ `带用户凭据探测 #0` → `probeFast 成功（tcp，26ms）` → `已保存到 /data/camera.txt —— 192.168.1.19 摄像头|rtsp://admin:***@192.168.1.19:8554` → `第一帧已出 → PLAYING（3280ms）` |
| 失败链路（海康错密码） | `探测结束 found=0 用时 372ms` + `探测失败 —— 账号或密码不对、或路径特殊（试了 16 个地址）—— 再点「账号登录」重填` ⇒ **不落盘、不静默** |
| 持久化 | 保存后 `reboot`，`/data/camera.txt` 内容仍在；进页 `列表重建 —— ... 加手动 1 条 ⇒ 共 3 条`，`#0 手动` 排在最前 |
| 直接播 | `cam 0` → `手动地址直接用 rtsp://admin:***@192.168.1.19:8554` → `PLAYING（2874ms）`（**不探测**） |

#### 三个坑（都踩过，必须留注释）

1. **生成名回调必须留在文件作用域**。`INIT_UI_EVENT_BINDINGS` 在**全局作用域**声明
   `onButtonClick_BtnCamPwdOk` 等；把它们定义在匿名 namespace 里会变成**另一个实体**
   ⇒ 要么链接错，要么在全局作用域调用时**同时命中两个声明 ⇒
   `call of overloaded ... is ambiguous` 编译失败**。
   ⇒ 解法：逻辑写成普通 helper（`camLoginOpen/camPwdCancel/camPwdSubmit`，放匿名空间），
     文件尾只放三行"转发"；触摸分发放进匿名空间的 `camPwdTouch`（内层声明隐藏外层声明）。
2. **`@` 与 `:` 在凭据里是安全的，`/ ? # %` 不是**。URL 用**最后一个 `@`** 分隔 userinfo 与主机、
   用**第一个 `:`** 分隔账号与密码 —— 实测 `rtsp://admin:ab@1@192.168.1.19:8554` 能通。
   但 `/` 会让 authority 段提前结束、`?`/`#` 会被当成 query/fragment、`%` 会被当转义前缀
   ⇒ 这几个**明确报错**（`账号里不能有 / ? # % :；密码里不能有 / ? # %`），
   **绝不静默失败**（"密码明明对却连不上"是最难查的一类问题）。
   ★ 顺带一个**打码漏字符**的真事故：`camMaskUrl` 一开始用**第一个** `@` 定位，
   于是 `admin:ab@1@ip` 被打成 `admin:***@1@ip` —— **密码尾部的 `1` 露出来了**。
   必须按"authority 段内**最后一个** `@`"定位（与 ffmpeg 的解析规则一致）。
3. **弹窗窗口 `touchable` 必须保持 false，按钮就得按坐标手动分发** —— 与 wifi 页同一个血案，
   坐标必须与 `ui/camera.html` 的控件盒逐个对齐（`y < 424` 让给键盘）。

#### QA（`/tmp/pg_camcmd`，免触摸验收）

`camlogin` 开弹窗 · `campwd <账号> <密码>` 直接写进两个输入框（密码可含空格）·
`camok` 点「保存并播放」· `camcred <账号:密码>` 跳过弹窗直接带凭据探测 · `camfile` 打印
`/data/camera.txt`（口令打码）。配合 IME 的 `/tmp/pg_imecmd`（`k <键号>`/`done`/`lbl`）
可以**真的用键盘打字**来验收。

（`mount -t squashfs /dev/block/mtdblock3 /res` → `Invalid argument`，`/proc/mounts` 里没有 res），
应用回落到根分区里的出厂版本。
⇒ **`tools/upgrade_device.sh` 第 4 步等的"zkgui pid 变化"只证明"应用重启了"，
不证明"mtd 写完并且 squashfs 校验通过"**。刷完要再等几秒并**确认 `/res` 正常挂上**
（`cat /proc/mounts | grep res` + `ls /res/lib/libzkgui.so`）再重启或断电。
补救很简单：**重新刷一次**（本次重刷后 `/res` 立即恢复正常，数据分区 `/data` 未受影响）。

## 8. 2026-09-19 追加：表盘"压扁"与"圆倒角透明"（含一次自伤事故）

### 8.1 压扁 = **大半径浅弧**，不是把圆压成椭圆

用户第二轮反馈：「表盘盖住了其他控件：控制按键、电台时间都被盖住了」。
真机逐像素复核：时间带 7200 个像素里只剩 **5 个青色**（整带均色 = 面盘浅黄）⇒ 确实被盖没。

**布局预算**（`ui/radio.html` 的硬边界，已写进 `tools/gen_vu_art.py::check()` 当断言）：

    已播时长 424..454 ┊ 总电平条 454..462 ┊ **仪表区 464..620** ┊ 控制键 620..724

面盘 **226x226 @y=408** ⇒ **226x128 @y=468**；读数窗挪到面盘下方 597..618。

★★ **压扁不能把圆压成椭圆**：指针是"整张图绕铰点转"，**刻度弧必须是正圆**。
真表"扁"靠的是**大半径浅弧**：把铰点挪到面盘**下边缘之外**（`PIVOT=(117,142)`，盘高只有 128）、
半径加到 110 ⇒ 盘内只露出弧的顶部一段。两条不能破的等式：**圆心==铰点**、**针长==弧半径+3**。

★ 半径上限被"指针图是方图、盒宽 = 2(R+7)"卡死：两只并排时 `NEEDLE ≤ 242`，
否则右盒到 x=500 > 480（`check_bounds` 判越界；`data-x` 为负还会被框架**钳成 0** 导致指针错位）。

### 8.2 圆倒角**必须真裁 alpha**（用户第三轮反馈：四角方块不好看）

现象与真因：表盘 PNG 是**不透明矩形**，圆角只是**画上去的一圈边框** ⇒ 边框之外四个角仍是面盘色。
修法 = 出 **RGBA** 并把角 `alpha=0`。三处缺一不可：

| 要点 | 做法 | 少做的后果 |
|---|---|---|
| 裁 alpha | `face.putalpha(round_mask(w,h,CORNER))`，遮罩 4x 超采样缩回 | 四角是面盘色的方料（就是这次的问题） |
| 缩回用 **`Image.BOX`** | 面积平均、无过冲 | 用 LANCZOS 会在形状外飘 `alpha=3` 的淡像素 ⇒ `check_assets`「幽灵像素」**FAIL（实测 32 处）** |
| 全透明像素 **RGB 也清零** | `face.paste((0,0,0), mask=α==0)` | `check_assets`「透明区污染」**FAIL（实测 136 px）** |
| 样张贴图带 mask | `dst.paste(face,(x,y),face)` | 样张四角又变回色块 |

**真机判据**（`docs/shot_vu_corner_compare.png` = 改前/改后 + 角部 6x）：

| 判据 | 改前 | 改后 |
|---|---|---|
| 两表 8 个角 | 面盘色 (255,250,226) | **(0,0,0) 透明** ✓ |
| 左上角对角线 `(x+d,y+d)` | 全面盘色 | d=0/2 透明 → d=4 **(54,52,48) 边框色** → d≥6 面盘 ✓ |
| `check_assets.py` 六项 | — | 全过 ✓ |

### 8.3 两个"检查工具骗人"的坑（都是这轮踩到的）

1. **`tools/vu_angle.py` 必须把命中限制在面盘矩形内**：指针色 (30,26,20)±12 是"很暗的暖黑"，
   **按钮面 (22,22,24)、导航栏 (28,28,30)** 全在容差里。铰点在盘内时撞不到；
   扁盘把铰点挪到盘外后，搜索盘罩住按钮那排 ⇒「每个角度覆盖率都 100%」、回读飞到 **−86°**。
   ⇒ **判据要同时限"色"和"位"**。工具准不准要拿**离线样张**全量程标（本工程 5 点 ≤0.4°）。
2. **`tools/check_overlap.py` 曾经整页漏查**：递归遇到"自己带 `position` 的容器"就不再往下走，
   而本工程控件全在 `window__N` 里 ⇒ radio 页 54 个控件**一个都没比过**，却照样输出"没问题"、
   退出码 0（表盘盖住时间就是这么漏掉的）。修好后同页从「1 组 2 个」变「4 组 / 54 个成员」，
   立刻报出那两条。判据：**"容器自身是控件" ≠ "它没有子控件"**；
   **任何"检查通过"都要先用已知案例证明它真会报**。

### 8.4 ⚠️⚠️ 自伤事故：**升级过程中重启设备，把 res 分区擦成了空白**

**这是我自己造的**：为了修"判据窗口内读到旧值 ⇒ 误报固化失败"，我在
`tools/upgrade_device.sh` 里加了『重触发不成就 reboot 再验』。那次 reboot 正好插在
**擦写 res 分区**的中间 ⇒ `mtd3` 被擦成 0xFF、新镜像没写进去 ⇒ `/res` 挂不上
（`/proc/mounts` 里没有 res、`ls /res` 空）、应用连 `libzkgui.so` 都加载不了
（**进程活着但画面冻在最后一帧、所有 QA 通道都不轮询**），而升级处理本身又在应用里 ⇒ **死锁**。

⚠️ 更该批评的是：**同一类事故在 §6.9 已经记过了**（"刷完不要立刻 reboot"），我这轮又犯了一次。

**正确做法（已在脚本里改正）**：
- 升级 res 的过程是「**卸载 → 擦除 → 写入 → 挂回**」，全程 **4~5 分钟**，
  期间设备也可能自己重启（adb 报 `device not found`）。⇒
  判据循环要 ①等设备回来 ②**等 `/res` 挂回来** ③再比 md5，窗口给到 6 分钟；
  **绝不要用"重启一次再验"来提速**。
- 判据比 **md5** 而不是字节数：只改素材不改 C 代码时 `.so` 尺寸完全相同，比字节数会**假通过**。
- **正规解法就是"再走一遍升级流程"**（用户口径）—— 别手工 mount、别手工 dd（那是我情急之下的应急手段，
  虽然确实把 squashfs 从 `update.img` 偏移 32 处切出来 dd 回去了、回读 md5 一致，但不该当常规流程）。
