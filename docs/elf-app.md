# 小精灵（桌面小精灵 · 实拍素材）· 实现与实测

> 需求（2026-09-18 用户）：「我在 pet 目录下放了两个视频。你看裁剪一下区域放到电子宠物里面？
> 我感觉效果更好。或者在做一个小猫 APP」—— 用户当面选定三条：
> **① 新建一个 APP**（现有"电子宠物/机器人"一字未动）；**② 主体是"小精灵"**；
> **③ 场景做成"桌面"**（木纹 + 台灯暖光 + 暗背景）。

## 0. 一句话结论

素材是**用户给的实拍片段**（黑底 + 固定机位），用 `tools/gen_elf_from_video.py` 抠像烘焙成
**25 张 214x253 的 RGBA 贴图**（待机 10 + 走路 10 + **进场 5**）+ 1 张桌面场景 + 1 张阴影；运行时是一个**画布应用**
（`src/core/PgElf.cpp`，slot 34，不新建 ftu），行为和电子宠物同类但更轻：
待机自己在桌上溜达/跳、25 秒没人理就睡着、触摸逗它、整点打招呼、**开场与偶尔从屏幕左边缘外「走进来」**（见 §2b）。
**它是"环境页"**（`isFlipPage() = true`）⇒ 也吃"挂绳倒挂"的整屏翻转（短按 C 键）。

## 1. 先说视频里有什么（全部量出来的，不是看出来的）

两个片段都是 **1280x720 @24fps、5.09s、121 帧、固定机位、纯黑背景**（背景亮度均值 0.1、标准差 0.3
⇒ 已经是"抠好的分割片段"，不用做复杂抠像算法）。逐帧量下来：

| 片段 | 内容 | 依据 |
|---|---|---|
| `desk-pet-seg1.mp4` | 小精灵**从画面左边飘进来、平移约 400px 后站定** | 质心 x 从 184 → 647；把上一帧按质心对齐后 IoU 仍 0.8~0.9 ⇒ **以整体平移为主**，形变不大 |
| `desk-pet-seg2.mp4` | 站定之后的**待机**（几乎不动） | 静止像素占比 79.5%；帧间运动量最大 0.11（seg1 是 0.78） |

另外两条**必须知道的事实**：

- **右下角有个固定水印**（圆角框徽标，两段 242 帧里亮像素数恒为 1096~1104、峰值亮度 51）
  ⇒ 裁剪/抠像时必须抹掉，否则每帧右下角会挂一个方块。
- ★★ **主体有时会被画面边界切掉** —— 这条比看上去重要得多：
  seg1 的 **源帧 16~34 主体的 bbox 左沿 x0 = 0**（实测），也就是那几帧的身体
  **有一半在画面外**（它正从左边走进来）。逐帧看 x0：`0,0,...,0`（16~34 帧）→ `9,27,43,59,...`（35 帧起）。
  ⇒ ① **走路动画绝不能取这几帧**（否则走路循环里会闪出"缺半边"的身体，用户 2026-09-18 报的就是它）；
    ② 它们反而是**唯一**能表达"从屏幕边上走出来"的素材（见 §2b）。

## 2. 抠像与烘焙（`tools/gen_elf_from_video.py`）

```
亮度阈值抠底（>18） → 抹水印 → 填**内部**洞（从画布四边泛洪标"外面"，剩下的暗块才是洞）
→ MinFilter 内缩 2px（源片边缘混了黑底，不内缩会留一圈黑边）→ 高斯羽化 1.8px
→ **一次统一缩放** 0.4208（BOX，面积平均）→ 对齐进固定画布 214x253
   （常规帧的锚点 = **可见部分的**脚底水平中心；进场帧见 §2b —— 那是另一套锚点）
```

**统一缩放是硬要求**：逐帧各自归一化会让"呼吸"变成"整体缩放"（看着像在喘大气）。
本项目自检：`idle` 帧主体高度波动 **3.8%**、`move` **3.4%**、`enter` **1.7%**。

★★ **时基与走速必须成对，而且现在由生成器反推后写进 `PgElfArt.h`**（C++ 里不再手抄）：

| 常量 | 值 | 怎么来的 |
|---|---|---|
| `kElfMoveFrameMs` | **102** | 走路帧取自源帧 38~60 等间隔（2.44 源帧 / 24fps） |
| `kElfWalkSpeed` | **143 px/s** | 相邻取样帧之间主体整体平移 **34.7 源px**（用**列占用曲线互相关**量，
不是 bbox 左沿 —— 左沿会随手臂/腿抖，实测相邻帧 4~28px）⇒ 14.18 源px/源帧 ×24fps ×0.4208 |

判据：**帧间隔 × 走速 == 素材里的实际位移** ⇒ 脚才不打滑（改一个必须一起改，重跑生成器即可）。
⚠️ 反过来算：帧间隔大了 / 速度小了，就会"脚在地上滑"（上一版 208ms + 104px/s 其实偏慢 20%）。

**为什么烘帧而不是播视频**：本板有 H.264 解码，但视频走**独立 disp 层**（不透明、不能叠加，
见 `docs/disp-layer.md`），而本页要把小精灵贴到桌面场景上 ⇒ 必须带 alpha ⇒ 只能烘帧 + 画布合成。

**产出**（`resources/images/game/elf/`，1.5MB）：

| 文件 | 尺寸 | 说明 |
|---|---|---|
| `idle_00..09.png` | 214x253 ×10 | 待机（**乒乓播放**：源片首尾并不重合，乒乓能保证接缝不跳） |
| `move_00..09.png` | 214x253 ×10 | 走动（**主体完整**；配合运行时水平位移） |
| `enter_00..04.png` | 214x253 ×5 | ★ **进场**（"从屏幕最左边走出来"，见 §2b）—— 身体天生缺半边 |
| `desk.png` | 480x540 | 桌面场景（木纹 + 台灯暖光，**不透明** ⇒ 走 memcpy 快路径） |
| `shadow.png` | 140x30 | 脚底阴影（单独一张：跳起来时影子不跟着飞） |

清单头 `src/core/PgElfArt.h` 由同一个脚本生成（含锚点 `(107,241)` 与上表两个常量）。

## 2b. ★★ "从屏幕最左边走出来"（用户 2026-09-18 报"身体缺半边"后做的）

用户原话：「move 00 这个图片的位置要定位到屏幕最左边的位置，负坐标，他是从边上走出来的。
**不然身体差了半边**。」—— 说得完全对，只是"位置"这件事要拆成两条：

1. **走路动画里不该有它**：`move_00/move_01`（源帧 26/31）正是被画面左边缘切掉的那两张
   ⇒ 走路循环每 5 帧就闪一次"缺半边的身体"。**现在走路帧只取主体完整的（源帧 38~60）。**
2. **它该用在屏幕最左边**：那几张"缺半边"的帧单独做成 `kElfEnter[]`（源帧 17~33 等分 5 张），
   并且**换一套锚点**：
   `水平锚点 = 推算的"完整身体中心" = 右沿 − 完整宽/2`（完整宽取走路帧的中位 461 源px）。
   于是每张帧都有一个"正确位置" `kElfEnterAt[k]`（生成器算好写进头文件）：

   ```
   kElfEnterAt = {-6, 16, 41, 63, 89}      // 画布 x；**第一张是负的**（身体中心还在屏幕左边缘外）
   ```

   ⇒ 运行时把精灵放在这些 x 上：**缺掉的那半边正好落在屏幕外**，看着就是"完整的身体从边上探进来" ✓

**三个实现要点**（都是踩过才定的）：

- **帧号由位置决定，不是时间**（`enterFrameFor()`）：取"位置还没走到、但最接近的那张"
  （第一个 `at[k] ≥ x`）⇒ 帧永远**领先**位置，多出来的部分被**屏幕边**裁掉 ⇒ 可见部分左沿**恒为 0**。
  反过来取"不超过位置的最大值"（第一版）会让左沿在 0→26px 之间**来回跳**（每换档跳一下，走路一顿一顿），
  像素判据抓到了：`左沿 0/4/10/16` vs 改后的 `0/0/0`。
- **起点必须是负坐标**（`startEnter()` 是唯一入口，开场 / QA `enter` / 自动行为"换位置"都走它）。
  ⚠️ 一旦有人在 `reset()` 里手写这几行改成 0 或正数，屏幕里立刻露出一具缺半边的身体。
- **位置优先于相位**（`currentFrame()` 里先判 `elfX_ < STAND_MIN_X` 再判相位）：
  进场被"跳一下/摸头"打断后相位会变成待机/开心，若按相位选帧就会用**完整的待机帧**画在屏幕左边缘
  ⇒ 又变成"缺半边"（验收实测复现过：bbox x[0,86]、中心 43 而不是 240）。
  配套两条自愈：`update()` 里"待机却停在 x<89 ⇒ 继续把进场走完"、`startPet()` 里"进场中不接受互动"。

**走路的左界也跟着抬到了 89**（`WALK_LO = max(EDGE_PAD, STAND_MIN_X)`）：普通走路不往
"身体会被屏幕切掉"的区域走，想贴左边就用进场动画。

## 3. 运行时行为（`src/core/PgElf.cpp`）

| 相位 | 行为 |
|---|---|
| 待机 | 乒乓播 idle 帧（120ms/帧）；每 7~16 秒自己决定"走一段"或"跳一下" |
| 走动 | 朝目标匀速移动（**143px/s** = 素材隐含速度 ⇒ 不打滑），播 move 帧 |
| 开心 | 抛物线跳一下（`hop = 4h·u(1−u)`）；触摸/长按更跳得高（42 / 74px） |
| 睡着 | 25 秒没人理 ⇒ **整屏压暗**（`blendRect` alpha 132）+ 头顶 "Zzz"，一有互动立刻醒 |
| **走进来** | ★ 从屏幕左边缘外（**负坐标** `kElfEnterAt[0] = -6`）走到家位置；帧**按位置**取 `kElfEnter[]`（见 §2b） |
| 换位置 | 淡出（`drawSpriteA`）→ 放到屏幕左边缘外 → **走进来**（素材只有朝右的姿态、画布不能镜像 ⇒ 只能从左进） |

★ 三个入口都走 `startEnter()`（开场 / QA `enter` / 自动行为换位置，1/5 概率），另有两条**自愈**：待机却停在 x<89 ⇒ 继续把进场走完；进场中收到互动 ⇒ 不计数（并打日志）。
★ QA 旋钮 `slow <n>` = 时间流速 ÷n（位移/帧循环/睡觉计时一起变慢）—— **抓进场/跳跃中间帧的唯一手段**
（抓一帧 1~2s，而进场只有 0.66s、走路 143px/s）。

- **触摸命中用"按下"的位置**（手指滑一点就换目标的话，摸着摸着就"跳"了）；点旁边**也算互动**
  （别让"点了没反应"）。
- `isFlipPage() = true` ⇒ 与电子宠物同类：**短按暂停键 = 整屏翻转 180°**（长按仍是返回列表）。
- `stillFrame()` **恒 false**：待机动画与睡觉计时都在推进，报静止会让宿主跳过 `update()`
  （本项目在宠物/找不同上各踩过一次）。

| # | 判据 | 实测 |
|---|---|---|
| ① | 桌面场景 **1:1**（挖掉角色区后与 `desk.png` 逐像素比） | 平均差 **0.07** |
| ② | 角色在场且站位对 | bbox x[149,331] **中心 240**（家 240）、脚底 y=431（432±14） |
| ③ | **待机动画在动**（同局隔 1.1s 抓两帧） | 角色区内 **18441** 像素变化（>300） |
| ④ | 走动 | 1.6s 后中心 x 240 → **380**（>60px） |
| ⑤ | **跳跃离地** | 跳跃帧 bbox 下沿 **359**（静止 430）⇒ 脚离地 71px |
| ⑥ | 睡着压暗 + Zzz | 整屏亮度 57.6 → **32.8**；Zzz 区亮墨迹 0 → **196** 像素 |
| ⑦ | 触摸互动（`pginj` 真注入） | 互动计数 0 → **1**（日志同时有 `touch: action=1/2` 与「点到它身上」） |
| ⑧ | 资源与内存 | 贴图 **27 张** / 6316KB / 失败 0（上限 40）；MemFree **4.2MB** |
| ⑨ | ★ **从屏幕左边走进来**（配 `slow 10`） | 三次采样的墨迹**左沿全是 0**（贴着屏幕左边）；
可见宽度 **90 → 97 → 104**（从一小片逐渐展开，完整是 194）；最终 x=240 |

★ ③⑤ 这两条是必须的：**静态截图看不出「它在不在动」**，而跳跃只有 900ms——
抓屏一次要 1~2s，**不把状态做成稳态就永远抓不到**（为此加了 QA `hoploop <n>` 连续跳；
进场那段只有 0.66s，则用 `slow <n>` 把时间流速放慢）。

★ ⑨ 的判据**刻意做成时间无关的**：「负坐标」那一瞬只有 0.4s，抓帧根本追不上
（第一版就是这么假失败的）。改成「第一次采样应是贴着左边的一小片（宽 90 < 130）、
随后逐渐展开」——这同样只可能在缺的半边落在屏幕外时成立，而且**不受抓帧耗时影响**。

## 5. 这一版踩到的坑（都值得记）

1. ★★ **`enterPhase()` 会复位 hop 相关的量，`startHop()` 必须"先切相位、再写本次时长/高度"**。
   写反了 ⇒ `hopMs_` 立刻被清 0 ⇒ 下一拍就判"落地"：日志里明明有 `-> 开心`，画面**根本不跳**。
   这类 bug 静态截图完全看不出来（正好抓在落地那一刻），只有"跳跃帧脚底必须离地"这条像素判据能抓。
2. ★★ **QA 命令的前缀匹配**：`hoploop 8` 被前面的 `strncmp(rest,"hop",3)` 截走 ⇒ 只跳一次、
   循环永不生效（现象：回显正常、确实跳了一下，但抓不到空中稳态）。**长命令要排在短命令前面**。
3. ★★ **QA 通道"内容不变就不执行"** ⇒ 验收脚本里连发两条相同的 `gdbg state`，第二条被静默忽略，
   读到的还是旧状态（表现为"计数没变"的假失败）。脚本里所有 QA 命令统一带自增序号。
4. ★★ **验收脚本的前置步骤必须"发完回读确认"**：应用被重进后 `auto` 会被复位成 on，
   整轮都在"自动行为开着 + 已睡着"的状态下跑 ⇒ ③⑦ 集体假失败。现在 `setup()` 会回读
   `自动=`/`睡着=` 并重试。
5. ★ **环境页会被"物理按键"翻转**：小精灵 `isFlipPage()` ⇒ 人手按一下 C 键整屏就翻 180°，
   而验收脚本控制不了人手 ⇒ 抓到的帧是倒的（bbox 覆盖整个画布）。脚本现在每次抓帧前
   幂等发一条 `flip off`。（这一条反过来也证明"环境页 + C 键翻转"在真机上生效。）
6. ★ **日志解析要锚定 + 倒序找**：日志里还有 `距上次互动=13773ms`、`PocketGame touch: x=240`，
   用 `.*互动=` 会把它当成互动次数（实测把 13773 当成了计数）；`re.search` 命中的是窗口里**最旧**那行
   ⇒ 必须 `reversed(logfile.splitlines())`。
7. ★★ **位置要优先于相位**：进场途中被跳一下打断后相位会变成待机/开心，若按相位选帧，
   就会拿**完整的待机帧**画在 x<89（屏幕左边缘）⇒ 屏幕里露出一具缺半边的身体。
   改前/改后都在真机上量到了：`bbox x[0,86]、中心 43`（错）→ `中心 240`（对）。
8. ★★ **宿主的「进应用」路径会补发一次互动键**（`mainLogic` 里 `34 1` 之后紧接 `onKey(PG_KEY_A)`）
   ⇒ 每次进应用都把开场进场打断在 -6。修法：互动的**唯一入口** `startPet()` 里加
   「进场中不接受互动」（并打一行日志，不做静默）。
9. ★ **`re.search` 匹配的是日志窗口里最旧的那条**：验收 ⑨ 第一版读到的是上一步的 `x=240`，
   看起来「进场压根没发生」。必须 `reversed(lines)` 取最后一条（这条在屏保翻转验收里也踩过，
   属于同一个人会踩第二次的坑 ⇒ 已抽成 `last_state_line()`）。
10. ★ **`gdbg sleep` 这类「强制」钩子不该被「自动行为开关」挡住**：第一版把睡眠守卫和自动行为写在一起，
   于是 `gdbg auto off` 之后强制入睡永远没反应（假失败一轮）。现在拆成 `goSleep()`
   （自动与 QA 共用），开关只挡"自己动一下"。

## 6. CPU 与内存（固化版实测，照实记录）

**同一场会话里的 A/B**（`/proc/<pid>/stat` 的 utime+stime 差分，8s，HZ=100）：

| 页面 | 8s jiffies | ≈CPU |
|---|---|---|
| 菜单（MODE_MENU） | 16 | **2%** |
| **电子宠物（MODE_GAME）** | **793** | **99%** |
| **小精灵（MODE_GAME）** | **794** | **99%** |

⇒ **凡 MODE_GAME 的画布页都是 ~99%**（宠物与小精灵完全同档）⇒ 这是本工程既有的
"画布页"水平，**不是本次改动引入的**。

**那 99% 花在哪**（固化版 `bench`，2 秒统计）：

```
bench 129 帧  每帧均值 update=23us render=494us present=10us 整个回调=809us（帧间隔≈15566us）
Elf: 画面门控 实画=593 跳过=2355（跳过率 80%）
```

- 本页自身的每帧成本只有 **809us / 15566us ≈ 5%**，而且**画面指纹门控跳掉了 80% 的帧**
  （静态时同一张帧不重画）⇒ 瓶颈**不在** `render()`。
- 剩下的大头在**框架的"整块画布推屏"**：宿主每帧 `present()` 会做
  `tv->setInvalid(!tv->isInvalid())`，框架就把整块 480x540 画布（≈1MB）重传到屏 ——
  这一份开销与"页面上画了什么"无关，宠物页一模一样。
- ⇒ **要省电/降温得改宿主**（不是本页的事）：① 画面没变就不 `present()`
  （把本页的"指纹门控"结果告诉宿主）；② 给 `MODE_GAME` 加"每游戏主循环频率"钩子
  （环境页 30fps 足够）。两条都是独立课题，本次**没做**。

**内存**：贴图 **27 张 / 6316KB / 失败 0**（上限 40）；开着小精灵页时 MemFree **4.1MB**、
MemAvailable 22MB。⚠️ 这是本工程目前**最吃内存的一页**（贴图 6.3MB + 场景 1MB）
⇒ 要给别处腾内存，先把进场帧从 5 张减到 3~4 张（视觉上只差「展开」的细腻度）。
