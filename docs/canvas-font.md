# 画布字库：原生多档 + 灰度覆盖率（2026-09-15 · v1.17.0）

> 用户诉求：「内嵌的文字改成 32×32，或者直接用控件做；整体太粗糙，**所有东西不能做拉伸**，
> 要边缘平滑、不能有锯齿。」
>
> 结论：**画布文字全部改成"按目标像素原生栅格化 + 灰度抗锯齿"**，档位含义不变
> （调用点一行没改），并把"不许拉伸"落成一条可执行的检查（`tools/check_stretch.py`）。

## 1. 旧实现错在哪（两个病，都直接违反用户的要求）

`src/core/PgFontData.h`（生成器 `tools/genfont.py` v1）只烘了**三套 1bit 点阵**：
ASCII 8×12、大号数字 16×24、中文 16×16。调用点传 `scale=1..5`，绘制时把**每个点阵像素
放大成 `scale×scale` 的实心方块**：

```cpp
// 旧 drawGlyph：中文分支
if (scale == 1) px(x + gx, y + gy, c);
else            fillRect(x + gx * scale, y + gy * scale, scale, scale, c);  // ← 拉伸
```

- **病一：拉伸。** `scale=2` 的中文 = 16×16 放大到 32×32，每个原始像素变成 2×2 色块；
  `scale=5`（游戏标题 80px）就是 5×5 色块 —— 笔画边缘全是台阶。
  **"放大"在这套渲染里就等于"拉伸"**，这正是用户明确禁止的。
- **病二：没有抗锯齿。** 1bit 只有"有墨/没墨"，斜边（撇、捺、圆角）只能是硬边。

**实测证据（离线按两版算法渲染同一个"五子棋"，显示尺寸都是 32px）**：

| | 灰阶种类 | 结构 |
|---|---|---|
| 旧（1bit + 放大 2×） | **1**（纯黑白） | 每个像素都是 2×2 方块 |
| 新（原生 32×32 + 4bit 覆盖率） | **144** | 边缘是连续覆盖率 |

真机同屏对比（五子棋遮罩层文字区）：

| | 灰阶种类 | 2×2 同色块比例 |
|---|---|---|
| 旧 | 5 | 94.4% |
| 新 | 39 | 29.5%（剩下的都是笔画内部整块，正常） |

## 2. 新实现

### 2.1 数据格式（`tools/genfont.py` → `src/core/PgFontData.h`）

| 字集 | 基准（N=1） | 档位 N | 每档字格 |
|---|---|---|---|
| ASCII | 8×12（consola 13px） | 1..5 | 8N × 12N |
| 大号数字 | 16×24（consola 26px） | 1..3 | 16N × 24N |
| 中文 | 16×16（simhei 16px） | 1..5 | 16N × 16N |

- **每一档都是"按目标像素数原生栅格化"**：`ImageFont.truetype(size = 基准 × N)`，
  字形直接画在 `字格 = 基准 × N` 的图里，绘制时 **1:1 贴像素**，不做任何缩放/插值。
- **字格尺寸 = 基准 × N** ⇒ `textW / textH / lineH` 与旧版完全相同，
  **所有页面的排版位置不变**（这是"改渲染不改布局"的关键）。
- **覆盖率 4bit/像素**（16 级，行内高位在左），绘制时 `blendPx(x, y, c, q * 17)`
  混合；`q == 15` 走 `px()` 快路径。
- 档位上限：`PG_FONT_MAX_N = 5`（文本）、`PG_FONT_BIG_MAX_N = 3`（大号数字 ——
  它的 scale 来自 `fitBigText(maxScale ≤ 3)`，再大就是放大，代码里已封顶）。

### 2.2 内存/体积（这是必须付的代价）

| 项 | 数值 |
|---|---|
| 点阵数据 | **553.6 KB**（4bit；中文@32 是最大头，333 字 ≈ 167 KB） |
| 生成的头文件 | 2.25 MB（`\xNN` 字符串字面量，编译器解析快） |
| `libzkgui.so` | 3.47 MB → **4.02 MB** |

⚠️ **`fun launch` 是调试推送**：库落在 `/tmp`（tmpfs，**每字节都占 RAM**），
所以开发期这 550KB 是实打实的内存开销；固化（`fun pack` + 刷机）落 `/res`（squashfs）就不占了。
真要缩：中文只在**被用到的档位**收**被用到的字**，调 `genfont.py` 的
`EXTRA_CJK` / `max_len` 阈值即可（`--check` 会打印每档字数与体积）。

### 2.3 按档收字（体积控制的核心）

字库是**子集**，收字规则（都在 `tools/genfont.py`）：

1. **字面量实参**（`c.textCenter(W/2, y, "五子棋", 5, ...)`）→ 直接收 `"五子棋"` 在 N=5 这一档。
2. **非字面量实参**（`b` / `buf` / `btns[i].t` —— snprintf 结果或表格里的串）→ 收
   **该文件里所有"短字面量"（≤14 字符；大字档 ≤8）** 作为保守超集。
   实测：取"全部字面量"会让中文@32 从 333 字涨到 611 字（+130KB），
   而画布上会画出来的文案都是短语，长的都是日志/URL。
3. **宿主代画**（`mainLogic.cc` 画软按钮，标签来自 `gGame->softButtons()`）
   → 收"**全部游戏短字面量的并集**"。比"该文件的字面量"精确得多
   （mainLogic 里有 345 个中文日志字根本不会上画布）。
4. **扫描要排除 `PgCanvas.cpp`**：它是实现，内部的 `textCenter→text` 转发调用不是"需求"，
   统计进来会把该文件全部字面量算成画布文案。
5. `EXTRA_CJK` 白名单（"继续重来退出暂停…"）只加在 **N≤2** 档（高位档一个字 3KB+，
   加 46 个就是 150KB）。

### 2.4 缺字是"可验收"的（不再静默）

画布缺字的两种表现：**跨档回退**（该档没收但别的档有 → 1:1 画在本档字格正中，字号不对但不消失）、
**缺字方框**（全档都没有）。两者都计数，QA 命令一条就能查：

```
glyphmiss            # 打印统计 + 最近 16 个缺失码点
glyphmiss reset      # 清零（便于"进某个游戏前后"对比）
```

实测（把 13 个画布游戏逐个进入 + 交互后）：

```
PocketGame: glyphmiss miss=0 fallback=0 (字库完整)
```

**改了画布文案的流程**：改 `src/core/*.cpp` 的字符串 → `python tools/genfont.py`
→ `./fun.exe build` → `fun launch` → `glyphmiss` 确认 0。

### 2.5 ★ 每档"自动对位"（不这么做会**裁掉笔画**）

原生栅格化的墨迹尺寸**不是线性的**：中文 16px 时墨迹正好 16 行，32px 时要 33 行。
如果照搬 `oy = base_y × N`（`-1 × N`），字号越大越会**把顶部裁掉**：

```
未对位时（实测）  中文 N=1 上沿 -1px   N=2 -1px   N=4 -2px   N=5 -3px
                  ASCII N=4 上沿 -6px（'%' 的顶部被切掉 6px！）
```

所以生成器给每一档先算一组 `(dx, dy)`（`fit_offsets()`）：

- **竖直**：整体下移 `-min(0, 墨迹上沿)` ⇒ 最高字从第 0 行开始。
  这**正好也是旧版整数放大的口径**（旧版墨迹上沿也在第 0 行）⇒ 排版位置不变。
- **水平**：能靠平移装下就平移；装不下就**左右对称裁**（绝不单边裁掉一条竖笔）。

对位后复检（生成器每次都会打印 `墨迹上沿 / 越界字形` 两列）：

| | 越界字形 |
|---|---|
| 中文 32 / 48 / 64 / 80px | **0** / 0 / 0 / 0 |
| 中文 16px（字格刚好等于墨迹高） | 25 个各 1px（不可避免） |
| ASCII | 1~15 个各 1px（`(`/`)`/`\|` 这类极端字形） |
| 大号数字 | 0 |

> 判据：**>1px 就要查**。1px 是"字格尺寸固定、字形本来比字格高一点点"的物理极限。

## 3. "不许拉伸"落成三条可执行规则

用户要求"所有东西不能做拉伸"。除了字库，还有两处：

| 位置 | 做法 | 执行者 |
|---|---|---|
| **静态背景图**（JSON 的 `backgroundPic`/`picTab`） | 图尺寸**必须严格等于**控件尺寸。不等 ⇒ 框架自己缩放 ⇒ 拉伸。九宫格 `.9.png` 例外（marker 边就是给拉伸用的） | **`tools/check_stretch.py`**，由 `gen_ui.py` 在生成后自动跑 |
| **运行时改尺寸的控件**（电量条 BattFill） | 不能"一张满格图 + 运行时改窄"（圆角端会被横向压扁）⇒ `tools/ios_theme.py` **按宽度各烘一张**（`batt_fill_<色>_<宽>.png`，3 色 × 40 宽 = 120 张小图） | `ios_theme.gen_battery()` |
| **画布文字** | 原生档位 + 1:1 贴像素，永不缩放 | `genfont.py` + `PgCanvas::drawGlyph()` |

`check_stretch.py` 上线当天就抓到一处真实的漏网：电量条改按宽度烘图后，
`ui/main.html` 里 `BattFill` 的**初始静态图名**（`batt_fill_blue.png`）已经不存在了 ——
这类"图没了/尺寸变了"如果没人查，表现就是运行时某处发糊，很难定位。

## 4. 踩过的坑（都是"静默"型）

1. **字符串字面量存点阵要 +1 字节**：C 字符串字面量结尾会隐含一个 NUL，
   数组尺寸按 `len` 声明会报 `initializer-string for array of chars is too long`。
2. **空格的字形不能丢**：生成时如果按"空图就丢弃"处理，空格就会进不了字集，
   运行时 `findGlyph` 找不到 → **每个空格都画一个缺字方框**。空字形必须保留。
3. **扫描器的两个陷阱**（见 §2.3 第 4/5 条）：不排除 `PgCanvas.cpp` 会多收 40 字；
   不区分宿主/游戏会把 mainLogic 的 345 个日志字塞进中文@32。
4. **`textH()` 从"写死 10×N"改成"实测墨迹高"**：N=1 仍是 10（一致），N=2 变 21（旧 20），
   只影响 `textCenterBox` 的 1px 居中 —— 换来的是"度量与真实绘制同源"。
5. **原生栅格化的墨迹尺寸不是线性的**：`oy = base_y × N` 会把大字号档的**顶部裁掉**
   1~6px（中文 N=5 裁 3px、ASCII N=4 裁 6px）。必须每档实测墨迹范围再对位（§2.5），
   判据看生成器打印的"越界字形"列（>1px 就要处理）。
6. **框架文字（ZKTextView）本来就有抗锯齿**，不是问题源：实测主界面标题（26px）
   中间过渡灰阶 **182 种**、14px 应用名 **31 种**。之前"文字过渡只有 4~11%"的结论是
   取样区域/阈值选错导致的误判 —— **判"有没有抗锯齿"要在文字自己的区域量，别把背景算进去**。

| 文件 | 职责 |

| `tools/genfont.py` | 扫描调用点 → 定档位字集 → **每档自动对位** → 原生栅格化 → 4bit 打包 → 写 `PgFontData.h`；`--check` 只自检（每次都会打印每档的**墨迹上沿 / 越界字形数**） |

## 8. ★★ 血案：码点表**非升序** + 二分查找 ⇒ 部分数字"字体有大有小"（v1.18.1）

**用户报障**：「数字华容道的字体怎么有大有小，感觉很奇怪。」

### 8.1 定位（三步，每步都有像素/数据证据）

**① 抓帧量墨迹** —— 同一盘 4×4 里，数字高度出现**两种**：

| | 墨迹 |
|---|---|
| 多数格子 | **32~40 x 50** |
| 少数格子（实测 3 个） | **16 x 25** |

差值正好 **2 倍** ⇒ 先怀疑"档位不同"。

**② 离线查点阵数据** —— 读 `PgFontData.h` 的 BIG@3 点阵逐字符渲染：
`'1'~'9'`、`'0'` 全部是 **32~40 x 50~52**，**字库数据完好** ⇒ 不是字形/生成器的问题。

**③ 查查找函数** —— `findGlyph()` 用**二分查找**（注释写"codes 升序"），
而 BIG 三档的码点表**不是升序**：

```
BIG_C3_CODES = 0x20, 0x30..0x39, 0x2E, 0x3A, 0x2D, 0x2B
               ↑空格  ↑'0'~'9'   ↑'.'  ↑':'  ↑'-'  ↑'+'      ← 后 4 个排在 '9' 之后
```

离线复现二分查找 ⇒ **`7` `8` `9` `.` `:` `-` `+` 这 7 个字符永远查不到**
⇒ 走 `drawBigGlyph()` 的"未收录回退"，改用 **ASCII 档**画（ASCII@3 的墨迹正好 **16 x 25** ✓）
⇒ 同一屏里字号差一倍。**实测掉档的正好 3 个格子 = 盘面里的 7/8/9** ✓ 完全吻合。

### 8.2 为什么数据会非升序

生成器原来写的是 `list(BIG['chars'])`，而 `BIG['chars'] = " 0123456789.:-+"`
—— 按**字符串原顺序**输出，就是上面那个非升序数组。
（ASCII/CJK 档没事：它们本来就是 `sorted(...)`。）

### 8.3 修法（两处，都要）

| 位置 | 改动 | 作用 |
|---|---|---|
| `tools/genfont.py` | `sorted(BIG['chars'])`；并在写文件前加**升序自检**（13 个档位全检，非升序直接打印告警） | **根因**：让数据符合"升序"约定 |
| `src/core/PgCanvas.cpp` `findGlyph()` | 二分失败后**再线性扫一遍**兜底 | **防御**：数据错了也不会静默画错。正常（升序）路径命中二分，**零额外开销**；只有"确实没收录/数据非升序"才走线性 |

> 为什么两处都做：生成器修的是"以后不会再错"，运行时兜底修的是"已经有错的产物也不出错"。
> 二分有个好性质：**命中即返回，所以返回的索引一定正确**，非升序只会"漏"不会"错"
> ⇒ 线性兜底就能补齐，不需要换掉二分。

### 8.4 影响面（不止数字华容道）

任何用 `bigText`/`bigNumber`/`fitBigText` 的地方都受影响，而且**不止数字 7/8/9**：

- **数字华容道**（7/8/9 变小字）← 用户报的这个
- **2048**（方块 8 变小字）
- **时钟/世界时钟的 LED 时间**（`7` `8` `9` 点 + **`:` 分隔符**都变小）
- **番茄钟 / 秒表 / 计时器**（数字与 `:`、`-`）
- 任何用大号数字的地方

### 8.5 验收（真机，逐格量墨迹）

```
BEFORE：16 格里 3 格墨迹 16x25（ASCII 回退），其余 32~40 x 50   ← 差 2 倍
AFTER ：16 格**全部** BIG@3，墨迹 30~39 x 50~52                ← 只剩 1~2px 字形自然差异
```

> ⚠️ 判据要写成"**高度集合的唯一性**"，不要写成"高度完全相等" ——
> 不同数字的墨迹高度天然差 1~2px（`'2'` 51 行、`'3'` 52 行、`'7'` 50 行），
> 这是字体设计决定的，不是 bug。

### 8.6 通用纪律

1. **二分查找 = 对数据有序性的硬约束**。凡是"生成器产表 + 运行时二分"的组合，
   生成器**必须排序**，而且**要有自检**（非升序是**静默故障**：不报错，只是查不到）。
2. **子集字库的字符顺序取决于构造方式**：从字符串字面量来（`" 0123456789.:-+"`）
   就**不是**升序 —— 别被"看起来是按类型排的"骗了。
3. 改动"查表失败后的回退策略"要当心**回退路径本身的观感**：
   本项目回退到 ASCII 档是合理的（保证不消失），但代价是**字号明显变小** ——
   正是这个"合理回退"把"查找 bug"变成了用户可见的"字体有大有小"。
   **排查时看到"同一批元素尺寸分两档"，优先怀疑"有一批走了回退路径"。**
