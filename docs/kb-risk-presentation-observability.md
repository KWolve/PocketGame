# 探测类功能「用户看得懂」的可观测性设计 + 风险分级纪律 + 注入式验收

> 🔍 **检索导引（命中条件）**：用户说「**扫出来很多数据，但不知道哪个是目标 / 哪个有问题**」
> 「**界面看不出来风险 / 结果没法一眼看懂 / 不知道怎么用**」「**怎么把可疑的排在最前面**」
> 「**列表按什么排 / 能不能只看有问题的**」「**误报太多 / 智能设备全被标成可疑 / 噪声淹没重点**」
> 「**关键词判定太宽 / 短词误匹配 / 名字里带某个词就被判可疑**」
> 「**扫描类功能怎么验收 / 环境里没有可疑设备怎么测 / 判据没法复现**」
> → **本篇就是答案**。适用：任何**扫描/探测/检测**类页面（设备发现、风险扫描、体检、嗅探、资产盘点…），
> 不限于无线场景。1~4 节是平台无关的方法论，5 节给出 FlyThings 的具体实现落点。

## 一句话

**"功能能跑"和"用户能用"是两件事**：判定逻辑全部正确、自检全过，用户仍然会说
*"扫出来很多数据，但不知道谁是摄像头"* —— **成败在呈现，不在判定**。
四条固定做法：**① 列表按风险排序（只做视图映射）② 「只看风险」筛选 ③ 行首色条 ④ 汇总卡点名**；
外加两条纪律：**分级按证据强度（泛词降级 + 短词词首匹配）**、
**验收必须可注入（否则环境里没有目标时判据根本不存在）**。

## 0. 先分清两类问题（别一上来就加判定规则）

| 用户的话 | 真实问题 | 该做什么 |
|---|---|---|
| "扫出来的**不准** / 明明是摄像头却没报" | **判定**问题 | 加特征 / 加证据源（协议指纹、端口、OUI…） |
| "扫出来**很多数据，不知道谁是**" | **呈现**问题 | **本节 1~4 节**：排序 / 筛选 / 色条 / 点名 |

⚠️ 血案：某探测页判定库自检 **19/19 全对**、端到端能认出构造的假目标并给出最硬证据，
用户仍反馈"不知道哪个是"。此时**继续加判定规则收益为零** ——
要先把已有结论**搬到用户眼前**。

**判据自身的表达也算呈现**：判定枚举（`level` + `why`）必须**足够宽**能完整显示。
血案：原因列只有 `100px / 11px` 字号，"视频流可直读"这类判据被截断 ——
**判据就是答案，被截断等于没答案**。

## 1. 四条呈现做法

### ① 列表按风险排序（风险高的永远在最上面）

- 规则：**风险降序 → 同风险按"用户熟悉的稳定键"升序**
  （设备表按 IP、AP 表按信号强度、文件表按路径…）
- 排序**必须在"就绪那一刻"就排好**，不能等用户点一下才排

★★ **只做"视图映射"，绝不重排底层数组**。这是本节最重要的一条：

- 行点击 / 深探 / 锁定目标**都按"列表下标"定位对象**，
  一旦重排底层数组，点第 3 行会操作到**另一个对象** —— **而且不报错**（最阴的一类 bug）
- 正确做法：底层保持原样，另存一个**下标数组** `order[]`；
  对外暴露 `item(i)` = `底层[order[i]]`，**列表显示 / 调试 dump / 点击定位全部走它**，
  三者天然一致
- 列表被筛选过时同理：点击回调必须**先映射回真实下标**再动作
- 排序结果要**缓存**（带一个"已排到哪一代"的标记，数据变了才重排），
  否则每次取一行都排一遍

### ② 「只看风险」筛选（一键把噪声滤掉，剩下的就是答案）

- 放在**列表与底部操作之间**；两态按钮：未开启（次级色）↔ 开启（强调色 + 文字变"显示全部（N）"）
- **门槛取"可疑及以上"**：最弱的"关注"级通常是泛词命中，属噪声，**不进筛选**
- 文案带上数量：`只看风险设备（2 台）` —— 用户不看列表也知道有几个
- 同样只做视图映射；**空结果要有提示**（"筛选下没有风险设备（共 N 条）"），
  否则用户以为扫描失败
- **布局放不下时先找空隙**：血案项目里"列表底 652 / 按钮顶 696"之间正好 44px，
  放一条 38px 的筛选条，**不动任何现有坐标**（改坐标要连带改 5~10 个控件的 x/y，风险高得多）

### ③ 行首色条（一眼扫过就知道哪行值得看）

- 配色分档：**高危红 / 可疑金 / 关注弱灰 / 普通 = 与行卡同色（视觉上隐形）**
- 宽度 4~6px、竖直居中即可；**不要做成整行变色**
  （行卡底多半是九宫格圆角图，运行时改底会破坏圆角，见 `../uicontrols/nine-patch-rule.md`）
- ⚠️ **色条不挂圆角图**：5px 宽的小控件挂九宫格会画出怪边；
  只设底色 + 状态色即可（多数框架里"只设底色看不到变化"，要**同时**设状态色）

### ④ 汇总卡"点名"（三行：结论 / 点名 / 下一步）

| 行 | 原来（统计口径，用户看不懂） | 改成（结论口径） |
|---|---|---|
| 第 1 行 | `在线 5 台设备` | `⚠ 高危 1 台疑似摄像头`（有风险时**优先报风险**，颜色跟随等级） |
| 第 2 行 | 网络信息 | **点名**：`<目标IP> · 视频流可直读 · 高危`（不用滚动列表就知道是谁） |
| 第 3 行 | 无 | 下一步动作：`列表已按风险排序 · 点下面「只看风险设备」只看它们` |

★ "点名"取**排序后的第一条风险记录**（排序已保证它最可疑），零额外计算。
★ 无风险时给**正反馈**（`在线 5 台 · 未发现可疑`，绿色）—— 否则用户不确定"是不是没扫出来"。

## 2. 风险分级纪律：按**证据强度**，不按"可能相关"

| 级 | 放什么 | 例 |
|---|---|---|
| 高危 | 名字/证据里**明说** | `camera` `ipcam` `spycam` `监控` `偷拍` `针孔` |
| 可疑 | **明确**迹象（看到就想走过去看一眼） | 品牌型号 `v380` `camhi` `besder`；模组命名 `esp_` `esp32`；用途 `baby` `kids`；**词首**型号前缀 `ipc` `gc-` `x6-`；通用 `cam` `cctv` `nvr` `dvr` |
| 关注 | **泛词**（消费电子普遍会用）—— **不进筛选** | `iot` `wireless` `mini` `video` `eye` `watch` `hidden` `smart` |
| 普通 | 其余 | — |

★★ **血案一：泛词上"可疑"级，会把噪声变成主角。**
`某热点名含 "IoT"` 被判 2 级"疑似监控设备" ⇒ 智能插座、灯泡、扫地机**全被标红**，
**真正的摄像头反而被淹没** —— 与用户诉求完全相反。
⇒ 凡"智能设备也会用"的词一律降到"关注"级。

★★ **血案二：短词用子串匹配必然误伤。**
`MiniPC-5G` 被判"疑似监控设备" —— 因为 `minipc` 里含 `ipc`（m-i-n-**i-p-c**）。
⇒ **2~3 字母的词 / 型号前缀一律"只认词首"**。
`a4-` 尤其危险（打印机热点常叫 `DIRECT-A4-…`）。

**判定链的顺序也有讲究**：

```
高危词（子串）→ 可疑词（子串）→ 可疑词（词首）→ 硬件级证据（OUI 等）
→ 隐藏目标 → 泛词（词首无关，子串）→ 普通
```

- **词首判定放在 OUI 之后**：OUI 是硬件级证据，比"名字里有个 iot"硬得多
- 判定要写**纯函数** + 出参给原因串（UI 直接显示），**同一函数给 UI / dump / 自检三处共用**
- 泛词命中的对象**仍要在全列表可见**（带弱灰条 + "关注"），只是不上筛选 —— **既不漏、又不吵**

## 3. 注入式验收：让"风险置顶"变成可复现判据

**问题**：真实环境往往**一个风险目标都没有**（实测环境 43 个 AP / 5 台设备全部 0 级）
⇒ "排序对不对"根本看不出来（退化成纯 IP/信号序，和改之前一模一样）。

**做法**：加**注入命令**（仅调试通道，生产为空）：

| 命令 | 作用 |
|---|---|
| `inject <名> [参数]` | 注入一条伪目标，走**真实排序路径** |
| `injectclear` | 清掉注入项 |
| `rank` | 打印列表**当前显示顺序**（前 8 条 + 等级 + 判据） |
| `only 0\|1` | 切筛选态 |

★ 注入的**两个坑**（都踩过）：

1. **参数要在空格处截断** —— 否则 `inject IPCamera-4F2A -85` 的目标名会变成
   `"IPCamera-4F2A -85"`（把参数也吞进名字）。分派时要 `memcpy` 出名字段。
2. ★★ **注入项必须"钉住"**：上层栈会**周期性上报/刷新数据**且是**整体赋值**
   （`vec = *newdata`）⇒ 注入项活不过几秒，抓屏时看到的是旧列表
   （会误判成"注入没生效"，实测白排查一轮）。
   ⇒ 注入项存**独立容器**（生产恒空 ⇒ 零影响），每次数据刷新后**重新挂上**；
   并且注入命令**自己立刻回读排序后的前 N 名** —— 一条命令给判据、不依赖后续时序。

**验收判据（照这个标准）**：

```
inject IPCamera-4F2A -85 → level=3
排序后 #0 IPCamera-4F2A  -85dBm level=3   ← 参数最差，却排第一（风险优先于"信号/距离"）
排序后 #1 xxx_IoT        -92dBm level=1
排序后 #2 <最强信号AP>    -34dBm level=0   ← 信号最强，掉到第三
```

**界面**逐像素：行首色条按等级分层、汇总卡点名是红字、点筛选后普通行**变空**
（采到页面底色 = 被筛掉）+ 筛选条变色。

## 4. 判据坐标纪律（补充 `pixel-analysis-ai.md`）

`pixel-analysis-ai.md` 讲了**怎么读**截图；这里补一条**取点前必须算的**：

★★ **列表项的屏幕坐标 ≠ item 内坐标**，先算清 **容器偏移 + 行高 + 间距**：

```
屏幕x = 列表.x + item内x        # 例：列表 data-x="12" ⇒ item x=8 对应屏幕 x=20
屏幕y = 列表.y + n*(行高+间距) + item内y
```

血案：在**屏幕 x=8..14** 采样行首色条，看到纯背景色 ⇒ 结论"色条没生效"，
白排查两轮（改源稿做对照、加空指针告警、重新部署…）—— **色条其实一直是好的**，
只是采样点落在了列表**外面**。

★ 推论：**判据算错会得出与事实相反的结论**。任何"某控件没生效"的判断，
先用**一个已知一定存在**的控件（如行卡底、标题文字）验证采样点在不在位。

## 5. FlyThings / EasyUI 的具体落点

| 要做的事 | 落点 |
|---|---|
| 列表视图映射 | 排序在**数据层**做一个 `item(i)` 返回"排序后第 i 条"；列表 `getItemCount` / `obtainItemData` / 点击回调**全走它** |
| 行首色条 | `div class="text"`（**无 picTab ⇒ 圆角注入会跳过**）+ `setBackgroundColor` **和** `setBgStatusColor` 一起设 |
| 筛选条 | 两态按钮；运行时改底色用 `setBackgroundColor` + `setBgStatusColor` + 按高度自动选档的圆角九宫格；**尺寸随意**（九宫格宽度会拉伸） |
| 汇总卡三行 | 三个 `text` 控件，按等级 `setTextColor`；无风险时给绿色正反馈 |
| 列表刷新 | 数据代次（generation）+ 筛选态一起当刷新判据，变了才 `refreshListView()` |
| 注入/自检 | 复用项目的文件式调试通道（写命令文件 → 主循环轮询执行），**每个独立页用自己的命令文件** |

⚠️ 运行时改底色的两条硬规则（多数 EasyUI 项目通用）：
① 只 `setBackgroundColor` **看不到变化**，必须同时 `setBgStatusColor(正常态, 颜色)`；
② `setBackgroundPic()` 会**清掉**底色、`setBackgroundColor()` 会**清掉**图 ——
   "整行换底"要另想办法（预置多张重叠行卡切换显隐，或改用行首色条）。

## 6. 一页速查（现象 → 第一嫌疑 → 立即验证）

| 现象 | 第一嫌疑 | 立即验证 |
|---|---|---|
| "扫出来很多但看不出哪个是目标" | 列表**没按风险排** | 打印列表前 8 条的等级：是不是按 IP/信号排的？ |
| "可疑的混在一堆里" | 缺**筛选** | 有没有"只看风险"入口？门槛是不是把泛词也算进去了？ |
| "一眼看不出哪行有问题" | 缺**色条/点名** | 行首有色条吗？汇总卡报的是"总数"还是"风险结论"？ |
| "智能设备全被标可疑（误报多）" | **泛词上了可疑级** | grep 关键词表：`iot/wireless/mini/video/smart` 在几级？ |
| "某个正常设备被误判" | **短词子串匹配** | 看名字里有没有 2~3 字母词（`ipc`/`dv`/`a4-`）恰好嵌在中间 |
| "点某一行，操作到别的设备" | **重排了底层数组** | 点击回调拿到的下标，和显示用的下标是同一套吗？ |
| "改了排序但列表看着没变" | 视图**没重建 / 没刷列表** | 刷新判据里包含"排序代次"和"筛选态"吗？ |
| "判断控件没生效" | **采样点算错** | 先用一个已知存在的控件（行卡底/标题）验证采样坐标 |
| "环境里没有可疑目标，没法验收" | 缺**注入** | 有没有注入命令 + 顺序回读？注入项会不会被周期性刷新洗掉？ |

## 7. 换平台/换项目对照清单

1. **列表类型**：是 `ListView`（有 row 复用）还是手写滚动？
   —— 复用型列表**逐行回调里必须显式清空**上一行的风险文字/颜色（不清会串行）
2. **排序放哪**：数据层（推荐，UI 三处自动一致）还是 UI 层？
3. **视图映射**：点击回调能否拿到"真实下标"？
4. **改底色 API**：是否需要"底色 + 状态色"两件套？会不会清掉背景图？
5. **九宫格圆角**：按高度选档还是必须精确尺寸？小尺寸（<8px）控件要**跳过圆角**。
6. **调试通道**：命令文件路径、是否"内容变化才执行"、日志缓冲区多大
   （缓冲区小的板子上，"一次打 20 行"的自检会被刷掉 ⇒ **改逐条查询**）
7. **注入项的生命周期**：数据多久刷新一次？注入要不要"钉住"？
