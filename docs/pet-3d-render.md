# 电子宠物 · 写实 3D 离线渲染管线（pet3d）

> 起因（用户 2026-09-17）：*"我想要一个 3D 效果的宠物动画，把它放到这个机器里面，按键动一下它就可以有一些变化。
> 整体的 3D 动态效果可以做一个 WorkBuddy 机器人，做出各种常见的表情包。"*
> 第一版我手绘了扁平矢量稿（SVG），用户否决：*"这个效果不是我想要的，我想要的是更接近真实的。这个效果过于低端。"*
> ⇒ 转为**离线 PBR 渲染**：PC 上用真 3D 引擎渲出带 alpha 的 PNG 帧，设备端只做 1:1 贴图。

## 0. 结论先看

| 项 | 值 |
|---|---|
| 引擎 | **headless Chrome + WebGL(three.js r160)**，走真实 GPU（实测 ANGLE / NVIDIA Quadro P620 / D3D11） |
| 材质 | MeshPhysicalMaterial（白壳 clearcoat 亮油）+ 金属（metalness 1）+ 深色玻璃屏（透明 clearcoat） |
| 光照 | `RoomEnvironment` IBL + 主光（软阴影 2048）+ 补光 + 轮廓光 |
| 输出 | 带 alpha 的 PNG（`premultipliedAlpha:false`），超采样 2~3 倍后 LANCZOS 缩到最终尺寸 |
| 设备侧 | 与摇骰子同一条路：`resources/images/game/pet/*.png` + `core/PgGameArt.h` 清单 + `pg::sprites().get()` |
| 依赖 | **零安装**：three.js 三个文件放 `vendor/`，驱动只用 node 内置模块 |

## 1. 台架怎么跑

```bash
cd PocketGame/tools/pet3d
NODE="C:/Users/Admin/.workbuddy/binaries/node/versions/22.22.2-2/node.exe"

$NODE server.js stills.html out 960 1140        # 主图 + 12 个表情特写
Q="mode=pose" $NODE server.js stills.html out3 640 760   # 6 组姿态
Q="mode=expo" $NODE server.js stills.html out2 640 760   # 曝光对照
$NODE server.js debug.html dbg 640 400          # 导出表情贴图原图 + 纯色定位屏幕

python qa_shot.py out/*.png            # 客观判据（覆盖率/包围盒/亮度分位/过曝）
python preview.py out/hero.png 76      # 字符画（--mode gray 判明暗 / --mode hue 判配色）
python sheet.py                        # 合成给人看的预览图 → preview/
```

`server.js` 的设计（**刻意不依赖 puppeteer / CDP**）：页面渲染完一帧就把 PNG **POST 到 `/save?name=xxx`**，
node 服务器直接落盘；全部渲完 POST `/done`，服务器杀 Chrome 退出。只用 `http`/`fs`/`child_process`。

## 2. 两个"看不见的坑"（都是这次实测挖出来的）

### 2.1 ★★ 阴影正交框必须**完整覆盖接阴影的地面**，否则框外整片被判成"在阴影里"
`ShadowMaterial` 的地面原来是 200x200，而主光的 `shadow.camera` 正交框只有 ±30
⇒ **框外区域一律返回"被遮挡"** ⇒ 画面右下角多出一大块 alpha=87（= 满强度黑）的脏色，
`bbox` 一路顶到画面最右边（`(181,127)-(959,1042)`）。
**修法**：地面缩到 40x40、正交框放到 ±34（地面必须比框小）。
★ 判据：`qa_shot.py` 打印的 `bbox` 右/下边界**等于图像边界**就是它。

### 2.2 ★★ 主光仰角太高 + 偏侧 ⇒ 头把影子打在自己胸口上
第一版 `key.position=(-26,46,32)`（仰角 56°、方位 -40°）：头的投影落在身体的**正面**
⇒ 身体整片发暗（重色 `k`）。把主光往**正前方**挪到 `(-22,44,46)`，投影落到身后（z 负方向）就看不见了，
同时正脸还被照亮（`dot(n, L)` 0.537 → 0.683）。★ 补光别用纯冷色（`0xdcecff` 会让右侧面糊成一片蓝灰）。

## 3. 建模与表情的分工

- **几何是程序化的**（`robot.js` 的 `buildRobot()`）：RoundedBoxGeometry 头部 + 胶囊手臂 +
  球关节 + 环/柱细节。**没有外部模型文件**，改比例只改代码。
- **表情是"屏幕内容"**：脸部屏幕是贴在头正面的一块 **自发光贴图**（`MeshBasicMaterial` + `toneMapped:false`，
  2D canvas 现画）。⇒ **加一个表情只要加一个 `case`**，不用重烘任何 3D。
  这是"离线烘帧"路线里唯一能做到"表情随意扩展"的做法（对比：每个表情都烘一张全身图，
  素材从 ~1.2MB 涨到 ~4MB，且表情不能与随机动作组合）。
- ★ **发光字形的画法**：两遍——先大 `shadowBlur` 的辉光描边/填充（主色），
  再小 `shadowBlur` 的核心（浅色）。核心那一遍的 alpha 别给满（0.62），
  给满会把字形洗成纯白、丢掉色相（第一版就是 `0.9` ⇒ 眼睛渲染成灰白）。
- ★ **玻璃罩的 opacity 会整体压暗屏幕**：`0.26` 时字形的峰值亮度从 250 掉到 ~187；
  改成 `0.18`。屏幕贴图必须**探出**腹板/凹陷的前表面，否则只露一点点（见下）。

## 4. 相机与构图

`fitCamera(cam, object, {box, az, el, padX, padY})` —— 用物体包围盒**迭代 3 次**把相机框满，
比手算距离省心。传 `box` 可以只看局部（如头部特写要排除天线）。

宠物资材按 **320x380** 出图，摆在画布内 (80,80)。

## 6. 动画：姿态是参数，不是新模型

关键帧用「**关键时刻 + 自动补间**」写（`stills.html` 的 `kf()`，smoothstep 缓动），
不用逐帧手调；`applyPose(robot, pose)` 只改这几个量，**没有任何缩放**（工程铁律）：

| 量 | 含义 |
|---|---|
| `rootY` | 整体升降（呼吸 / 起跳 / 落地） |
| `leanZ` `leanX` | 身体左右 / 前后倾 |
| `headPitch` `headYaw` `headTilt` | 点头 / 转头 / 歪头 |
| `armL` `armR` `armLX` `armRX` | 两条手臂的张开 / 前后摆 |
| `antZ` `antX` | 天线摆动（"活着"最便宜的一条线索） |
| `glow` `chestColor` | 胸口灯与天线灯的亮度 / 颜色 |

已烘好的四段（`Q="mode=anim" node server.js stills.html anim 640 760`）：

| key | 帧 | fps | 内容 |
|---|---|---|---|
| `idle` | 36 | 18 | 呼吸起伏 + 眨眼（第 21~24 帧）+ 天线摆 |
| `happy` | 30 | 20 | 摸头反应：下蹲(-0.95) → 起跳(+3.4) → 落地过冲(-0.38) → 归位 |
| `sleep` | 30 | 12 | 垂头 + 灯灭 + Z 字飘（慢速循环，fps 低才像"睡着"） |
| `faces` | 48 | 10 | 12 个表情轮播，每个 4 帧带弹跳 |

### 6.1 ★★ 表情是「眼睛 + 嘴 + 装饰」三层，各自独立可换
`drawFace(canvas, expr, W, H, {blink})`：
- 眨眼**只替换眼睛层**（`EYES_BLINK`），嘴和装饰原样保留 ⇒ 不必为每个表情再烘一套闭眼版本。
- 加第 13 个表情 = 在 `EYES` / `MOUTH` / `FX` 三个表里各加一项，**不用重烘 3D、不用重刷固件**。

### 6.2 ★★ 动画的"到底动没动"要靠**帧间像素差**，不能只看包围盒
`anim.py` 同时打印：逐帧包围盒波动 + **相邻帧灰度平均绝对差**。
只看包围盒会**漏报**"剪影不动但内容在变"的动画 —— 表情轮播的剪影几乎不动（上沿只差 2px），
但眼睛嘴一直在换（帧间差 2.83~12.63）。判据写成"包围盒波动 < 3px **且** 帧间差 < 1.0 才告警"。

### 6.3 ⚠️ GIF 编码器会**合并完全相同的相邻帧**
`faces` 第一版每 4 帧里有 2 帧姿态完全相同（都是 0）⇒ 48 帧的序列出成 **36 帧**的 GIF，
帧数与渲染帧数对不上还查不出原因。**正解：让每一帧都两两不同**（哪怕只差 0.01）。
★ 验收时要**数 GIF 的实际帧数**（`im.seek()` 循环），不能只数目录里的 PNG。

## 9. 真机实测（固化版，2026-09-17）

| 项 | 数据 |
|---|---|
| 进页 | `enter game[33] 电子宠物` |
| 贴图 | `spr` → **10 张 / 2238KB / 失败 0**（9 姿态帧 + 1 阴影） |
| 缺字 | `glyphmiss miss=0 fallback=0` |
| 互动 | `Pet: 摸头 #1 -> 开心跳` → `开心跳结束 -> 回到待机`（`gdbg pet` 与按键/触摸同源） |
| 帧率 | `bench` → `render=5537us`，帧间隔 21252us ⇒ **47 次/秒** |
| 内存 | 宠物页开着 MemFree **10.1MB**，退出回收后 **13.3MB**（贴图 2.2MB 全额归还） |

### 9.1 ★★ 部署方式决定了内存预算：**这个功能必须用固化版**
| 部署 | zkgui RSS | MemFree | 能否放 2.2MB 贴图 |
|---|---|---|---|
| 调试版 `fun launch`（应用 7.6MB 全进 `/tmp` tmpfs = 吃 RAM） | 11.4MB | **1.5MB** | 不行（预算 ≤1MB） |
| **固化版（应用在 flash 的 squashfs，不占内存）** | 5.1MB | **31MB** | 宽裕 |

⇒ 大贴图应用**验收一律用固化**（86s），别用 `ITER=1` 的 launch 去验内存。

### 9.2 帧率的瓶颈**不是宠物贴图**，是每帧整屏写背景
裁剪把宠物贴图从 280x333 降到 216x289（像素 −34%），`render` 只从 5737us 降到 5537us
⇒ **宠物 1:1 贴图只占约 1ms**，另外约 4ms 是"整屏 clear + 地面 fillRect + 光池 ellipse"
（约 33 万像素的写入）。要再往上走只有**脏矩形**：画布是**零拷贝挂在控件上的持久缓冲、
宿主不清屏**（`platform/PgDisplay.cpp` 的 `attach`），所以静态背景只需首帧画一次，
之后每帧只重画"宠物 + 阴影"所在的那一条带（约 66K 像素）⇒ 预计能到 ~55fps。
本次没做（收益/复杂度不划算，47fps 对这种舒缓动画视觉上已经流畅）。

## 10. ⚠️⚠️ 踩坑：`stillFrame()` 报"静止"会**连 `update()` 一起被跳过**
我试过用"帧指纹"（phase + 姿态号 + 位移 + 互动次数）判断"画出来和上一帧逐像素一样"，
想借宿主的静止跳过省掉每帧 5.5ms。**结果宠物直接冻住**：
宿主跳过 render 的同时把 `update()` 也跳过 ⇒ `ms_` 不再推进 ⇒ 姿态/位移/眨眼永远停在那一刻
⇒ 指纹永远相等 ⇒ 永久冻帧。实测日志：连续两条 `gdbg state` 都报 `ms=217`，`累计实绘=3` 再也不涨。

★ **规律**：**"靠时间推进的状态"不能报静止**（`MEMORY.md` 里早有这条，我又踩了一遍）。
要让这个优化成立，游戏的时间轴必须是**绝对时钟**（每帧从 `clock_gettime` 现算，而不是累加 dt），
那样跳过 update 也不丢信息。本页没做，`stillFrame()` 老老实实恒返回 `false`。


## 12. 表情层：把脸拆出来（2026-09-17 第二批）

### 12.1 交付形态
| 素材 | 张数 | 尺寸 | 说明 |
|---|---|---|---|
| 身体帧 `kPetBody[8]` | 8 | 216x289 | **屏幕是空的**，只有姿态（手臂/头/天线的角度） |
| 表情层 `kPetFace[13]` | 13 | 85x61 | 透明小贴图：12 个表情 + 眨眼 |
| 地面阴影 | 1 | 197x57 | 单独一张 |

**8 个姿态 × 13 个表情 = 104 种组合，内存只要 8+13 张（解码 2.20MB）**；
对比"表情焊进姿态帧"的 96 张全尺寸贴图（约 20MB）。

### 12.2 表情层贴哪儿：靠"品红锚点帧"量出来
头会点头/抬头 ⇒ 屏幕在画面上的位置会挪几个像素，而画布**不能缩放/旋转**贴图。
所以渲染时**额外渲一批"把屏幕涂成品红"的同姿态帧**（`solid:'#ff00ff'`），
生成器读回像素求品红包围盒 ⇒ 每个姿态的"表情层左上角"（8 个姿态实测 84~88 x 58~63，
取中位数 85x61）。**不用手算投影矩阵，也不会随渲染取景改动而失准。**

### 12.3 字形常量改成"设计空间 + 缩放变换"
表情层要出两种尺寸（512 宽的屏幕贴图 / 85 宽的小贴图），而所有字形常量（线宽、模糊半径、
圆的半径）都是按 512x326 写死的。做法：`makePainter` 里 `ctx.setTransform(K,0,0,K,0,0)`，
之后**全部按设计空间画** ⇒ 一套常量出任意尺寸，比例完全一致。

### 12.4 ⚠️⚠️ 喂给画布文字的格式串必须 **≤14 字符**
`tools/genfont.py` 对"**变量实参**"（`textCenter(..., line, ...)`）只回退到
「**本文件 ≤14 字符的短字面量**」这个保守超集（`file_literals(path, max_len=14)`，
就是为了不把日志/URL 收进字库）。第一版写的是
`snprintf(line, ..., "表情 %s · 互动 %d 次")` —— **15 个字符**，超限 ⇒ 生成器看不到它
⇒ 真机 `glyphmiss` 报 `miss=3018 ... U+60C5 '情' / U+4E92 '互'`，**这两个字根本不画**。
★ 这是"静默不画"的典型：日志、帧率、画面结构全都正常，只有 `glyphmiss` / 量像素才发现。
★ 规律：**画布文案要么作为字面量实参直接传，要么格式串压到 14 字符以内**；
改完画布文案一律重跑 `tools/genfont.py` 并用 `glyphmiss` 验收（`miss=0 fallback=0`）。

## 13. 输入：暂停键当"互动键"用（新增宿主钩子）
宿主默认把暂停键解释成"暂停/继续"，**根本不会走到 `Game::onKey()`**。
新增 `virtual bool pauseKeyIsAction() const { return false; }`：宠物覆盖成 true，
宿主就把按键原样交给 `onKey(PG_KEY_A)` 且不碰 `state_`（否则第一下走完被置成 RUNNING，
第二下就落到"暂停/继续"上去了）。**默认 false ⇒ 既有游戏一字不变**。

对应交互：**短按 = 摸头**（即时反馈）、**600ms 内连按两次 = 换下一个表情**。
★ 第一版做的是"延迟 220ms 等第二下"⇒ 判定太脆（任何延迟就退化成只摸头），
改成"按下立刻摸头 + 窗口内第二下追加换表情"，代码里也少一个待决状态。

### 13.1 真机按键验收（`pgkey`，必须带 `norepeat`）
```
pgkey 108 100 /dev/input/event3 norepeat              # 短按 -> 摸头
pgkey 108 90 /dev/input/event3 norepeat; pgkey ...    # 同一次 adb 调用里连按两次 -> 换表情
```
⚠️ `pgkey` 默认会**模拟内核 autorepeat**，而本板 gpio-keys **没有 autorepeat**、
应用层是按 DOWN→UP 时长判长按的 ⇒ 不带 `norepeat` 会被框架判成"长按(repeat 路径)"。
⚠️ 两次 `adb shell` 之间的往返开销有几百毫秒，**测连按必须放在同一次 adb 调用里**（用 `;` 串起来）。
⚠️ 设备的 `chmod` **不支持符号形式** `+x`（报 "Bad mode"），要用 `chmod 755`。

## 15. 自动行为：让它像宠物，而不是"按键才动"的玩具（2026-09-17 第三批）

### 15.1 四个阶段 + 两条自动线
| 阶段 | 触发 | 表现 |

| 待机 `PH_IDLE` | 默认 | 呼吸 + 眨眼 + **每隔 9~18s 自己做个动作** |

| 睡着 `PH_SLEEP` | **25 秒没人理** | 垂头 + **灯灭** + 场景调暗 + Zzz，慢呼吸 |

- 自动动作 3 次里 2 次换表情、1 次打招呼（打招呼太频繁会显得吵）。
- **任何互动都会叫醒它**（睡觉时按一下先醒、不摸头，符合直觉）。
- 睡觉的"灯灭"是**烘在帧里**的（`glow: 0` 让天线灯与胸口灯真的暗下去）——
  运行时改不了灯的亮度，所以必须在渲染阶段给。实测睡着时宠物区域均值亮度
  36.1 vs 待机 41.3。

`kPetIdle0/kPetHappy0/kPetSleep0/kPetGreet0`，**加姿态不用改运行时代码**。

### 15.3 ⚠️⚠️ 表情层锚点必须用**屏幕中心**，尺寸取**最大姿态**
打招呼会 `headYaw 0.20`，头一左右转，屏幕四边形在画面上既平移、宽度也变
（15 个姿态实测 **84~96 宽、57~67 高**）。画布不能缩放贴图 ⇒ 尺寸只能取一个常量：
- 取**最大**（96x67）+ 按**中心**对齐 —— 小姿态下多出来的那圈是**透明的**
  （表情层只有字形、没有底），不会盖住屏幕边框；
- 第一版用"中位数尺寸 + 左上角锚点"，打招呼那几帧字形明显偏到左上角。

## 16. ⚠️⚠️ 「要画出来的字必须在 .cpp 字面量里能找到」
这一条今天踩了**两次**，两次都是"静默不画"：

| 症状 | 根因 |
|---|---|
| `glyphmiss miss=3018`，`情`(U+60C5) / `互`(U+4E92) 不画 | 格式串 `"表情 %s · 互动 %d 次"` 是 **15 字符** ＞ `file_literals` 的 `max_len=14` ⇒ 生成器看不到 |
| `glyphmiss miss=1512`，`墨`(U+58A8) / `镜`(U+955C) 不画 | 表情名来自**生成物 `PgPetArt.h`**，而 `genfont.py` 只扫 `.cpp` 的字面量 |

★ 规律：`tools/genfont.py` 收字有**两条路**，两条都有前提：
1. **字面量实参**（`textCenter(..., "你好呀！", ...)`）→ 无长度限制；
2. **变量实参** → 回退到「**本文件里 ≤14 字符的短字面量**」这个保守超集。
⇒ 来自**头文件 / 生成物 / 运行时拼出来**的文案，两条路都走不到 ⇒ 必须像
   `PgPet.cpp` 的 `kPetFaceChars0/1/2` 那样**在 .cpp 里把字面量"过一遍"**（分段 ≤14 字符）。
★ 验收一律跑 `glyphmiss`：`miss=0 fallback=0` 才算过。

## 18. 触摸手势：点哪儿决定反应（2026-09-17 第四批）

设备示意图上写了"点头顶=摸头、点肚子=逗它、左右滑动=翻表情"，这次把它兑现了。
**不需要任何新素材**（复用已有的摸头/打招呼姿态）。

| 手势 | 动作 | 判据 |
|---|---|---|
| 点宠物**上半**（头） | 摸头（开心跳） | 按下点落在贴图内 且 `y < petZoneY_` |
| 点宠物**下半**（身体） | 打招呼（挥手回应） | 落在贴图内 且 `y >= petZoneY_` |
| 落在宠物**以外** | 也当摸头 | 别让"点屏幕没反应" |
| **中间横滑**（≥55px，纵向 ≤45px） | 右滑=下一个表情 / 左滑=上一个 | 在 `PG_TOUCH_MOVE` 里判 |

### 18.1 三个实现要点
1. **动作在 `PG_TOUCH_UP` 才执行**（按下只记起点）。否则"想滑动换表情"的人会先被摸一次头。
2. **用按下的位置判分区**，不用抬起的位置 —— 手指滑一点就换部位会很怪。
3. 分区位置由 `render()` 每帧写进 `petX_/petY_/petZoneY_`（贴图高度 42% 处 = 头身交界），
   `onTouch` 直接读 ⇒ 改构图时触摸区自动跟着走，不用手抄坐标。

### 18.2 与全局"右滑返回"不冲突
全局手势要求**从左边缘起手 + 横移 ≥120px**（见 `pg::Swipe`），而本页手势只要 55px
且通常从屏幕中间起手 ⇒ 两个不会打架。**在左边缘横滑仍然是返回**（全局行为，不动）。

### 18.3 宿主给的坐标是**画布内坐标**
`mainLogic` 里是 `dispatchCanvasTouch(act, ev.mX - CANVAS_X, ev.mY - CANVAS_Y)`
（`CANVAS_X=0, CANVAS_Y=160`）⇒ 游戏拿到的是 **0..480 / 0..540**，不是屏幕坐标。
★ 工程里**自带一条画布触摸的 QA 通道**，比 `pginj` 算屏幕坐标省事得多：
`echo "tap 243 204"` / `echo "down 200 300"` / `move` / `up` —— 走的是
`dispatchCanvasTouch`，与真触摸同一条路。

### 18.4 ⚠️ `pginj` 注入的触摸可能**延迟送达**
实测：注进去的 tap 当时没反应，几十秒后才在日志里冒出来（同一条命令的日志错位）。
⇒ **测触摸用工程的 `tap/down/move/up` QA 通道**（精确、即时）；`pginj` 留给
"验证触摸驱动本身"，别用来判交互逻辑的时序。

## 20. 情绪升级：被戳烦了会生气、再戳会哭（2026-09-17 第五批）

之前不管怎么碰它都是正面反应（摸头开心 / 点身体打招呼）——**永远不会不耐烦的宠物不像宠物**。
这次补上负向一极，动物帧从 15 张涨到 **21 张**（+angry 3 +cry 3，解码 5.39MB）。

| 阶段 | 触发 | 表现 |
|---|---|---|
| 生气 `PH_ANGRY` | **8 秒内连续互动 ≥5 次** | 抱臂 + 低头瞪 + 身体小幅抖动 + **胸口灯变红** |
| 哭 `PH_CRY` | 继续戳到 **≥9 次** | 双手抬到脸前抹泪 + 抽噎 + **灯变冷蓝并变暗** |

- **"连着"才算法**：相邻两次互动间隔 < 8 秒；隔久了重新从 1 计数（"慢慢摸不算骚扰"）。
- 灯的**颜色和亮度是烘在帧里的**（`applyPose` 改的是材质色），运行时改不了
  ⇒ "生气变红灯 / 哭变暗蓝灯"只能在渲染阶段给。

### 20.1 ⚠️⚠️ 升级链的断点：**不能在阶段结束时清零计数**
第一版在"生气播完"时把计数清零了，于是**"继续戳到哭"永远够不着**：
生气只播 2.6 秒，这段时间里最多再戳 2 下，5+2 < 9 ⇒ 那一段死代码。
实测日志证明了：`气消了 -> 回到待机` 之后下一条是 `摸头 #8（骚扰计数=1）` —— 计数被清了。
**正解：计数只交给时间窗自然衰减**（隔 8 秒不碰才归零），阶段结束**不清零**。
代价是连续戳它会一直闹脾气（≥5 就一直是生气）——这本来就是想要的效果。

## 21. 渲染性能：45fps → 62fps、CPU 从 24% 降到 2.8%（2026-09-17 第六/七批）

宠物一进页面就在 45fps 连续重绘整屏（33 万像素/帧）——这是这次交付里最大的一处浪费。
两刀砍下去，**画面逐像素不变**。

| 阶段 | render | 帧间隔 | 帧率 | CPU（render×帧率） |
|---|---|---|---|---|
| 原始：每帧整屏重绘 | 6389us | 22024us | 45 | 287ms/s = **24%** |
| ① 脏带重绘 | 4588us | 20211us | 49 | 225ms/s = 19% |
| ② **无变化直接跳过** | **553us** | 16193us | **62** | 34ms/s = **2.8%** |

### 21.1 第一刀：脏带重绘（-28%）
**前提（这条不成立整个优化就是错的）**：画布是**零拷贝挂在控件上的持久缓冲、宿主不清屏** ——
`platform/PgDisplay.cpp` 的 `attach` 里 `b->data = canvas_.pixels(); tv->setBackgroundBmp(b);`，
框架只把这块位图 blit 到 LCD，**不会**逐帧清它 ⇒ 上一帧画过的静态内容还在。
⇒ 只重画"宠物 + 阴影所在的那一条带"：
- 脏带 = **上一帧位置 ∪ 这一帧位置**（宠物在 dy 里动）+ 阴影矩形（**阴影不随 dy 动**，固定）。
  ⚠️ 漏掉"上一帧位置"就会留一条**拖影**。
- 带内背景的绘制顺序必须与整屏路径**逐字一致**（天 → 地 → 地平线 → 光池），否则两条路径像素不同。
- 光池是**椭圆**（逐行左右边界都不同）⇒ 不能按行填色偷懒，整块重画（2.8 万像素，可接受）。
- 铭牌在脏带之外，**不会自己更新** ⇒ 用"铭牌指纹"（阶段/表情/互动次数）判它变了才重画。

### 21.2 第二刀：与上一帧逐像素相同就直接不画（-88%）
待机时宠物**看起来**一直在动，但**真正变化的帧只有 ~17%**：
呼吸位移是**整数像素**（一圈只走 6 个值）、姿态 4 帧、眨眼 160ms、表情不变。
而画布是持久缓冲 ⇒ 不画 == 画了同一样的东西。

★★ **这一条的价值不在"省了多少像素"，而在"放对了地方"**：
我**第一次**（很早以前）拿同一套指纹去 `stillFrame()` 返回 true，结果**宠物直接冻死** ——
宿主会**连 update() 一起跳过**，`ms_` 不再推进 ⇒ 指纹永远相等 ⇒ 永久冻帧。
现在把它放进 `render()` 里就没这个问题：update() 照常推进，只是"这一帧画出来一样"时省掉绘制。
⇒ **同一套指纹，放对地方就是优化，放错地方就是 bug。**

### 21.3 ★★ 方法论：**先确认东西画出来了，再谈性能**
第二刀做完后我量到 render=1917us（-46%），正准备收工 —— 顺手做的**逐像素 A/B 对照**却显示
"宠物区亮像素 = 0"：**优化后的路径压根没画宠物**。
根因是我替换 render() 的一大段代码时，**把三行 `blit()` 一起替换掉了**（阴影/身体/表情）。
⇒ 那份"漂亮的性能数据"是**假的**（什么都没画当然快）。
★ 所以验收口径必须是**两条路都"画对了"**：`宠物区亮像素 ≈ 10000` + `静态区逐像素差 = 0`。

### 21.4 留下的可观测性
- `bench`（宿主自带）：update/render/present 每帧均值 + 帧间隔。
- `gdbg state`：多了 **实绘 / 跳过** 两个累计计数（跳过比例一眼可见）。
- `gdbg dirty on|off`：**A/B 开关**。关掉 = 每帧整屏重画 ⇒ 两边截图必须逐像素一致。

## 23. 放大宠物：试了、量了、**回退了**（2026-09-17 第九批）

用户问 "还能不能更大"。我把渲染取景从 280x333 放大到 **345x410**（宠物内容占画布宽 44% → 52%），
真机上走了一遍所有姿态把贴图全加载，量到的东西让我回退了：

| 配置 | 贴图解码 | **全载后 MemFree** | render（实测帧） | 帧率 | 内容占画布宽 |
|---|---|---|---|---|---|
| **280x333（最终保留）** | 5.39MB | **6.19MB** | 638us | 61 | 44% |
| 345x410（放大 1.25 倍） | 7.98MB | **2.73MB** | 919us | 60 | 52% |

★ 贴图解码后占堆 = **帧数 × 宽 × 高 × 4 字节，和面积成正比**（21 帧 × 267×348 × 4 ≈ 7.4MB）。
★ 本板总共 **56MB**，这工程有过 **OOM 血案**（720p 硬解被内存挤死，见 docs/online-media.md）。
  只放大 1.25 倍换来 **+8%** 的画面占比、却把余量从 6.2MB 压到 **2.7MB** ⇒ **不划算**。
★ 退出页面会全额归还（12.17MB）—— 这一点两边都成立，所以问题只在"页面开着的时候"。

### 23.1 真要更大，得先付代价（三条路，还没做）
1. **减帧**：`sleep/greet/angry/cry` 各减一两个姿态（21 → 16 帧），能省 ~1.9MB；
2. **按动画分组只保留当前组**：常驻 idle 的 4 帧，动作帧用完就 `sprites().clear()` 重载
   ⇒ 内存能压到 ~2MB，代价是**每次互动切换有 ~20ms 解码卡顿**（约 1 帧多的顿）；
3. **缩回去**：把每个动画的帧数砍半、靠更大的运行时位移补流畅度（呼吸/跳跃本来就是运行时算的）。

### 23.2 顺手补的一个"防漂移"改造（这条留下来了）
`世界单位 → 像素` 的比例原来是运行时手写的 `333.0f / 37.9f` —— **改渲染取景就会静默不同步**
（呼吸起伏与跳跃幅度跟着错，画面看上去"还能动"，很难联想到是常量没改）。
现在**由生成器输出** `petart::kPetPxPerUnit`（= kPetFrameH / 37.9），真值只有一处。
★ 和"脚底行 kPetFeetY"、"裁剪偏移"是同一个套路：**凡是同时被生成器和运行时用到的数，一律让生成器输出**。

## 24. 表情面板：12 个表情从"盲划"变成"可选"（2026-09-17 第十批）

之前 12 个表情**存在但没法浏览** —— 只能左右滑一个一个盲试。加了个面板：**长按宠物**
展开 4×3 的表情图鉴（每格一张表情层原图 + 名字，当前选中的那格高亮），点哪格选哪个、点面板外收起。

### 24.1 交互怎么排的（画布上的手势已经不少了）
| 手势 | 动作 |
|---|---|
| 轻点宠物上半 / 下半 | 摸头 / 打招呼 |
| **横向拖 ≥55px** | 上一个 / 下一个表情 |
| **长按 ≥600ms** | **展开表情面板** |
| 面板内点格子 / 点外面 | 选中该表情并收起 / 只收起 |

★ **长按在"抬手"时才判**：按下就弹面板的话，抬手那一下会被当成"点了某一格"。
★ 面板开着时**滑动手势被屏蔽**（否则在面板上划一下就悄悄改了表情），
  且**跳过重绘/脏带都关掉**（面板是模态的，让增量逻辑继续生效会算错要擦哪儿）——
  反正是临时状态，不值得为它做增量。

### 24.2 素材复用：一格不用新加
面板里每格就是那 13 张表情层里的**原图 1:1 贴**（96x67，画布不做缩放）。
名字用 `kPetFaceNames[]`，字形早在 `kPetFaceChars0/1/2` 那三个收字字面量里了（见 §16）。

### 24.3 实测
