# 八个游戏的功能检讨 + 新游戏选型建议

> **方法**：逐份读完 `src/core/Pg{2048,Tetris,Plane,Flappy,Snake,Mines,Sokoban,Breakout}.cpp`
> 共 3501 行（2026-09-13），逐个核对**玩法完整度 / 触摸适配 / 一致性**。
> **结论先说**：**8 个游戏全部支持触摸**，整体完成度不低（2048 最高）；
> 真正的问题不在"能不能触摸"，而在**三处一致性缺陷**与**触摸手势挤压**——
> 这恰好是"再往里面加适合触摸的游戏"之前该先理清的地基。

## 一、逐个检讨

| # | 游戏 | 行数 | 操作方式 | 完成度 | 触摸质量 |
|---|---|---|---|---|---|
| 1 | **2048** | 505 | 滑动（阈值 26 / 抬手兜底 18） | ★★★★★ | ✅ 有防抖 |
| 2 | **俄罗斯方块** | 566 | **四种手势挤一处**（水平拖=移动／下拖=软降／上滑=直落／轻点=旋转） | ★★★★ | ✅ 有防抖 ⚠️ 手势冲突 |
| 3 | **打飞机** | 494 | 拖动（跟随，手指上移 46px 避遮挡） | ★★★★ | ✅ 跟随式 |
| 4 | **贪吃蛇** | 410 | 滑动转向 + **点一下暂停** | ★★★★ | ⚠️ 无防抖 |
| 5 | **扫雷** | 374 | 点格子挖开 + 长按插旗（另有插旗模式） | ★★★★ | ✅ 点按类 |
| 6 | **推箱子** | 511 | 滑动移动 + 撤销，多关卡 | ★★★★ | ⚠️ 无防抖 |

### 1. 2048 —— 全工程完成度最高的一份

- **动画**：滑动 110ms ease-out、合成/新块弹跳 150ms、16 档色板完整（2→2048 逐级配色）
- **音效**：合成 / 移动分开播（`SFX_MERGE` / `SFX_MOVE`）
- **触摸细节（值得别的游戏学）**：
  - **异常跳变保护**：`|Δ|>160` 只重同步基准、不产生动作（防触摸驱动噪声把方块甩飞）
  - **动画期间锁输入**（`if (animMs_ >= 0) return true;`）
  - **连续滑动**：一次触发后以当前位置为新基准 —— 可以一口气连滑好几步
- **收尾完整**：达成 2048 有顶部提示条；GAME OVER 覆盖层带"本局得分"
- **问题**：无。

### 2. 俄罗斯方块 —— 功能最全，但**手势全挤在一个区域**

- 操作映射：水平拖 **每 24px 一格**、下拖 >40 软降（2 次计 1 分）、上滑 <-50 硬降（每格 2 分）、**轻点（<14px）旋转**
- ⚠️ **手感风险最高的一份**：四种手势没有分区，全部靠位移方向/幅度区分。
  实际使用中「想横移但手抖了」→ 判成旋转；「想软降但拖斜了」→ 判成横移。
- 另外：旋转只有一个方向，没有"逆向旋转"。
- **这是最需要"软按钮"的游戏** —— 而 `SoftButton`（画布底部触摸按钮）在框架里定义了、**8 个游戏没有一个用它**（见 §二.1）。

### 3. 打飞机 —— 细节最贴心

- `targetY_ = y - 46.0f`：**手指上方留 46px**，避免手指挡住战机；左右做了边界钳制
- 自动开火，玩家只需拖动走位 —— 触摸屏上的自然玩法
- 问题：无。

### 4. 贪吃蛇 —— 唯一的"游戏内暂停"，也是唯一的不一致

- 代码里留了一段**很有价值的教训注释**（值得保留）：
  > 「开始/继续/重来」三个分支必须挂在 **UP（抬手）** 上，不能挂 DOWN ——
  > 一次点击会先后到达 DOWN 和 UP；若 DOWN 时就改状态，紧接的 UP 会落进"点一下=暂停"分支，
  > 于是**点一下想开始、结果变成已暂停**（用户 2026-09-12 报的"能暂停不能开始"）。
- ⚠️ 问题 1：**暂停机制与其它 7 个不统一** —— 贪吃蛇是"点一下屏幕 → 游戏内 PAUSED（画布遮罩、无弹窗）"，
  其它 7 个是"按物理暂停键 → 框架暂停弹窗"。同一张列表里两套暂停交互。
- ⚠️ 问题 2：**无异常跳变保护**（滑动类游戏，风险同 2048 但没防护）。

### 5. 扫雷 —— 触摸适配天然好

- 9×9、10 雷；格子边长 `(vw()-8)/9 ≈ 52px` —— **远超 38px 的手指下限**，点按精度没问题
- 双模式：直接点=挖开、长按=插旗；另有 `flagMode_` 开关（按 A 键切换），照顾"长按不好按"的场景
- 问题：无（点按类不需要跳变保护）。

### 6. 推箱子 —— 自己造了一套"底部按钮"，但没走统一接口

> 📌 **本条已更正**（2026-09-13 复查）：最初误判为"文案与实现不符"，实际看漏了渲染代码 ——
> `keyBar()` 写的"点底部按钮操作"**是对的**。

- 它在画布底部 `vh()-54` 处**自绘了 4 个按钮**：上一关 / 下一关 / 撤销 / 重来，
  命中检测也自己硬编码（`(vw()-5*8)/4` 等分 + y 区间判断）。
- ⚠️ **真正的问题**：这恰好说明"**画布底部软按钮是刚需**"，
  但 `SoftButton`（框架里定义的能力）**没人用** ——
  推箱子**自己造了一套**（自绘 + 硬编码），俄罗斯方块则**完全没有**、只能靠四种手势硬撑。
  同一个需求两套实现，还有一处缺口。
- 功能本身完整：多关卡、`undo()` 撤销、过关判定。
- ⚠️ 无异常跳变保护（滑动类）—— **2026-09-13 已补**（与 2048 同一套 `|Δ|>160` 只重同步）。

### 7. 打砖块

- 两阶段：`launched_` 为假时拖动挡板 + 点屏幕发射；发射后只拖动
- 只用 x 轴（`(void)y;`）—— 竖屏下合理
- 问题：无。

### 8. 小鸟过水管 —— 完成度最低的一份（323 行）

- 点屏幕振翅，`started_` 标志区分"待起飞/飞行中"
- 行数最少，玩法最薄（无难度递增、无道具）
- 问题：无功能缺陷，但**内容深度不足**。

## 二、横向问题（这是比"加游戏"更该先处理的）

### 1. ⚠️ `SoftButton` 定义了却没人用 —— 需求是真的，接口是空的

`PgGame.h:84` 定义了"画布底部的一排触摸按钮，游戏可用可不用"，但全工程
**`grep SoftButton` 只有定义处一处命中**。后果分成两种：

- **推箱子**：确实需要底部按钮 → **自己造了一套**（自绘 4 键 + 硬编码命中检测）；
- **俄罗斯方块**：同样需要 → **没有**，只能把"移动/软降/直落/旋转"四种手势全塞进一个触摸区域。

同一个需求，一处自造、一处缺口 —— 说明**该把 `SoftButton` 真正实现出来**（2026-09-13 已实现）。

### 2. ⚠️ 暂停机制有两套

| 游戏 | 暂停方式 |
|---|---|
| 贪吃蛇 | **点一下屏幕** → 游戏内遮罩（无弹窗） |
| 其余 7 个 | **物理暂停键** → 框架暂停弹窗 |

同一列表中两套交互，用户要先记住"这个游戏是哪种"。

### 3. ⚠️ 触摸防抖保护不一致

| 有「异常跳变」保护 | 无保护 |
|---|---|
| 2048、俄罗斯方块、**贪吃蛇**、**推箱子**（后两个 2026-09-13 补齐） | 扫雷 / 打砖块 / 小鸟 / 打飞机 —— 点按或跟随类，**不需要** |

> ✅ **2026-09-13 已统一**：贪吃蛇与推箱子补上了与 2048 同一套的 `|Δ|>160 只重同步` 保护。

### 4. ⚠️ 推箱子 `keyBar()` 文案错误（见 §一.6）

### 5. 缺"游戏内重开/返回"的可视入口

重开只能：物理 **C 键**（`PG_KEY_C` → reset）或游戏结束后点屏幕。
纯触摸用户（不按物理键）在**玩到一半想重开**时没有入口 —— 只能长按返回列表再进来。

### 6. 无难度 / 关卡选择（推箱子除外）

2048 无法调棋盘大小、贪吃蛇不能调速、扫雷固定 9×9 10 雷、小鸟无难度递增。

### 7. 无排行榜（只有单局最高分）

`Host` 只提供 `highScore/setHighScore` 单值，没有"前 N 名"。

### 8. 内容深度参差

2048（505 行）与小鸟（323 行）的玩法厚度差了近一倍。

## 四、新游戏选型：适合触摸屏的

筛选标准：① **触摸是"更自然"的操作**（而非勉强适配） ② 实现成本（纯 C++ 软渲染、零资源）
③ 与现有 8 个**不重复** ④ 耐玩度。

| 候选 | 触摸适配 | 成本 | 与现有重复 | 推荐 |
|---|---|---|---|---|
| **打地鼠** | ★★★ **触摸专属**（键盘玩不了） | 低 | 无（现有无反应类） | ⭐**首推** |
| **五子棋**（内置 AI） | ★★★ 点一下落子 | 中（要写评分 AI） | 无（现有无棋类） | ⭐**推荐** |
| **数字华容道**（15-puzzle） | ★★★ 点/滑 | 低 | 无 | ⭐**推荐** |
| **记忆翻牌配对** | ★★★ 点翻牌 | 低 | 无 | ⭐**推荐** |
| 三消（消消乐） | ★★★ 拖拽交换 | **高**（匹配/连锁/掉落动画） | 无 | 可选 |
| 汉诺塔 | ★★ 点选→点放 | 低 | 无 | 可选 |
| 泡泡龙 | ★★★ 点瞄准 | 高 | 与打砖块略近 | 可选 |
| 黑白棋（翻转棋） | ★★★ 点落子 | 中 | 与五子棋近 | 备选 |
| 接苹果 | ★★ 拖动 | 低 | 与打飞机/打砖块近 | 备选 |

### 首推四个的理由

1. **打地鼠** —— 唯一"**触摸屏独有**"的类型：靠快速、多点、随机的点击反应，物理键盘做不出来。
   也补上了现有 8 个全是"策略/动作"、没有**反应类**的空白。实现成本低（一屏洞 + 计时 + 命中判定）。
2. **五子棋** —— 触摸屏上"点一下落子"是最自然的交互；补上**棋类**这一整类空白；
   内置一个简单评分 AI（连五/活四/冲四打分）即可，不需要搜索树深度。
3. **数字华容道** —— 点击相邻块滑动，**零学习成本**；难度靠棋盘尺寸（3×3/4×4）；实现极简（数组 + 邻接判定）。
4. **记忆翻牌配对** —— 点击翻牌，**适合触摸、老少皆宜**，且**一局时间短**（符合掌机碎片时间）；
   实现极简（牌堆数组 + 两张比对）。

### 触摸屏适配的共同要求（新增游戏必须满足）

- 单指可玩，**不需要多点、不需要物理键**
- 可点元素 **≥ 44px**（见 `docs/ui-design-baseline.md` §4）
- 不引入新的手势冲突（若手势复杂 → **用软按钮**，把 `SoftButton` 真正用起来）
- 触摸防抖保护：滑动类必须带"异常跳变重同步"
- 文案（`desc` / `hint` / `keyBar`）必须与实现一致

## 六、建议的推进顺序

```
① 修 3 个 P0 缺陷（推箱子文案 / 补防抖 / 俄罗斯方块软按钮）  ← 地基
② 加 1~2 个新游戏（建议先「打地鼠」+「五子棋」，一个补反应类、一个补棋类）
③ 上机验收（真机截图 + 手感）
④ 再决定是否继续加（数字华容道 / 记忆翻牌）
```

**为什么先修再加**：软按钮一旦落地，俄罗斯方块立刻受益，后续新游戏也能少走"手势挤一处"的弯路 ——
否则每加一个手势复杂的游戏，就多一份同样的债。

## 附：画布绘制原语的两个坑（2026-09-14 实测）

### ★★ 坑：环内被涂黑 —— "透明擦除"在画布上等于"涂黑"

**症状**（用户报障）：五子棋里 **AI 落子后，红圈（最后一手标记）里面是黑的**，
正常应该是白子。实测抓帧：红圈中心像素是 `#000000`，而白子应是 `#F4F6FA`。

**根因**：`Canvas::strokeCircle` 原来这么写 ——

```cpp
fillCircle(cx, cy, r, c);                 // 画实心圆
fillCircle(cx, cy, r - t, 0x00000000);    // 以为"透明 = 擦除内部"
```

但底层 `Canvas::fillRect` 是**直接赋值**（`row[i] = c`），**不做 alpha 混合**：

```cpp
for (int i = 0; i < iw; ++i) row[i] = c;   // ← 没有混合，写什么就是什么
```

⇒ 内圈被**真的写成 alpha=0 的像素**；画布再合成到屏幕时 alpha=0 就**透出下层页面底（纯黑）**。
**环内部永远是纯黑，把底下的内容整块盖掉。**

**为什么长期没被发现**：它盖的正好是深色内容 —— 五子棋黑子 `#1C1E24` 与纯黑 `#000000`
肉眼分不出；**只有盖住白子（AI 落子）时才暴露**。所以"看起来正常"不等于没事。

**修法**：需要"挖空"就**自己算形状**，别依赖 `alpha=0`。改成逐行只画环带：

```cpp
int inner = r - t;
for (int dy = -r; dy <= r; ++dy) {
  int o = (int)(0.5 + sqrtf((float)(r*r - dy*dy)));      // 外缘半宽
  if (dy <= -inner || dy >= inner) {                     // 上下两端整行都在环上
    fillRect(cx - o, cy + dy, 2*o + 1, 1, c); continue;
  }
  int i = (int)(0.5 + sqrtf((float)(inner*inner - dy*dy)));  // 内缘半宽
  int band = o - i;
  fillRect(cx - o, cy + dy, band, 1, c);                 // 左半环
  fillRect(cx + i + 1, cy + dy, band, 1, c);             // 右半环
}
```

**同一 bug 的另外两处**（一起修好了）：
- `PgMemory.cpp` 的 `strokeCircle`（卡片上的圆圈标记）—— 圈内会盖掉卡片内容
- `PgWhack.cpp` 的 `strokeEllipse` ×2（地鼠洞口沿）—— 椭圆内部会被涂黑

验证：修复后打地鼠页**纯黑像素 0.00%**；五子棋红圈中心回到 `#F4F6FA` + 高光 `#FFFFFF`。

**通用纪律**：
1. 画布上**没有"橡皮擦"语义** —— `fillRect/fillCircle` 都是覆写。要挖空就画形状。
2. 引入任何"用特殊颜色表示透明/擦除"的写法前，**先确认底层像素写入是否做 alpha 混合**。
3. 深色内容上的绘制 bug 容易被"看不出来"掩盖 —— **验收要用"高对比内容"覆盖一遍**
   （本例：用白子覆盖才暴露）。

### ★★ 坑二：游戏素材全是**硬边**（无抗锯齿）—— v1.16.0 修复

**症状**（用户报"很多游戏里面的素材好多都有锯齿状"）：棋子是**多边形**、圆的斜边是 1px 台阶。
真机证据（五子棋白子边缘）：木色 `#C6A46E` → 白子 `#F4F6FA` **直接跳变、零过渡像素**。

**根因**：`PgCanvas` 的所有原语都是"**整数取整 + fillRect**"，没有任何边缘混合：

```cpp
int dx = (int)(0.5 + sqrtf((float)(r*r - dy*dy)));   // ← 取整 = 台阶
fillRect(cx - dx, cy + dy, 2*dx + 1, 1, c);
```

这不是"贴图分辨率"问题 —— 游戏素材**本来就是程序化绘制**的（不是 PNG），
锯齿来自**画布自己没做抗锯齿**。

**方案选择**：`ZKPainter`（框架的 `div.painter` 控件）是另一条路，但要把 21 个游戏的
`render(Canvas&)` 全部重写成它的状态式 API（`setSourceColor/drawArc/fillTriangle…`），
且**它的渲染质量没有实测过**（框架文档未提抗锯齿）。**成本远高于收益**，
所以选择"给自绘画布加 AA"—— 一个文件、全部游戏立刻受益。

**实现**：**距离场覆盖率**（`putAA` + `blendPx`）

```cpp
// 只有边缘那一圈（覆盖率 ∈ (0,1)）才混合；内部仍走 fillRect 快路径
inline void putAA(Canvas *cv, int x, int y, Color c, float cov) {
#if PG_CANVAS_AA
  if (cov >= 1.0f) cv->px(x, y, c);
  else if (cov > 0.0f) cv->blendPx(x, y, c, (int)(cov * 255.0f + 0.5f));
#else
  if (cov > 0.0f) cv->px(x, y, c);
#endif
}
```

- 圆：覆盖率 = `r + 0.5 - 到圆心距离`
- 环：取"外缘覆盖率"与"内缘覆盖率"的较小者
- 圆角矩形：四角 1/4 圆用距离场，中间仍是矩形快路径
- 椭圆：`水平覆盖 × 竖直覆盖`（椭圆没有闭式精确距离）
- 三角形：交点保持浮点，逐像素按水平覆盖率混合
- 开关：`PgCanvas.h` 的 `PG_CANVAS_AA`（1 开 / 0 关，用于 A/B 性能）

**性能实测（必须量，别猜）**：2048 运行时 4 秒的进程 CPU jiffies：
| AA | jiffies | 
|---|---|
| 关 | 378（≈94.5/s）|
| 开 | 379（≈94.8/s）|

⇒ **AA 的开销可忽略**（内部快路径覆盖了绝大部分像素）。
⚠️ 顺带测出的更重要事实：**游戏本身就是 ~95% CPU**（30fps 全屏软渲染的常态），
真要降 CPU 得从"减少重绘 / 脏区更新"入手，不是砍 AA。

**验收判据**：同一区域"不同颜色数" 5 → **11**（多出来的就是边缘过渡色）；
白子边缘出现 `A89F95` / `C5756B` 这类中间色（修复前是直接跳变）。

**通用纪律**：软渲染的**每一个**几何原语都要问一句"边缘混合了吗"。
纯水平/垂直的 `hline/vline/strokeRect` 不需要；**斜边/圆弧/圆角必须做**。

> **续篇（2026-09-15）**：上面解决的是"几何原语的边缘混合"。**文字**的锯齿是另一条链路
> （内嵌点阵字库原来只烘 16x16 的 1bit 点阵、绘制时整数放大）——
> 已改成「按目标像素原生栅格化 + 4bit 覆盖率」，见 **`docs/canvas-font.md`**。
> 顺带把"所有东西不能做拉伸"落成了三条可执行检查（静态图尺寸比对 / 电量条按宽度烘图 /
> 画布 1:1 贴像素）。

## 附：画布手势阈值与**怎么验收手势**（2026-09-15）

### 俄罗斯方块「上滑直落」阈值调大（用户反馈"容易误触发"）

原实现只判 `dy < -50` 就直落 —— 而直落是**立刻锁定方块（不可逆）**，
横移时手指略微向上带、或滑动轨迹是斜的，就会被判成直落，误一次毁一手。
现改成**两条同时满足**才触发（`src/core/PgTetris.cpp` 顶部常量，改之前先读注释）：

| 常量 | 值 | 含义 |
|---|---|---|
| `HARD_DROP_DY` | **90**（原 50） | 上滑位移下限，约 4 格高 |
| `HARD_DROP_DX` | **40** | 允许的横向漂移上限 —— 超过就说明"本意是横移" |
| `SOFT_DROP_DY` | 40 | 下拖多少算软降一步 |
| `TAP_DX` / `TAP_DY` | 14 / 14 | 轻点（= 旋转）允许的最大位移 |

> 手感上不影响正常使用：要直落时人会明显往上甩一下；而且底部本来就有
> 「左 / 下 / 右 / 转」四个实体软按钮（同一次检讨里加的），横移不依赖手势。

### ★★ 验收画布游戏的手势：**别只靠抓帧**

抓帧判"有没有触发某个操作"会被**自然演进**干扰（俄罗斯方块的方块自己会往下掉、
消行也会改变画面）——我第一次就是这么误判的（面板区变了 ≠ 直落发生）。

**确定性的两件套**：

```bash
# ① QA 直接喂画布触摸（绕过内核/框架触摸链路；坐标 = **画布坐标**，480x540）
adb shell "echo 'tap 240 270'  > /tmp/pg_autostart"   # 点掉 READY 遮罩、开始游戏
adb shell "echo 'down 240 400' > /tmp/pg_autostart"
adb shell "echo 'move 240 310' > /tmp/pg_autostart"   # 上滑 90px
adb shell "echo 'up 240 310'   > /tmp/pg_autostart"

# ② 读分数（gscore）—— 分数只在**有效操作**时变，是最干净的判据
adb shell "echo 'gscore' > /tmp/pg_autostart"         # → score=32 state=1
```

⚠️ **多行内容别用设备端 `printf`**：实测 `printf 'a\nb' > /tmp/pg_autostart` 写进去是**空文件**
（单行 `echo` 一直可靠）。要一次下发多条命令就**在 PC 侧写好文件再 `adb push`**
（见 `tools/` 下的验收脚本写法）。

⚠️ 用这两条之前要知道：
- QA 文件是**内容变化才执行** ⇒ 每次下发的内容必须不同（末尾加一个 `q<N>` 之类的无效行，
  见 `docs/touch-inject.md`；**别用 `#` 加后缀**，`#` 后面会被当注释剥掉）。
- `enter <n>` 会进游戏，但游戏停在 `GSTATE_READY` ⇒ 必须先 `tap <画布中心>` 才开始
  （否则 `gscore` 报 `state=0`，所有手势都被 READY 分支吞掉 ⇒ **测试会全部"看起来没触发"**）。
- **抓帧 + 分数一起看**：抓帧看观感，分数做判据。
- ⚠️ 画布底部 62px（`PG_SOFT_BAR_H`）是软按钮条，喂手势要避开（用 y≈400 起手）。

## 附：把一款游戏"做像样"要动什么 —— 打地鼠视觉改版（2026-09-15，v1.18.0）

用户原话：「打地鼠这种界面应该**结合实际场景换成草地背景图**，**锤子样式可以弄几个切图切换动作**。
**连击的时候需要有弹出 combo 之类的赞赏图**，让产品更具备可玩性。」

### 1. 先给画布加**贴图能力**（这是前提）

`Canvas` 原来只有几何原语 —— 锤子这种"木纹 + 金属质感"的素材画不出来。新增：

```cpp
struct Sprite { const uint32_t *px; int w, h; };
void Canvas::drawSprite(const Sprite &sp, int x, int y);
void Canvas::drawSpriteA(const Sprite &sp, int x, int y, int alpha);   // 带整体透明度
```

三条约定（与"不许拉伸"一致，别破坏）：
① **1:1 贴图，不缩放不插值** —— 要多大就离线烘多大；
② 像素格式与画布一致（0xAARRGGBB），逐像素 alpha 混合，`alpha=0` 直接跳过（sprite 大半是空的）；
③ 图数据是 `const`、编在 .so 里（`src/core/PgWhackArt.h`），**不占堆**；代价是 .so 变大
   （数据量 ≈ Σ w×h×4：锤子 3 帧 × 120×120 ≈ 169KB ⇒ .so +190KB）。

### 2. 锤子 = **离线烘的三帧切图** + 每帧自己的锚点

`tools/gen_whack_art.py` 用 PIL 画一把卡通木槌（木柄 + 浅木槌头 + 两端金属箍 + 深描边），
再**绕握把旋转**出三帧：`up(-26°) 举起` / `mid(-4°) 挥下` / `hit(30°) 砸中`。

★★ **坑：旋转后必须把内容平移回画布内，并把"该帧的锚点"一起导出来。**
三帧绕同一个握把转，角度越大越往一侧探 —— 实测 `up` 帧右边越界 36px、`hit` 帧左边越界 40px，
**直接被裁掉一截**（肉眼看是"锤头少了一块"）。做法：
每帧求内容包围盒 → 居中回画布 → 记录 `anchor = (ANCHOR + shift)` → 运行时按**该帧的 anchor**
对齐（`图左上角 = 触点 - anchor`）。这样不裁切、不浪费数据、屏幕上握把落点三帧一致（换帧不跳）。

生成器的**自检**（每次跑都打印，别省）：
```
帧 up   墨迹  3664 px (25.4%)  锚点 (35, 106)  出界像素 0 ✓
帧 mid  墨迹  3885 px (27.0%)  锚点 (54, 106)  出界像素 0 ✓
帧 hit  墨迹  3518 px (24.4%)  锚点 (84, 105)  出界像素 0 ✓
自检：通过 ✓
```
"出界像素"判据是**检查画布四边有没有 alpha>8 的像素** —— 用包围盒判断会漏
（`bbox` 恰好到边界时，既可能是"刚好贴边"也可能是"已被裁"，分不出来）。

### 3. 草地场景：**程序化绘制**，不贴图

一张 480×540 的真图 = 259200 × 4B ≈ **1MB 内存**（本板总共 56MB），不值得。
改成程序化：草坪渐变（远深绿 → 近亮绿）+ 泥土斑 + 草簇 + 小花 + 石头。

★ **纹理要"每帧一致"，不能用 `rand()`**：草簇位置用**哈希函数**（`h32(i)`）算 ——
零存储、同一个 i 永远同一个位置，不会闪烁；存位置表则要占内存。

★ **地鼠"从洞里钻出来"**：Canvas 没有裁剪/遮罩 API，做法是
**先画完整地鼠，再用"洞口前沿"（下半椭圆）把它下半身盖住**：
```cpp
void fillEllipseLower(Canvas &c, int cx, int cy, int rx, int ry, Color col);  // 只填 y ∈ [cy, cy+ry]
```
顺序：`画洞 → 画地鼠 → 再画洞的下半部`。上半不画，所以不会盖住地鼠的头。

### 4. 连击赞赏（COMBO）：程序化 + 分级

连击 ≥2 时在**命中处**弹出（不是屏幕中央 —— 反馈要跟手）：

| 连击 | 颜色 | 形容词 | 备注 |
|---|---|---|---|
| 2-4 | 金 `#FFD640` | 不错! | |
| ≥5 | 金 | 厉害! | |
| ≥8 | **橙红 `#FF8A30`** | 太强了! | |
| ≥12 | 橙红 | 无敌! | |

- 放射线 12 条（用 `fillTriangle` 画楔形），长度随"弹出阶段"伸长 + 轻微脉动；
- 文字**先 8 方向画深色描边再画亮色**（草地底色花，没描边看不清）；
- 淡出**靠颜色向草地色插值**（画布文字没有 alpha 参数）；
- 弹出动画**只做位移 + 放射线伸长，不做缩放**（缩放要重采样 = 糊）。

### 5. ★★ 顺带抓出的两个**底层**问题（都不是打地鼠自己的）

#### 5.1 我自己引入的回归：`strokeEllipse` 把环画成了**实心椭圆**

上一轮给原语加 AA 时，椭圆环的覆盖率公式写错了两处：

```cpp
float cov = (1.0f - f) / gl + 0.5f;
if (cov > 1.0f) cov = 1.0f;               // ← 提前 clamp
float ci = 0.5f - (f - inf/rxf) / gl;     // ← 符号反了
if (ci < cov) cov = ci;
```

- 椭圆**内部深处** `gl`（梯度模）→ 0 ⇒ `(1-f)/gl` 爆成几万 ⇒ cov 被 clamp 成 1（填实）；
- 内边界那项符号写反（洞中心方向算出的是**正**距离 ⇒ 永远 `ci > cov`，起不到约束）。

⇒ 打地鼠的命中环变成一个盖住半个屏幕的**实心亮绿椭圆**（实测 29743 个该色像素）。

**修法**：两个边界各算"到边界的像素距离"，取较小者，**最后才 clamp**：
```cpp
float cov = 0.5f - (f - 1.0f) / gl;              // 外边界（正 = 在外侧）
if (inf > 0) { float ci = 0.5f - (inf/rxf - f) / gl; if (ci < cov) cov = ci; }  // 内边界（正 = 在洞里）
if (cov > 1.0f) cov = 1.0f;                      // ★ clamp 放在取 min 之后
```

离线验证（同参数 `rx=60, ry=30, t=3`，Python 复现两个公式）：
**旧 5104 个不透明像素（实心）→ 新 522 个（细环）** ✓

> 教训：**圆的版本（`strokeCircle`）用真实距离、没这个问题**；换成椭圆的"梯度近似"时，
> 只验证了"边界附近对不对"，没验证"内部深处会不会被填" —— 而内部深处恰恰是爆表的地方。
> 凡是"距离/梯度"的写法，**都要单独想一遍"离边界很远的地方会算出什么"**。

#### 5.2 固定 dt 的隐患：**帧率一掉，游戏内时间就走得比真实时间慢**

主循环传下去的是**常量** `LOOP_MS = 33`。但定时器周期只是"最小间隔"：
回调里要跑渲染（软渲染全屏重绘），某帧一超过 33ms，这一 tick 就被拉长，
**而 dt 还是 33** ⇒ 游戏时间被"延展"。

**实测血案**：打地鼠的连击赞赏设 900ms，改版后帧率掉到 ~7fps 时，
它**在屏幕上停了 3.6 秒**（差 4 倍）；同理"30 秒倒计时"会跑 2 分钟。

**修法**：dt 用**实测经过时间**（钳到 200ms，防止卡顿恢复时"一步跳太大"）：
```cpp
const long long now = pgNowMs();
static long long sPrev = 0;
int dt = sPrev ? (int)(now - sPrev) : LOOP_MS;
if (dt < 1) dt = 1;
if (dt > 200) dt = 200;
sPrev = now;
```
修完复测：combo 在 ~900ms 后正常消失 ✓（之前 3.6 秒）。

> 这条对**所有**游戏/工具都生效 —— 任何"按毫秒推进"的逻辑之前都在偷偷变慢。

### 6. 顺带加的两条**常备工具**

| 命令 | 用途 |
|---|---|
| QA `fps` | 统计 2 秒内主循环次数（设备没有 top/vmstat）—— **性能回归的第一手数据** |
| QA `gdbg <...>` | 把调试命令转发给当前游戏（`Game::debugCmd`）。打地鼠支持 `hit <i>` / `wake <i>` / `reset` |

**为什么要 `gdbg`**：连击赞赏**没法靠手点验收** —— 地鼠冒头位置随机，
点空一下连击就归零，盲点几乎必然断链。有了 `hit <i>` 就能精确制造 20 连击。
关键纪律：**QA 走的是与真实操作完全同一条代码路径**（`GameWhack::hitHole()` 是唯一实现，
触摸和 QA 都调它），否则"验的"和"玩到的"就不是一回事。

## 附：消消乐（糖果三消，v1.22.0，2026-09-15）

需求原话：「游戏里面再帮我加一个消消乐。UI 效果要参考《开心消消乐》」（附 App Store 链接）。
形态 = **画布类游戏**（走 `main.ftu` 的 `GameCanvas` + 原生 HUD）⇒ **不新建 ftu**，
比"独立应用"少一半工作量（**六个**改动点见 §五 开头的更正）。

| 项 | 结果 |
|---|---|
| 玩法 | 8x8 / 7 种糖果（颜色+形状双重区分）/ 滑动或点两下交换 / 3+ 连线消除 + 连锁计分 / 关卡目标 + 25 步 / 死局自动重排 / **特殊块：4 连出方向炸弹、5 连出彩虹球**（v1.23.0） |
| UI | 参考产品的视觉语言：花园底 + 木质棋盘 + 浅色糖果凹槽 + 顶栏木牌进度条；13 张 PNG 素材 |
| 帧率 | **60fps**（固化版；调试版 51~58 —— 差在内存而非渲染）/ render ~5ms；第一版只有 33fps，见下面第 1 条 |
| 验收 | 31 项（日志 + 逐像素 + **差分判据**），含 `pginj` 真触摸点图标进游戏、`glyphmiss 0/0` |

**这一节真正值得留在通用文档里的四条**（细节与血案见 `docs/match3.md`）：

1. ★★ **贴图要"整图不透明"才走 memcpy 快路径** ⇒ 推论：**"每格一张小图"的场景，
   图里要带上它的底**（消消乐把凹槽底烘进糖果图：render 17.7ms/33fps → 4.6ms/58fps）。
   已补进 `docs/game-art-pipeline.md` §3 硬规则第 7 条。
2. **`ImageDraw` 的半透明 `fill` 直接写 alpha**（PIL 的 draw 不做合成）—— 这才是"看着不透明
   实则非不透明"的**真凶**；**不是** `resize(LANCZOS)` 的锅（有对照实验：整图不透明时缩回后
   alpha 伪影 = 0，含一块半透明 fill 时 = 112240）。正解 `lerp(底色, 叠加色, t)` 预混合。
3. **三消验收不能盲点**：8×8 盘上随机交换几乎必然无效 ⇒ 新增 `tools/match3_qa.py`
   （从 QA `gdbg board` 日志算可行交换 + 抓屏**逐像素**判画面，含"覆盖层压暗"反推）。
   这与「打地鼠连击不能手点」是同一条纪律：**验收手段本身要可复现**。
4. **QA 钩子改状态时要连状态机一起复位**：`gdbg level n` 只换了棋盘没复位 `state_`，
   于是卡在 OVER，后续 `gdbg swap` 被 `isPlaying()` **静默拦截** —— 症状极像"交换功能坏了"。
