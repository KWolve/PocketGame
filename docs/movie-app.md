# 动画短片应用（飞天仙女 / 可爱小猫）—— 全屏循环播放

> 2026-09-20。用户需求原话：「我在 `pet_video` 里面放了两个视频，cat 和 moon。
> 我现在需要把这个视频放到设备里面去。然后做两个 APP，一个是飞天仙女，进去直接全屏

## 二、片源：为什么必须转码（三条都是实测，不是猜）

| 源片实际情况（`ffmpeg -i`） | 后果 |
|---|---|
| **HEVC (H.265)**，`hvc1` | 本工程的视频链路是 **H.264 专用**：`zk_h264_player` 只解 H264、`PgStream` 的 bsf 是 `h264_mp4toannexb`。直接丢进去 = 黑屏。 |
| **720x1280 = 921,600 像素** | 超解码内存守卫的安全线（960x544 = 522,240）；本板 56MB 内存，720p 不缩放会触发内核 OOM。 |
| 10.08s / 24fps / 双向音频 | 见下面的体积预算。 |

**转码口径**（`tools/gen_movie_assets.py`，可复现）：

```
crop=720:1200:0:40    # 源 720x1280 纵向居中各裁 40px → 720x1200
scale=480:800         # 1200/720 = 800/480 ⇒ **正好是屏幕比例**，铺满且不变形
fps=15  2-pass 300kbps  AAC 40kbps 22050Hz 单声道  +faststart
```

- **为什么"先裁再缩"**：源 9:16（0.5625）、屏 3:5（0.6）。按宽度铺满要到 853 高 ⇒ 必须裁纵向
  53px。先裁成 720x1200（= 屏幕比例）再缩放，屏幕上就是 **1:1 像素**：无黑边、无变形、
  **不需要硬件缩放**。
- **为什么 22050Hz 单声道**：`PgAudio` 那条常开流就是 22050/单声道，编码成同规格可以**省一次重采样**。
- **`+faststart`**：把 `moov` 挪到文件头，ffmpeg 不用发 Range 去尾部找（见 `docs/online-media.md` §13.7）。
- **质量实测**（对 480x800 高质量参考帧的 SSIM）：480x800@15fps/300kbps = **0.933**，
  与 384x640 同码率（0.935）持平 —— 那就取原生 480x800，播放时零缩放。
- ★★ **音频下混要显式写"平均"**（2026-09-21 实测）：片源有的是单声道、有的是立体声。
  立体声走 ffmpeg 默认矩阵下混到单声道时，两声道同相的内容会**叠加** ⇒ 实测电平
  **+3dB**（RMS 2100 → 2959），两段片子会一个偏响一个正常，用户切来切去听得出来。
  现在脚本会先探测源的声道数，立体声一律用 `pan=mono|c0=0.5*c0+0.5*c1`（真正的平均）。
  验证：产物 RMS 应与源一致（实测 fairy 2098 vs 源 2100 ✓）。

### 2.1 ★★ 换片源 = 重新转码 + 重新固化（一条命令链）

用户换掉 `pet_video/` 里的源片后，**设备上看不到变化**（固化的还是上一版镜像）——
2026-09-21 就遇到过：「可爱小猫播放的视频不对」其实是用户把 `cat.mp4` 换成了新的
（旧 1.10MB/单声道 → 新 2.32MB/立体声）。处理的完整链路：

```bash
python tools/gen_movie_assets.py     # 1. 重新转码（会报体积，超上限直接失败）
tools/upgrade_device.sh <新版本号>    # 2. 重新出包 + 固化（脚本自带体积校验与 /res 挂载自检）
python tools/movie_seam_qa.py kitten 25 --dur 10.10   # 3. 真机验收（见 §3.3 三条判据）
```

★★ **判"设备上播的是不是你要的那段"用音频指纹**（本次就是靠它定案的）：
把源片与固化产物的音频各抽 9 秒（`-ac 1 -ar 8000 -f s16le`）算 NCC ——
正确映射应 **≈ +1.0**（实测 kitten↔源cat **+0.9994**、fairy↔源moon **+0.9993**），
交叉对比应 ≈ 0。**比看画面可靠得多**：这两段源片在整段平均色彩上几乎一样
（色距只有 4.3，都偏蓝），单看画面根本分不出哪段是哪个。

## 三、播放与"连续播放"的实现（`src/ui/MoviePage.cpp`）

### 3.1 链路（全部复用已验证模块，本页不新增底层）

```
/res/ui/media/*.mp4 --ffmpeg 解封装--> 设备硬解 zk_h264_player --> disp 视频层
                    --> 从 UI 层 videoview 那块透明区域透出来
       音频 --> ffmpeg 软解 AAC --> 重采样 --> 灌进 PgAudio 常开 PCM 流
```

页面侧关键三行（`ui/fairy.html` / `kitten.html`）：
`videoview VideoMain 480x800`（**UI 层给视频层开的透明窗口**）+ `ImgMovieCover`
（不透明整屏底图，起流那 1 秒盖住"上一个页面透过来 + 黑底发虚的字"，出画立刻隐藏）+
两行状态字。

### 3.2 相位机（`IDLE → SWITCHING → WAITFRAME → PLAYING`，出错进 `ERROR`）

| 相位 | 判据 | 动作 |
|---|---|---|
| SWITCHING | 等 `!StreamPlayer::running()`（≤8s，失败重试到 12 次） | `setRotation(0)` + `startWithDisplay(file,0,0,0,480,800,`**`loop=true`**`)` |
| WAITFRAME | **`H264Player::framesDecodedInRun() > 0`** | 收底图 → PLAYING，提示再留 4s |
| PLAYING | `StreamPlayer::fileLoops()` 变了 | **只更新计数**（循环在流层完成，见 §3.3） |
| PLAYING | `!running()`（正常播放**不该**出现） | 流真断了 → 回 SWITCHING 重起，连续 3 次进 ERROR |

★ 关键：**正常循环根本不经过 SWITCHING** —— 它只在"第一次起流"和"流真的断了"时用到。

### 3.3 ★★ 循环 = 流层就地 seek（不是"停流再起一轮"）— 2026-09-20 改版

第一版是"这一轮 `running()` 变 false ⇒ 盖底图 ⇒ 回 SWITCHING ⇒ 重新起流"。
用户实测反馈：**「视频不连贯，播放结束重新播放不要切换画面」** —— 因为那条路的接缝代价是
**0.5 ~ 1.5s 的可见黑屏**：收尾（几十 ms~1.5s）+ 重新 `init` 硬解 + **等首帧 200ms~1s**，
而那段黑屏期间本页还必须盖着不透明底图（否则 UI 层没内容、会透出上一层残留）。

现在改成**流层连续循环**（`StreamPlayer::startWithDisplay(..., loop=true)`）：
`PgStream` 的解封装线程读到 `AVERROR_EOF` 时**不停流**，而是

```
av_seek_frame(fmt, -1, 0, AVSEEK_FLAG_BACKWARD) + avformat_flush
  + avcodec_flush_buffers(adec)          ← 清音频解码器残帧
  + 本轮时间基准归零（t0 / audioBaseMs）  ← ★ 不归零就是老毛病"整轮包一口气喂完"
  + 清挂起帧与 PTS 队列
continue;                                 ← 解码器与 disp 视频层**全程不重建**
```

实测（`tools/movie_seam_qa.py`，48 个样本 / 32 秒）：

| 判据 | 结果 |
|---|---|
| 接缝开销（一轮时长 − 片长 10.10s） | **21 / 24 / 23 ms**（≈ 一帧，肉眼不可见） |
| 各轮时长极差 | **3 ms**（完全一致 ⇒ 没有累积漂移） |
| 相位 | 全程 `PLAYING`，**一次都没离开过** |
| `running` | 全程 `1`（流没断过） |
| 平均解码帧率 | 13.9~15.0 fps（片源 15） |
| 硬解丢包 | `0` |

★ 判据怎么来的（这页没法用"抓屏"验接缝 —— 抓一帧要 1~2s，接缝只有 20ms）：
1. **`fileloops` 在涨 + `running` 恒 1 + 相位恒 PLAYING** = 中间没有"停流重起"（这是"有没有
   切画面"的直接证据，因为那条路必然让相位离开 PLAYING、`running` 掉 0）。
2. **`lastseek_ms` 的差分 = 一轮实际时长** —— 与片长相减就是**接缝开销**。
   这是最硬的一条：接缝要是停了 300ms，差分立刻变成 10.4s 并**逐轮累积**。
3. **`decoded` 的平均帧率**（累计值差 / 时长）—— 整段时间轴有没有丢帧。
   ⚠️ 别看"单段增量"：状态文件 500ms 刷新 + 采样的相位差会让它 6~17 之间抖，
   那是采样抖动（真掉帧会掉到 0~2）。

两条防护（都是"静默失败"的敌人）：
- **快速失败计数**：循环间隔 < 800ms（片源/读盘异常）⇒ 连续 3 次进 `ERROR` 停住。
  否则片源坏了会变成"无限重起 + 日志刷屏"，把日志服务刷爆。
- **中途退出**按 `stopForSwitch()` 停（**不置**"需要复位应用"标志）—— 本页是独立 ftu，
  主界面的主循环不在前台，没人消费那个标志（同 `cameraLogic` 的口径）。
- `loop` 是**每次起流显式传的**（不是粘性开关）—— 别的页面（投屏/网络电视/摄像头）
  调同一个函数时不传就是 `false`，不会被这里带跑。

### 3.3b ★★ 播放期间不许进屏保（本页"零操作"，只关一次不够）

本页全程**没有任何用户操作**（进去就看，看完长按退出），所以框架的"无操作超时"一路走到底。
只在进场时 `setScreensaverEnable(false)` 是不够的（用户实测放着不管仍会进屏保）。做法：

- `onUI_show`：关屏保检测 + 若已进屏保则立刻 `screensaverOff()` + 重置计时；
- **`tick()` 里每 1 秒压一次**（`setScreensaverEnable(false)`），而且
  `isScreensaverOn()` 一旦为真就立刻叫回来 —— 比"等下一次超时再压"稳得多；
- **`onUI_hide` / `onUI_quit` 都要复位**（`setScreensaverEnable(超时 > 0)`）。
  ⚠️ 这条是红线：屏保是**全局粘性状态**，我们在 tick 里每秒强制关它 ——
  退到别人手里不复位的话，**设备待机时就永远不进屏保了**（同 `navibar` / `setVideoPage`）。

验收判据：状态文件里的 `saver_on` 恒为 0（`saver_to` 是 30 秒，而采样跑了 30+ 秒）。

### 3.4 ★★ 三个"必须显式做"的事（都有血案）

1. **必须显式 `setRotation(0)`**：`StreamPlayer::sRotManual` 是**全局粘性值**
   （主界面起播时用存盘偏好设它，那是网络电视页"手动转屏"留下的），而
   `desiredRotation()` 在"源无元数据"时**兜底 90°**（那个兜底是给横屏源的）。
   本片源是**竖屏 480x800**，套上 90° 就躺倒了。
2. **起流必须在 UI 线程**（`startWithDisplay` 里要拿回声卡）⇒ 只在 `onUI_Timer` 里发起。
3. **判"真的出画"只看解码回调**（计数在子线程清零，不能拿累计值做减法）。

### 3.5 交互

进去就是全屏画面、**没有任何按钮**（用户要的就是"全屏连续播放"）。
- **任意物理键长按 ≥700ms = 返回列表**（本板 gpio-keys **无 autorepeat**，长按只能在应用层
  按时长判，见 `docs/ui-design-baseline.md` §9）。
- 103/105 短按 = 音量±。
- 底部「长按任意键返回列表」的提示**只在缓冲期 + 出画后 4 秒**显示，之后整屏只剩视频。

## 五、★★ 体积：/res 分区只有 7.6MB（这一步不做就会刷出"卡 logo"）

**实测数字（2026-09-20，`fun pack` 逐项对照）**：

| 状态 | `update.img` | 余量（分区 7,995,392 B） |
|---|---|---|
| 基线（无素材、未 strip） | 6,955,580 | 1,039,812 |
| ＋两段视频 | **＋851,968** | —— |
| ＋`libzkgui.so` 未 strip | 7,811,644 | 仅 **183,748** ⚠️ |
| ＋`libzkgui.so` **已 strip** | **7,647,804** | **347,588** ✓ |

- **H.264 已压缩 ⇒ 进 squashfs 基本 1:1**（852KB 素材 = 852KB 镜像），别指望压缩率。
- `libzkgui.so` 里 `.symtab + .strtab` 有 **725KB**（raw），`strip` 后镜像 **−163,840 字节**
  （符号表高度可压缩，别按 1:1 估）。**代价**：崩溃回溯的地址不再能反解函数名；
  日志里的 `__FILE__:__LINE__` 不受影响（那是字符串）。
- 因此 `tools/upgrade_device.sh` 加了两道**机器判据**（不靠"我记得"）：
  1. **打包前 strip** `.fun/v85x/libzkgui.so`（打一行"省了多少字节"，不静默）；
  2. **出包后立刻校验 `update.img ≤ 7,995,392`**，超了**当场停**并给出三条可行手段。
     ⇒ 失败发生在 PC 侧，**连设备都还没碰**（分区写不下会在擦/写中途失败，
     而升级处理本身跑在应用里 ⇒ 现场只能重刷，见工作区记忆 §0 红线）。
- 素材侧也有上限自检：`python tools/gen_movie_assets.py` 合计超过 850KB 会**报错退出**。

## 六、踩过的坑（都是"看着对、其实是坑"）

### 6.1 ★★ 加视频播放页必须改 `navibar.cc` 的白名单（否则导航栏压住画面顶部 52px）

`src/logic/navibar.cc` 的 `videoPageActive()` 里有个**自愈兜底**：`pg::setVideoPage(true)`
是全局粘性标志，它额外校一次"当前 Activity 是不是已知的播放页"，**不是就地清掉标志**。
⇒ 新加的播放页如果不在白名单里，表现是 **`setVideoPage(true)` 被自己人清掉 ⇒ 导航栏
重新出现、永久压掉画面顶部 52px（真丢内容）**，而页面代码看着完全正确。
本次已加 `fairyActivity` / `kittenActivity`。**加第三个播放页时别忘了这一行。**

### 6.2 ★★ 视频区在 `check_overlay.py` 里要登记，否则报一条很吓人的 SLIVER

`tools/check_overlay.py` 会把"被常显 navibar 盖掉一部分、且确实会画东西"的控件判成
**SLIVER（必修）**。而视频区（`videoview`）被盖 52px 是**设计如此** —— 修法不是挪盒子
（那是硬件 disp 层的显示坐标），而是"进播放页把 navibar 收起来"。
⇒ 工具里本来就有 `VIDEO_VIEWS` / `SETTLED` 两个白名单（`Caster`/`IptvVideo`/`CamVideo`），
本次补了 `VideoMain`。**新增同类视频页要往这两处各加一行**。

### 6.3 ★★ 日志缓冲会骗你：判据要落文件

`LOGD` 只有十几行缓冲，而且被 zknet 的 SSDP/扫描日志持续冲刷。本次实测：
**`movie[fairy]: 已起流/第一帧已出/第 N 轮播完` 这些一次性日志全被冲掉了**，
能看到的只有高频日志（解码回调、按键）—— 于是"相位机到底推没推进"无法判断，
一度误判成"逻辑没跑"。⇒ 改成**写 `/tmp/pg_movie_<tag>.txt`**，一眼就能读。

### 6.4 ★★ 长按退出：`tick()` 返回 false **不会**关闭页面

`onUI_Timer` 返回 false 只是"让框架停掉本页定时器"。第一版只置了标志、没调
`closeActivity()` ⇒ 现场表现是 **长按后画面卡住、定时器停了、QA 通道再也不响应，
而页面还在前台（key 监听也还挂着，日志里继续打按键）**。
正解：退出动作里显式 `EASYUICONTEXT->closeActivity("<xxx>Activity")`
（与 `cameraLogic::camQuitAndCleanup()` 同一做法）。

### 6.5 ★ 注释里的 `**/` 会提前结束注释（本次编译挂了 100+ 个 "stray '\345'"）

写 `**/res 分区装得下**` 这种"加粗 + 绝对路径"的注释时，`**/` 里的 `*/` 就是注释结束符
⇒ 后面整行中文变成代码。**C++ 注释里绝对不要出现 `**/`**（工作区记忆 §35 早记过，
这次又踩了）。排查口诀：`grep -rn '\*\*/' src/`。

### 6.6 ★★ 升级脚本的验证环节曾"静默依赖设备侧 busybox"⇒ 假失败

第一次固化：`/res` 里的 `.so` **完全正确**（md5 与本地一致），但 `/tmp/busybox` 被设备重启
清掉、补推没成功 ⇒ 设备侧 `md5sum` 返回空 ⇒ 脚本在"只能等"的窗口里**白等满 10 分钟**，
最后报"固化未确认"（**假失败**）。已修：设备侧读不到就 **`adb pull` 回 PC 自己算 md5**
（判据等价、不依赖设备工具），并在接受不了时**打一行警告**而不是静默返回空。

### 6.7 ★★ 从 A 片直接点 B 片会黑屏（`hide` 不停流 + 起流失败不重试）

**复现**：飞天仙女正在播 → 直接进可爱小猫。日志：

```
movie[fairy]: onUI_hide                 ← fairy 退到后台（只走 hide，不走 quit）
W PgStream: 已有任务在跑                 ← fairy 的解码链还占着
W movie[kitten]: startWithDisplay 失败
movie[kitten]: 相位 -> ERROR            ← 第一版永久停在这里（黑屏）
PgStream: 收尾完成（sRunning 已清零，可再次播放）   ← 其实 70ms 后就干净了
```

**两个成因，都要修**：
1. **`onUI_hide` 必须停流**。本页是被 `openActivity` 切到后台的 —— **只走 `onUI_hide`，
   不走 `onUI_quit`**（后者只在 Activity 被 `closeActivity` 销毁时来）。不停流的话：
   ① 解码通道 + disp 视频层一直被占着（本板 55MB）；② 下一个播放页起不来。
   回到前台时 `show()` 会自动重起一轮。
2. **起流失败必须重试，不能直接进 ERROR**：`stopForSwitch()` 的收尾是**异步**的
   （几十 ms ~ 1.5s），而"切到 B"是**立刻**发起起流 ⇒ 必然撞上"已有任务在跑"。
   现在 SWITCHING 相位会**反复重试**（每 250ms 一次，最多 12 次≈3s）才报错。

**验收**：A 播到一半 → 切 B ⇒ `phase=PLAYING`、`decoded` 递增（不再 ERROR）。

### 6.9 ★★ 调试版（`fun launch` 推 `/tmp`）会被 OOM 杀掉 —— 视频页必须用**固化版**验收

改完循环逻辑后在调试版上再验时，出现"进应用后 `phase=WAITFRAME` 卡住、`decoded=0`、
disp 里没有视频层"。查 `dmesg` 才看到真相：

```
Out of memory: Kill process 2915 (zkgui_ui) score 180 or sacrifice child
Killed process 2915 (zkgui_ui) total-vm:31480kB, anon-rss:6988kB ...
```

**进程被内核 OOM 杀了、init 重新拉起**（所以 `pid` 变了、状态文件是全新的）。
本板 MemTotal 只有 **55MB**，而 `fun launch` 把程序**放进 tmpfs（占 RAM）**；
主界面 + 屏保页 + 视频页三层 Activity 叠加时就不够了（固化版资源在 `/res`、不进 RAM，
同一场景实测 `MemAvailable` 21MB）。

⇒ **纪律**：这类大贴图/视频应用，**迭代阶段用 `ITER=1`，但验收一律固化到 `/res` 再跑**
（工作区记忆 §17）。看到"莫名其妙的卡住 + `pid` 变了"先去查 `dmesg`，
别怀疑自己的相位机。

### 6.10 ★★ 屏保是全局粘性状态 + 退出返回的是**上一页**（两个 QA 陷阱）

① 我们在 `tick()` 里每 1 秒强制 `setScreensaverEnable(false)` —— 这是**全局**开关。
`onUI_hide` / `onUI_quit` 都必须把它复位，否则**设备待机时永远不进屏保**。
实测判据：退出回主界面后 `saver` 命令报 `enable=1`，空放 36 秒后 `isOn=1`（屏保正常进来）。

② **QA `quit` 关掉当前页后回到的是"栈里的上一页"，不一定是主界面**：
本次从仙女 → 小猫 → `quit` ⇒ 回到**仙女**（`movie[fairy]: onUI_show`，它重新起流继续播）。
当时看到主界面 `saver` 报 `enable=0`，差点当成"复位失效" —— 其实仙女还在前台压屏保，
**是对的**。⇒ 要回主界面必须把栈里的视频页**逐个关掉**（再 `quit` 一次）。

③ **用 QA 命令进/出屏保页之后，`mainActivity` 的前台态可能没同步**：此时 `saver` 会报
`enable=0`（屏保检测关着，看起来像"再也进不了屏保"）。这是因为 `mainLogic::tickScreensaverPolicy()`
开头就 `if (!gActivityActive) return;`（"主界面不在前台就什么都别做"，防两边互相覆盖）。
**走一次正常路径即自愈**：进任意独立页再退出（实测退出视频页后 `enable=1`）。
本次实测：进仙女 → `quit` 退出 ⇒ `saver` 报 `isOn=0 timeout=30 enable=1` ✓。
⇒ **不是本次改动引入的**（`MoviePage` 只在 show/hide/quit 时把开关设成"允许"），
但现场遇到"设备不进屏保"时要知道这一点。

### 6.11 ★ `decoded` 的单段增量会抖，别拿它当"掉帧"判据

状态文件每 500ms 刷新一次，而采样器是 600ms 一次 ⇒ 读到的值有最多 500ms 的相位差，
`decoded` 的单段增量会在 6~17 之间跳（期望 9）。**真掉帧会掉到 0~2**，别被 6 吓到。
判"整段时间轴有没有丢帧"要用**平均帧率**（累计差 / 时长），判"接缝有没有停"要用
**`lastseek_ms` 的差分 − 片长**（见 §3.3）。

### 6.12 ★★ 固化"报成功"之后还有两个陷阱（本次都踩了）

**① 跑的可能还是旧代码。** 固化脚本比 md5 只能证明"**盘上的文件**是本次构建"，
不能证明"**内存里的进程**是本次构建"。本次固化后进应用，发现状态文件**缺新字段**
（没有 `saver_on`/`lastseek_ms`）—— 即跑的还是上一版的库。
⇒ **确认跑新库必须用"只有新代码才有的东西"做判据**（本次就是那几个新字段，
比"`pid` 变了"可靠得多 —— pid 会因为任何原因重启而变化）。若发现是旧的，
`adb shell kill -9 <pid>` 让 init 拉起即可（或重跑一次脚本，它会等 pid 变化）。

**② 连续 reboot 之后 `/res` 可能挂不回来。** 本次固化完成、验证通过，接着**又 reboot
了两次**，之后：

```
squashfs: SQUASHFS error: Can't find a SQUASHFS superblock on mtdblock3
```

`/res/lib/libzkgui.so: No such file or directory` ⇒ **应用直接起不来**（无日志、无状态文件、
QA 通道不响应）。这种时候**不要手工 `mount` / `dd` 回写**（§0 红线），
正路是**重走一次 `tools/upgrade_device.sh <版本>`**（它自己会"卸载→擦→写→挂回"）——
本次实测重跑一次即恢复，全程 124s。
⇒ 纪律：**固化后需要重启时，用 `setprop ctl.restart zkswe`（只重启应用，脚本里就是这么做的）
或 `kill` 应用进程；不要连着整机 reboot。**

### 6.13 ★ `--dur` 参数填错会让验收"假失败"

`movie_seam_qa.py` 的接缝判据是"一轮时长 − 片长"。第一次我按**旧日志里的
"PLAYING 相位时长 9.4s"** 填了 `--dur 9.4`，于是稳定的 10123ms 被报成"多 723ms ⇒ 接缝拖延"。
真实片长要看 `ffmpeg -i` 的 `Duration`（**fairy 10.10s / kitten 10.10s**）。
**教训**：判据的参数必须来自"权威来源"，不能来自另一次测量的中间量。

### 6.14 ★★ 长时间循环播放后**画面静帧**（出帧数冻结在 100001）—— 删一行保护就够

**用户现场**（长时间工作后）：日志刷这两行，画面**不动了**：

```
W PgH264: 解码器持有帧 100001（远超池大小，驱动异常？）→ 丢弃本次喂入（累计丢 37350）
  PgStream: [HW] 已喂 137400 包（硬件解码出帧 100001，解码器持有 100001…，丢 37397…）
  PgStream: ★ 本地文件循环第 910 轮（seek 回起点…已出帧 100001）
  movie[kitten]: 第 910 轮播完（本轮 10108ms，流未中断）-> 自动续播
```

**为什么危险**：它是"**假活着**"——`phase=PLAYING`、`running=1`、`fileloops` 照涨、
每轮 10.1s 也"正常"，**状态文件里一切正常**（`decoded` 那一行是唯一线索）。
但解码器**一帧都不吐**：`/tmp/pgframe.pgm` 抓帧 6 秒不落盘（这条判据最直接）。

**根因**：`zk_h264_player_get_picture_count()` 的语义**不是"待显示队列长度"，而是
"累计已提交帧数"**（喂多少报多少）。旧代码拿它当"缓冲积压"的安全上限（`> 100000` 就
丢弃本次喂入）—— 而**新的 seek 循环不再重建解码器**，这个累计值一路涨到 100000
（15fps 下只是 **1.85 小时**，实测 `lastseek_ms` 已 2.68 小时）⇒ **每一帧都被丢** ⇒ 饿死。

⇒ 教训：**语义错的判据，把阈值调大不解决问题**。那条保护 2026-09-14 就因为同一个语义
踩过一次（注释里写着"正常永远不触发"），但当时只是把阈值调高、没删；seek 循环把
"永远不会发生"变成了"1.85 小时必发生"。

**修复（两处）**：
1. `src/platform/PgH264.cpp::feed()` —— **删掉丢弃逻辑**，只保留一条"涨到天文数字时记一笔"
   的观测日志（`kPqLogLine`）。uint32 计数 15fps 要 9 年才溢出，涨多少都无害。
2. `src/ui/MoviePage.cpp` —— 加**通用兜底**：`PLAYING` 期间盯**出帧计数**，
   连续 `kStallMs`(3s) 不涨就判"解码链路卡死" ⇒ 停流重起（复用 SWITCHING 那条路）。
   实测重建后：`decoded` 从 0 重新增长、`drop=0`、**抓帧恢复落盘** ✓。
   QA 命令 **`stalltest`** 可主动复现这条分支（伪造"已停滞 4 秒"），否则只能等 1.85 小时。

**验收要点**：`drop` 应恒为 0（修好后没有任何丢弃路径）；出帧计数应持续增长；
`stalltest` 后能看到 `解码停滞 … -> 重建播放链路` 且随即恢复出帧。

### 6.8 ★ QA 通道文件会"重放"，测试前必须清

`/tmp/pg_<页>cmd` 的判定是"**内容变化就执行**"，而内容在**进程内**记着。
上一轮测试留下的 `quit` 会**在下次进页时立刻生效** —— 本次实测就被它污染了一次
（点进小猫页，几秒后自己退出了，我还以为切换逻辑坏了）。
⇒ **每轮测试前先 `echo '#clear' > /tmp/pg_<页>cmd`**（或 `rm`），再下发新命令。
同类坑：`/tmp/pg_autostart` 在进程重启后也会**重放最后一条**（`docs/online-media.md` §10 有记）。
