# 全志 V85X 在线流播放：内存红线（OOM）、播放循环三个坑、声卡独占

> 🔍 **检索导引（命中条件）**：用户问「**播放 720p 就直接崩/应用莫名重开一遍**」
> 「**设备越用越卡、应用反复重启，只能重启设备**」「**投屏能出画面但只有 2fps / 片子只播一小段就结束**」
> 「**画面比声音慢很多 / A-V 不同步**」「**我们占着声卡，别的程序放音会卡住**」
> 「**在线流播放该给多大内存预算 / 为什么 OOM killer 杀的是我的应用**」
> 且平台为 **全志 V851s / V853 / V85X（FlyThings / EasyUI，eyesee-mpp）** → **本篇就是答案**。
> 相关：`../hardware/audio-and-input-hardware.md`（声卡通路与输出开关）、`../v85x/videoview-transparent-window.md`（VO 上屏区域）

## 一句话

V85X 小内存板（实测 **56MB**）上，**1280x720 H.264 硬解会直接触发内核 OOM**（VIDEO 引擎升频后
`VDecChn0` 申请 ION 内存失败，内核把应用 `SIGKILL`）；**被 OOM 杀过之后内存不会自己回来**，
设备会进入"起来就死"的重启循环，**只能重启机器**。所以播放前必须**先算再开、超限明确拒绝**。
另有三个播放循环的坑（无音轨时音频时钟恒 0 → 2fps；无音频源读循环狂奔 → 片子只播 1/5；
帧 PTS 取值错 → A/V 漂移）与"常开 PCM 流独占声卡"的副作用，本文一次说清。

## 0. 实测环境（换板必须逐项重测）

| 项 | 值 |
|---|---|
| 平台 / 面板 | 全志 V851s，480x800 竖屏，FlyThings（EasyUI） |
| 内存 | `MemTotal 56632kB`（≈56MB） |

| 解封装 | ffmpeg 4.1（组件包，只编了 http/https + 少量 demuxer/parser） |

## 1. 🔴 内存红线：720p 硬解必然 OOM

### 1.1 现象（用户会怎么描述）

- 「**应用莫名重开了一遍**」（`pidof` 应用名，pid 在变；框架把应用托管给 init，被杀就立刻拉起）
- 「越用越卡」「**最后起来就死**，怎么都不行」

### 1.2 命令与实测输出

```bash
busybox dmesg | tail -30          # 关键就这三行
```
```
VE: before freq=200000000
VE: real freq=400000000                                        ← 视频引擎升频（开始硬解）
VDecChn0 invoked oom-killer: gfp_mask=0x242c2c2, order=2, oom_score_adj=0
COMPACTION is disabled!!!                                      ← 本内核没开内存规整
  __alloc_pages_nodemask ← ion_page_pool_alloc ← ion_system_heap_allocate
                        ← __ion_alloc ← ion_ioctl
Normal free:2520kB min:940kB ... present:65536kB managed:56632kB
Out of memory: Kill process <pid> (zkgui_ui) score 100 or sacrifice child
oom_reaper: reaped process <pid> (zkgui_ui)
```
踩中之后会 **每 ~5 秒杀一次**（连续十几次），因为 init 会立刻把应用拉起来、再解码、再死。

### 1.3 定量（同一块板，真机采样 `/proc/meminfo`）

| 源分辨率（H.264） | 像素 | 结果 |
|---|---|---|
| 640x360 | 23 万 | ✅ 可播；解码池约占 **15MB**，播完**不归还**，但**同分辨率第二轮一点不涨**（池复用）|
| 960x400 | 38 万 | ✅ 可播 |
| **1280x720** | 92 万 | ❌ **1 秒内 `MemFree` 23MB → 2.5MB → OOM 杀进程** |

> ⚠️ **"被 OOM 杀过之后内存不会自己回来"**：实测 `MemAvailable` 从 28MB → 11MB → 6MB → 1.3MB，
> `drop_caches` 只能回收一部分。这解释了"为什么第一次播放还能出画面、后面越来越差"。

### 1.4 这是板子限制，不是"播放器参数没调好"

把**同一个 720p 文件**交给**厂商框架播放器**（EasyUI 的 `ZKVideoView`，走 zkmedia 自己的
vdec/vo 通道）：它 `create vdec channel success` 之后**同样被杀**（pid 连续变、`MemFree` 掉到 2.7MB）。
⇒ 换 MPP 参数、调 `mVdecVideoAttr` 都救不了，**先在应用侧拦住**才是正解。

### 1.5 做法：**先算再开**（在 `VDEC_CreateChn` 之前判断）

```cpp
/* 三个判据；推荐"像素硬上限 + 内存地板"两条，见下面第 ③ 条的理由 */
① 像素硬上限：w*h > 960*544（≈52 万像素）→ 拒绝并打日志（本板实测 720p 必死，别试）
② 内存地板：MemAvailable < 7MB → 拒绝并提示"请重启设备"（说明已被 OOM 打残）
③ ⚠️ 不要用 MemAvailable 去卡"这次够不够"：
   同分辨率第二轮播放内存一点不涨（池复用），但播过一轮 MemAvailable 只剩 ~11MB，
   按"够不够"判会把第二轮自己拒掉 —— 判据只认像素上限。
```
配套省内存改动：码流缓冲 `w*h/4` 夹 `[256KB, 768KB]`（不要给 `w*h*3/2`）；
`VDEC_SendStream` 遇缓冲满错误码要**重试而不是丢包**（缓冲小了背压更常见）。

### 1.6 现场处置三条

1. 设备"变卡/应用反复重启" → 先看 **pid 有没有变** + `busybox dmesg | tail`；
   有 `Out of memory: Kill process ...` 就是本条 → **重启设备**（内存不会自己回来），别无他法。
2. 播放失败先看有没有"拒绝播放"这类日志 —— 那是守卫在保护你，不是链路坏了。
3. 片源优先 **≤960x544、≤4Mbps**；换新板子要重新标定上限（见 §6）。

## 2. 播放循环的三个坑（自维护播放循环：ffmpeg 解封装 + MPP 硬解）

> 前提：`ffmpeg av_read_frame → 转 Annex-B → VDEC_SendStream → VDEC_GetImage → 送显示`，
> 并且**自己按 PTS 节奏送帧**（不是把 URL 丢给播放器）。

### 2.1 无音轨源 → 画面只有 2fps（最隐蔽）

**现象**：只有视频轨的片子，每帧日志都打"等音频超 500ms 硬送"，实际 2fps。
**根因**：`audioClockMs()` 用"已推进声卡的帧数 - 队列"算时钟；**没有音频轨时它返回 `0 帧 - 0 队列
= 0ms`** —— 一个**永远不前进的合法时钟**，于是每帧都判"没到显示时刻"，每帧都等满兜底超时。
**修**：没有音频轨（或音频解码器打不开）时**显式关掉音频时钟**、改用墙钟同步。

### 2.2 无音频源 → 读循环狂奔，片子只播 1/5 就结束

**现象**：10s / 300 包的片子，**301ms 就把 300 个包全读完**（解出 7 帧就 EOF），画面闪一下就没了。
**根因**：有音频时是"音频环满了挡住调用方"把读取节流到实时；**没有音频就没有节流器**。
**修**（两步都要）：
- 无音频时：**帧没到显示时刻这一圈就不读包**（读取被压到显示节奏）；
- **读窗口**：最近读到的视频包 PTS 超过 `已播时间 + 1.5s` 就停读。

⚠️ **读窗口不能用"已送包 - 已出帧"的帧数差来判** —— 那是**死锁**：解码器要更多输入才吐下一帧，
窗口一关它没输入、又永远吐不出帧（实测卡在第 1 帧、CPU 空转）。用**媒体时间**判就与解码器内部
行为解耦了；另外窗口**必须等第一帧出来之后再生效**（解码器预热要吃掉几十个包才吐第一帧）。

### 2.3 帧 PTS 取错 → A/V 漂移

**根因**：硬解是异步的，`GetImage` 取出的帧对应的是**前几个**送进去的包。用"最近读到的包"
当帧 PTS，会把它推到未来（读得越快推得越远）→ 每帧都在等一个超前的时间戳。
**修**：**PTS FIFO**（送包时入队、出帧时出队）；再把 B 帧造成的 PTS 倒退**钳成单调**。
**实测（960x400 + AAC）**：368 帧 / 14.1s ≈ 26fps，日志
`解码帧 #240 → 墙钟 9143ms / 音频时钟 9948ms / 本帧 PTS 10051ms`，音画差在 ~100ms 内。

### 2.4 铁律：帧只能"挂起"，绝不能阻塞等（有音频时）

第一版"帧没到点就 `usleep` 等音频时钟" → 整链路掉到 **0.4 倍实时** + 伴音断续。
根因：等待期间同一线程没在读包喂音频 → 音频环被抽干 → 音频时钟不前进 → **越等越等不到**。
正解：`(A) 挂起帧到点才送（超时硬送兜底）→ (B) 非阻塞取帧 → (C) 读包（音频队列满时短睡重试 =
全链路实时节流器）`。音频环别给大（给 1s 会让画面跑到网络前 1 秒多、互相拖死），**400ms 稳**。

## 3. 声卡独占：常开 PCM 流会让别的进程"挂住"

- **现象**：应用（含厂商的 `tinyplay`）之外的程序打开 `hw:0,0` **不是报错，而是挂住**
  （`timeout 8 tinyplay x.wav -D 0` 被超时杀掉、**无任何输出**）。
  如果设备上还有别的程序要出声（或产测脚本要放音），就会表现为"卡住"。
- **为什么明知独占还常开**：爆音（pop）来自反复 open/close PCM，常开流是"音效进出无 pop"的前提。
- **正解 = 给出显式"让出/拿回"能力**（不要偷偷改默认行为）：
  `releasePcm()` / `acquirePcm()` + 一条 QA 命令；让出期间在线流**自动降级为只播视频**
  （否则会一直往一个收不进数据的队列里写，把整条链路卡死）。
- **闭环验证判据**：让出后 `/proc/<pid>/fd` 里 `pcmC?D0p` **数量为 0**，`tinyplay` 立刻正常播放；
  拿回后 fd 恢复、音效照旧。
- **推荐落地形态 = 空闲自动让出**（本工程 v1.7.7 默认 30 秒）：主循环每 500ms 判断
  「阈值 > 0 + 没有在线流在跑 + 距上次"要用声音"超过阈值」→ 让出；**拿回是按需的**
  （音效入口 / 起流前各试一次），实测**拿回耗时仅 13ms**，听感上无感。
  必须同时提供"关掉它"的开关（本工程 QA `pcmidle 0`），否则排障时会被"声卡怎么不见了"绕晕。
  ⚠️ 让出期间起在线流要能自动拿回，拿不回才降级为只播视频 —— 否则会往一个喂不进去的队列里死写。

## 4. 画面旋转：本平台**不能**用解码器自带的旋转（会输出黑帧）

**场景**：竖屏设备（480x800）看横屏内容 / 手机竖拍的 MP4（像素存成横的、只用
`displaymatrix` 元数据声明"要转 90/270 才正"）—— 不处理的话画面就是**侧躺**的。

### 4.1 试过并失败的（都别再试）

| 方案 | 结果 |
|---|---|
| `VDEC_CHN_ATTR_S.mInitRotation` | 帧的宽高**确实变了**（960x400 → 416x960），但**像素全是 0**；MPP **不报任何错** |
| `AW_MPI_VDEC_SetRotate(chn, ROTATE_90)` | 通道已存在时返回 `0xa0058009`，且**让复用通道彻底不出画** |
| 显示层旋转 | 本平台**没有这个接口**（逐项查过）：`VO_VIDEO_LAYER_ATTR_S` 无 rotate 字段、<br>没有 `mpi_vpss.h`、`libhwdisplay.so` 的 `hwd_layer_*` 没有、<br>`sunxi_display2.h` 的 `disp_layer_info` 也没有 |

### 4.2 可行做法：解码器照常出 0° 帧，**自己转正后再送显示**

1. 目标缓冲用 **`AW_MPI_SYS_MmzAlloc_Cached`**（MMZ）分配 —— 普通 `malloc` 的内存
   显示引擎(DE)访问不到。大小按 **Y 的 2 倍**申请（按 YUV420SP 理论 ×3/2 分配时，
   DE 会读到缓冲**末尾之后**，内核报 `DE invalid address: <缓冲末尾>`）；
2. CPU 转置（16×16 分块、缓存友好），Y 与色度平面分别转；
   支持 90/180/270（**180 不交换宽高**，90/270 交换）；
3. 构造 `VIDEO_FRAME_INFO_S` 送 VO。实测代价：单核 A7 上 640x360→384x640 的转置，
   25fps 播放时 CPU 空闲仍在 79~93%（可接受）。

### 4.3 构造帧结构的三个坑（都踩过）

- **必须按解码器实际的平面数填**：本平台 VDEC 输出 **YUV420P 三平面（I420）**
  （实测 `phy[0x48f80000, 0x48fbc000, 0x48fcb000]`，U→V 距离 =(W/2)*(H/2)）。
  **只填前两个平面、第 3 个留 0** → DE 去读第 3 平面拿到地址 0 →
  `DE invalid address: 0x0 / L1 PageTable Invalid`，画面上那片就是黑的。
- **`mStride[1]/[2]` 报的值不可信**（报文里是 640，实际色度行宽是 W/2=320）
  ⇒ 色度的跨距**自己按半宽算**。
- **先把解码帧的结构整体复制再覆盖**（`out.VFrame = src.VFrame`），别用 `memset(0)`
  从零构造 —— 结构里还有 DE 要用的字段（offset 等），清掉就废。

### 4.4 ⚠️⚠️ 一个把人带沟里的误判

旋转失败（黑帧）时内核会刷：
`DE invalid address: 0x49b5a000` + `L2 PageTable Invalid`，看着像"缓冲没映射进显示引擎"。
**但做 0° 基线对照后发现：0° 正常播放时同样在刷这条** —— 它是本平台 DISP 的**固有噪声**
（每次图层配置都会打，`id=0x4`）。

⇒ **判断旋转是否成功，只能看帧的像素数据**（把帧 dump 出来比对），
**不能拿内核这条当证据**。教训通用：**内核日志必须先做基线对照再下结论**。

## 5. 收尾两条铁律（两个 bug 都表现成"pid 每轮都变"，极易误判）

排查播放问题时，`pidof` 变了通常第一反应是"被 OOM 了"或"复位逻辑坏了"。
在 V85X 上有两个独立成因，**必须先看 logcat 有没有 `!!FATAL!!`**：

### 5.1 **绝对不要调 `AW_MPI_SYS_Exit()`**（除非同时把 VO 也拆干净）

- 现象：`DestroyChn + SYS_Exit ok` 之后紧跟
  `!!FATAL!! sig=11 fault_addr=0x14 pc=0x...`，应用被 init 拉起。
- 根因：**VO 的层/通道在本平台是"常开"的**（厂商播放器退出也不释放），
  而 `SYS_Exit()` 会把 MPP 全局资源一起释放 → VO 那边还引用着 → 收尾之后一碰 VO 就段错误。
- 正解：**只 `DestroyChn`，`SYS_Exit` 不要调**（`SYS_Init` 一辈子一次）。

### 5.2 判断"中途被打断"要把**两条路径**都算上

本平台"被停止过"的解码通道 `DestroyChn` 会**永久卡住**（收尾停在
`StopRecvStream ok` 之后再无下文、任务标志不归零、之后的播放全被"已有任务在跑"拒掉）。
所以必须区分"自然播完"（可安全销毁）与"中途被打断"（只能晾着/换通道）。

⚠️ "中途被打断"有两条路径，**只判其一就会误把脏通道当干净通道去销毁**：
- 硬中止（自己置的 stop 标志）
- **优雅停止**（外部 Stop 请求 → 另一条标志）

另外：**`stop()` 入口要在流已结束时直接 return** —— 收尾/收界面阶段也会调它，
否则会把"停止标志"置上，污染"退出原因"的判断，导致**每播完一次就误复位一次**。

### 5.3 验收口径（可直接抄）

- **连续 5 轮自然播完**（同一进程）→ `pid` **全程不变**、每轮都有解码帧、`FATAL=0`；
- **播放中途停止** → 收尾干净 + **数秒内自动复位**（设计如此），而不是等 40s 看门狗。

## 6. 内存偏低时**先自救**：回收页缓存能拿回十几 MB（别急着让用户重启）

**问题**：内存守卫（§1.5）在 `MemAvailable` 低于安全线时直接拒绝播放并提示"重启设备"。
但设备连续播放几次后可用内存就会掉到 7MB 左右 —— 用户被卡住。

**关键实测**：那些内存**大部分是可回收的页缓存**：

| 状态 | MemFree | MemAvailable | Buffers | Cached |
|---|---|---|---|---|
| 连播两次后 | 1.7MB | **14.0MB** | 4.0MB | 11.5MB |
| `echo 3 > /proc/sys/vm/drop_caches` 后 | 24.6MB | **31.4MB** | 0.02MB | 10.3MB |

⇒ 一次回收能拿回 **~17MB**；这类设备上应用通常是 **root**，该节点可写。

**做法**：守卫在"本来就要拒绝"时，**先 `sync()` + 写 `drop_caches=3`，再判一次**；
够就放行，确实不够才拒绝（拒绝文案也要写明"已尝试回收"）。
**只在内存不足时才回收**（不要每次起播都 drop，避免频繁清缓存拖慢系统）。

真机验证：
```
内存守卫 640x360 预计占用 ~16448kB，可用 10900kB
可用内存偏低（10900kB < 20000kB）→ 回收页缓存后 27716kB（已放行）
解码帧 #60 ...                        ← 播放正常
```

## 7. 怎么看"播出来的画面"（视频层**不在** `/dev/fb0`！）

`/dev/fb0` 只是 **UI 层**（disp `ch[2]`），播放出来的视频在 disp `ch[0]` ——
**读 fb0 / 各种截图工具都拿不到它**（"视频是黑屏吗 / 方向对吗"这类问题会完全看不到）。

全志平台自带一个 disp 节点可以 dump **合成后的整屏**：

```bash
# ⚠️ 写入值是**文件路径**，不是 0/1（写 1 只会失败，在 dmesg 留 `disp_capture_dump_store, open 1 err`）
echo "/tmp/cap.bin" > /sys/class/disp/disp/attr/capture_dump
# 产出 = 屏幕分辨率 × 4 字节 BGRA（480x800 → 1536000 字节）
```

**验证它确实含视频层**：同一位置抓"主界面"与"播放中"两张，逐像素比 ——
视频区差异 **91.4%**、底部 UI 区 **0.0%**。

**用法**：
- 判断"视频区是不是黑屏"：看该区域（如 0,0,480,700）的均值 / 非黑占比；
- 判断"旋转方向对不对"：把该区域与"你自己抓的帧"做**相关系数**（正确方向应显著更高）；
- 更干净的判据是在自己可控的链路里**把帧降采样成 PGM 抓出来**，
  再与"实拍帧"做几何核对 —— 实测正确变换相关系数 **0.87~0.90**、错误变换 **±0.13**，
  判据非常干净（不用靠肉眼）。

## 8. 局域网测试台架（别把台架问题当产品 bug）

| 坑 | 现象 | 正解 |
|---|---|---|
| 测试服务器**不支持 Range** | `av_read_frame` **第一次调用就 EOF**（日志"送 0 包/解出 0 帧"），看着像播放器坏了 | 很多测试片把 `moov` 放文件尾部，ffmpeg 要发 Range 去取 → **必须用支持 206 的服务**（自写 30 行或换工具），`python -m http.server` 不行 |
| 服务绑 `0.0.0.0`（Windows） | 设备侧 `Connection ... timed out` | **绑具体网卡地址**（防火墙） |
| 只看应用日志判"慢" | 误判成"带宽不够" | 用 busybox `wget` 拉大文件 + 读 `/proc/net/dev` 的 `wlan0` 字节数**直接量链路**（实测 2.4G 9~25Mbps、5G 26~67Mbps，而最强的源只要 4Mbps ⇒ 带宽从来不是瓶颈） |
| 播放中"内存/pid"没人看 | 事后才发现是 OOM | 采样脚本每秒打 `Rx / CPU / MemFree / pid`（**pid 变了就是被 OOM 杀了**） |

## 9. 一页速查

| 现象 | 第一嫌疑 | 立即验证 |
|---|---|---|
| 应用莫名重开 / 越用越卡 | **内核 OOM（分辨率超限）** | `pidof` 看 pid、`busybox dmesg \| tail` 找 `Out of memory` |
| 播放后设备再也起不来 | OOM 痕迹未释放，**只能重启** | `grep MemAvailable /proc/meminfo` 低于 7MB |
| 只有视频轨的片子 2fps | 音频时钟恒 0 | 日志是否有"等音频超 500ms 硬送" |
| 片子只播一小段就结束 | 无音频源没有节流器 | 日志"送 N 包/解出 M 帧/用时 Xms"里 X 远小于时长 |
| 画面比声音慢一截 | 帧 PTS 取的是"最近读到的包" | 帧日志里 `PTS` 是否远超音频时钟 |
| 别的程序放音卡住 | 我们的常开 PCM 流独占声卡 | `/proc/<pid>/fd` 里有没有 `pcmC?D0p` |
| "文件坏了"（第一次读包就 EOF） | 测试服务器不支持 Range | `curl -H 'Range: bytes=0-99'` 是否回 206 |
| **画面方向不对（侧躺/要转 90°）** | 手机竖拍视频的 `displaymatrix` 没被处理；<br>而本平台**解码器旋转会出黑帧** | 见 §4。核对自己转的方案 + **看帧的像素数据**（别看内核的 `DE invalid address`，那是噪声） |
| **每播完一次应用就像重启了（pid 总在变）** | ① 收尾调了 `SYS_Exit` → VO 悬空 **SIGSEGV**；<br>② "中途被打断"只判了一条路径 → 对脏通道 `DestroyChn` 永久卡住 | 先看 logcat 有没有 `!!FATAL!!`；再核 §5 的两条铁律 |
| 停止后播放器一直"已有任务在跑" | 收尾卡住（脏通道 DestroyChn）或看门狗未到点 | `streamstate` 之类的自检命令 + §5.2 |
| 跑久了就"内存不足、拒播" | 页缓存占着可回收内存 | **先回收再拒人**（§6）；`drop_caches` 能拿回 ~17MB |
| **视频是黑的 / 方向不对（截图看不到）** | 视频层不在 `/dev/fb0`（那是 UI 层） | 用 disp 的 `capture_dump`（§7），或把帧 dump 成 PGM 比对 |

## 10. 换板对照清单（不要照抄本文量值）

1. `grep MemTotal /proc/meminfo`、`grep -i compaction /boot/...` / `busybox dmesg | grep COMPACTION`
2. 逐档试分辨率（360p / 480p / 720p），每档记录：能否播、播放中 `MemFree` 最低点、播放后是否归还
3. 由此**重新标定像素上限**（本文 960x544 只对 56MB 板成立）
4. 用厂商框架播放器播同一个高分辨率文件做对照 —— 确认"板子限制"还是"我们的问题"
5. 确认音频通路的声卡与输出开关（见 `../hardware/audio-and-input-hardware.md`）
6. **旋转能力**：`VDEC_SetRotate` 是否存在、`mInitRotation` 是否真能出画（**必须看帧的像素数据**，
   §4.4 的噪声会骗人）、显示层有没有旋转字段（本文结论是 V85X 没有，换平台要重查）
7. **内存回收能力**：`/proc/sys/vm/drop_caches` 是否可写、回收能拿回多少（§6）；
   换板要重新量"一次播放消耗多少 / 稳态停在多少"
