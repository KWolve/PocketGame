# 方案深度检讨 & 与开源方案对比（FlyThings vs ESP32-P4+LVGL vs Linux+LVGL/Qt）

> **日期**：2026-09-29　**立场**：不是挑 bug，是审架构与商业结构（bug 清单见
> `框架缺陷与踩坑清单-2026-09-27.md` 27 条 + `MCP二次审查-2026-09-29.md`）。
> **样本**：PocketGame（V851s，3 周 32+ 应用全真机验收）+ 医疗影像（V553/V851s）两条线。
> **外部事实已核**（2026-09-29 检索）：LVGL **v9.5.0（2026-02）/ v9.6.0 为 v9 末版、v10 在途**；
> 软渲染器重写为按字（word）处理，**ESP32-P4 上旋转 ARGB 图 33ms→11ms、27→60 FPS**；
> SquareLine Studio 1.6.2 支持 LVGL 9.5 + 原生 SVG；ESP32-P4 = 双核 RISC-V 400MHz + 40MHz LP 核、
> 768KB SRAM + 最高 32MB PSRAM、2-lane MIPI-DSI（1024×600/1280×800@60）、MIPI-CSI+ISP、
> H.264 硬编 + JPEG codec、**PPA 2D 加速（混合/缩放/旋转）**、10/100M 以太网 MAC、USB2.0 HS OTG、
> **无 WiFi（需配 ESP32-C6）**。

---

## 〇、结论摘要（三句）

1. **这套方案在"能用"这个维度上已经打赢了开源路线**——3 周 32 个应用、单人 + AI，开源路线做不到（系统层要自己接）。
2. **但护城河不在"文档"，在"验证装置 + 板级事实"** ——文档会被模型能力追平，真机验证过的板级真相不会。
   我们目前把前者当核心、后者当附属，**优先级是反的**。
3. **风险不是"不如 LVGL"，是三个结构性依赖**：框架级缺陷不可修、验证成本的规模效应为负、AI 语料劣势导致
   每次上游演进都要重新付一遍文档+验证税。**结论：不用转开源，但必须建"退出通道"并把资产重心挪对。**

## 一、现状检讨：五个结构性风险（按危害排序）

### 1.1 ★★★ 知识库能让你"绕开"，不能让你"修好"

- **实测证据**：mtd3 的 squashfs superblock 丢失 —— **两次复现**（09-20/09-24），至今无根因结论；
  我们唯一的处置是"原样重跑一次升级脚本"。这类问题在开源栈里是一张 issue + 一个 patch。
- **推论**：知识库的上限 = **绕行能力**。凡属"框架行为不可配置"的缺陷（静默失败、superblock、渲染路径
  alpha 语义不统一），知识库只能教人躲，不能让人不再遇到。
- **另有一个隐形成本**：27 条缺陷里 ~60% 是"零文档/零 warning"，说明**厂商在这些细节上的投入意愿有限**
  —— 这不是能力问题，是排期问题。你无法通过写文档让它变快。

### 1.2 ★★★ 验证成本的规模效应是**负的**（这是最被低估的一条）

我把仓库里的包卡实测拉了一遍：

| 平台 | 已真机验证的包数 | 说明 |
|---|---|---|
| Z20（SSD20X） | **11 / 11**（首轮） | 几乎全部验证都集中在这块板 |
| Z21（SSD21X） | 少数几项（HTTP/NTP/HTTPS/Downloader/WebSocket/SoftAp/Ethernet） | 且暴露了 Z21 专属坑（RTC=1970、无 `/mnt/sdnand`） |
| V85X / T113 / F133 | **基本空缺** | h264-player 有 V851s 单点验证 |

- **同一个包换一块板，验证结论几乎不能继承**（Z20 无蜂鸣器/无 ADC、GPIO 只能 `zeroOutput`；
  Z21 RTC=1970 导致 HTTPS 证书报错；Z21 registry 没有 mqtt 包）——**"组件卡"的真实形态是"组件×板卡卡"**。
- 而"验证"这件事**只能真机做**（这是它值钱的原因），因此**每加一块板 = 线性增加成本**；
  6 个平台 × N 个包 = 迟早失控。
- **对比**：LVGL/ESP-IDF 的"验证"由**上游 CI 矩阵 + 全球社区**承担，你只付适配成本，不付证明成本。
  你付的是证明成本，所以你**必须在"哪些组合值得证明"上做取舍**，而不是追求全矩阵。

### 1.3 ★★ AI 语料的结构性劣势（每次上游演进都要重新付税）

- **事实**：LVGL / ESP-IDF / Arduino 在模型权重里 —— AI **零样本**就能写出八九不离十的代码；
  FlyThings 不在语料里，AI 每次靠我们`knowledge/`（82 篇）现场投喂。
- **推论（关键，别自我安慰）**：模型每换代一次，**开源栈的起点自动抬高，我们的起点不变**
  （除非我们同步扩文档）。这不是"差距会缩小"，而是**"同样工作量下对手越来越好"**。
- **对冲方向只有一条**：把知识组织成**模型能自动消费的形态**（MCP 已做，正确），
  并且**把新增成本压到接近零**（自动 ingest + 检索门禁，正在做）。⇒ 我们的知识库必须是"活的、自动生长的"，
  **不能是"人工维护的"** ——人工维护的知识库在长期竞争里必输。

### 1.4 ★★ 抽象链税 + 渲染上限

- **链路**：HTML → html2json → JSON → fui pack → FTU → 生成 C++ → 引擎。**调试链路长**，
  且中间层是黑盒（本次修的 A1~A8 全在这条链上）。开源栈是**直接 C API**，AI 改完立刻能读代码验证。
- **性能上限**：FlyThings 走软渲染 + framebuffer。LVGL 9.6 已把软件渲染重写为按字处理（无需 GPU/SIMD），
  且有 NEON / Helium / RISC-V V / **SVE2** 多后端与厂商 draw unit（SiFli EPIC），**在 ESP32-P4 上借 PPA
  把旋转 ARGB 从 33ms 压到 11ms**。封闭框架**接不进任何新加速后端**——这是我们做音频仪表、PBR 贴图、
  视频叠加时反复撞墙的根因。
- **注意区分**：这不是"小屏够用就行"的问题 —— 我们的产品路线（HA 磁贴、视频叠加、仪表动画）
  正持续往"需要合成/旋转/缩放"的方向走。

### 1.5 ★ 人才、生态与寿命

- 招人：LVGL/Qt/ESP32 简历满地，FlyThings 只能内部培养。
- 第三库：开源栈有现成组件（lv_lib_*、ESP Registry 上千组件）；我们只有自己攒的 `components/`（8 个模块）。
- 寿命：厂商 BSP 停更 = 产品线冻结。开源栈最坏情况是**自己接手上游**（疼，但可能）。
- **对医疗线尤其重要**：合规（IEC 62304 类的软件生命周期证据）需要**可追溯的上游版本与安全补丁策略**，
  闭源框架的"版本不可复现"（打包产物体积都不可复现，见缺陷 D5）在审计时是硬伤。

## 二、重新定义资产：我们真正有的是什么

把这三样分开看，优先级要重排：

| 资产 | 现在的地位 | 真实价值 | 结论 |
|---|---|---|---|
| **知识文档**（82 篇 + 检索） | 核心，人力维护 | 会被模型能力追平；**边际价值随模型变强而下降** | 保持，但目标改为"**自动生长 + 可检索可验证**" |
| **验证装置**（selfcheck / bugreport / QA 通道 / pginj / 判据体系） | 附属工具 | **模型越强越值钱**：因为它是"AI 说的话有没有兑现"的唯一裁判 | ★ **升级为核心资产** |
| **板级事实**（Z20 无蜂鸣器、/data 只有 512KB、面板 MT-B 协议、Z21 RTC=1970…） | 散落在文档里 | **语料里不存在、也永远不会存在**；LLM 会编 GPIO 引脚、编 ADC 通道 | ★ **结构化 + 每次验完自动回填** |

一句话：**开源栈的优势是"知识免费"，我们的优势必须是"真相可证"**。
前者随模型能力贬值，后者不贬值。所以：把研发投入从"写更多文档"挪到"让每个结论都能一键复验"。

## 三、三方对比（十维度，每维度给判据而非形容词）

| 维度 | FlyThings（厂商闭源套件，V85X/Z20） | ESP32-P4 + LVGL/ESP-IDF | Linux + LVGL/Qt（树莓派/CM5、RK3566/3576、全志 H 系） |
|---|---|---|---|
| **AI 零样本可开发性** | 差（语料≈0，靠自建知识库） | **最好**（语料海量 + 官方文档可检索） | 好（Linux 语料多，但 GUI 层要靠 LVGL/Qt 语料） |
| **板级真相可得性** | 好（我方知识库是全行业最全） | 中（社区案例多，但**具体模组/屏的坑要自己踩**） | 中偏下（硬件组合太发散，坑最多最杂） |
| **GUI 性能上限** | 低（软渲染、帧缓冲、不可接加速） | 中高（**PPA 硬件混合/缩放/旋转**、双缓冲；800×1280 级 60FPS 有实测） | 高（GPU/VPU；LVGL 9.6 已支持 Wayland **DMA-BUF** 直送帧） |
| **多媒体（视频/摄像头）** | **强**（多路 DVR/AHD/UVC + 硬编解，aw-dvr/mpi 一整套） | 中（MIPI-CSI+ISP、H.264 硬编、JPEG；**编解码能力以官方 datasheet 为准**，多路/高码率受限） | **最强**（VPU 多路硬解、RTSP/浏览器/协议栈齐） |
| **启动速度 / 功耗 / 实时性** | 中（Linux 类，启动秒级~十几秒） | **最好**（无 OS 级启动、低功耗、硬实时可控） | 差（启动 10~20s+、2~5W 级、需正常关机） |
| **量产 BOM**（粗估，需实核） | 低（V851s 级 SoC 单芯 + 内存） | **低**（P4 模组 + 需配 C6 才有 WiFi） | 高（主板 + DDR + eMMC/SD + PMIC） |
| **网络/协议栈** | 中（够用：WiFi/以太/RTSP/MQTT 均验过） | 中（自带 LWIP/MQTT/TLS，**WiFi 要外挂 C6**；跑不了完整 Linux 栈） | **最强**（完整 Linux 网络栈、容器、Python、代理） |
| **验证成本 & 规模效应** | **负**（每块板重新证明，且只能真机） | 中（上游 CI 免费，剩模组/屏适配要自己验） | 中偏负（硬件组合发散，回归面大） |
| **可修性（bug 能否自解）** | **差**（框架级不可修，靠厂商排期） | 好（开源源码，能自己 patch/提 PR） | 好（全栈可控） |
| **生态/人才/寿命** | 差（单一厂商、单一社区） | **最好**（乐鑫文档质量 + 组件注册表 + 大量厂商工具链） | 好（社区巨大，但方案层需自己收口） |

**读表要抓的三点**：
1. 我们真正独占的行是「**板级真相可得性**」和「多媒体」——**其余九行都是开源栈占优或持平**；
2. 「验证成本」这一行最危险：**每加一块板就重来一遍**，而对手的上游 CI 是免费的；
3. 「GUI 性能上限」与「可修性」是**结构性的**，不是写文档能补的。

## 四、选型决策（按案子特征，不按偏好）

| 案子特征 | 推荐 | 理由 |
|---|---|---|
| 小屏 HMI、**无复杂动画**、成本敏感、厂商 BSP 现成（我们的 Z20/V85X 面板类） | **FlyThings** | 系统层现成，验证资产已就位，改架构纯亏 |
| 带屏 + 摄像头 + 要**快启/低功耗/离线**、无 Linux 需求、UI 有动画（≤1024×600/1280×800） | **ESP32-P4 + LVGL** | PPA 硬件合成 + 快启 + 低 BOM；WiFi 场景配 C6 |
| **多路视频 / RTSP / 浏览器 / 复杂协议**、内存 ≥256MB | **Linux + LVGL 或 Qt**（RK/全志/CM5） | 只有 Linux 栈扛得住多路硬解与完整网络栈 |
| 医疗影像类（合规 + 长生命周期 + 可追溯） | **Linux + Qt（或 LVGL）+ 自建 BSP 归档** | 需要上游版本可追溯、安全补丁策略、可复现构建 |
| 现有 FlyThings 项目要做**大动画/高帧率**页面 | **拆出去**：该页走独立渲染/预烘帧（我们已在做） | 别指望框架提速 |

**混合路线值得记一笔**：LVGL 9.6 已支持 Wayland DMA-BUF 直送（帧→surface 不经 GPU 纹理上传），
意味着"Linux 跑业务 + LVGL 做 UI"不再是拼凑方案。若未来要迁移，这是阻力最小的落点。

## 五、修正："知识库足够完整 ⇒ 开源与不开源没差别"

**对应用开发者：成立。** 我们就用 82 篇文档 + MCP，在"没有源码"的前提下 3 周做完 32 个应用——
这就是证明。

**对产品公司：不成立。** 三件事知识库替代不了：

1. **修的能力**：superblock 这类量产风险问题，只能厂商修（知识库只教你重启一次）。
2. **跟的能力**：上游每代演进（新内核/新安全补丁/新加速后端），开源栈你随时能跟；闭源栈你只能等。
3. **人的能力**：招不到人、外包接不了、第三库没有 ⇒ 组织规模被单厂商供给锁死。

⇒ **结论不是"转开源"，而是**：继续用 FlyThings 拿时间优势，但**必须建"退出通道"**，
即把与框架的耦合面压到"换框架重写 UI 层 = 可控工作量"的水平。这条我们其实已经做了一半
（HTML 描述层 + 逻辑层分离），要做的是**把剩下的耦合点列出来并封边**。

## 六、行动建议（守 / 补 / 防）

### 守（现有优势，别分散）
1. **验证装置升为核心**：selfcheck（整机快照）+ bugreport + QA 通道 + selfcheck 自动回填矩阵，
   这是对手**短期追不上**的部分（LVGL 生态里没有等价物：通用框架给不了"这块板"的判据）。
2. **板级事实结构化**：把散落的板级事实（Z20 无蜂鸣器/`/data` 512KB、Z21 RTC=1970、面板 MT-B…）
   收进机器可读层，与包卡并列。**目标：AI 问"这块板能不能做 X"能在一次调用内得到可证答案。**

### 补（本轮暴露的短板）
3. **验证矩阵要如实呈现稀疏度**：现有"11/11 五件套"容易被误读成"全平台已验证"——
   包卡里应加 `verifiedCoverage: Z20 全 / Z21 部分 / V85X 空` 这类总览字段。
   （我们自己的经验：文档让人误判 = 比没文档更贵。）
4. **验证取舍要成文**：明确"哪些包 × 哪些板必须验"（比如：量产用的板 + 出货要用的包，其余标"未验证"），
   避免"每板全包都验"的失控。
5. **自动生长闭环**：项目内 docs → 检索门禁 → 入库，全程尽量无人工（现在入库门禁已就位，ingest 还是手工）。

### 防（为未来留退路，成本低但必须做）
6. **耦合点清单与封边**：列出所有直接依赖 FlyThings 专有 API 的业务代码位置，
   把"平台相关层"收成一个薄适配层（读写偏好、网络、音频、显示、触摸各一个接口）。
   **验收判据**：把 `flythings_*` / `easyui` 头文件的 include 收敛到 ≤5 个模块。
7. **新案子做一次并行试点**：拿一个"小屏 + 摄像头"的新需求，用 **ESP32-P4 + LVGL** 做一次
   两三天的最小可行对比（同一 UI，量开发耗时 / 帧率 / 启动时间 / BOM）。
   **不打分、不争论，只收数据** —— 这是唯一能让选型决策脱离口水的办法。
8. **对厂商要 SLA 而非文档**：把 27 条缺陷按"量产风险 / 体验 / 文档"分级，
   只对**量产风险级**（superblock、静默失败）要求根因与时间表。

## 附录 A · 需要以官方口径核准的三项

1. ESP32-P4 的 H.264 是"仅硬编"还是"编解码"——检索到的二手资料表述不一致，**须查乐鑫官方 datasheet**；
2. P4 的 MIPI-DSI 为 **2-lane、Video mode**（多份资料一致，但选屏前仍需按带宽公式核）；
3. 各家模组的量产报价与温度等级（工业级 vs 消费级）——本文的 BOM 判断是量级估算，**必须实核**。
