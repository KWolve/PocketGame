# 嵌入式触屏 UI 设计基线（扁平控件风 · 无图资源 · 小屏竖屏）

> **检索命中条件**：问「UI 怎么做 / 没有设计稿怎么定风格 / 按钮多大 / 字号多少 / 配色怎么给 /
> 列表卡片放什么信息 / 状态怎么显示 / 要不要做成像素风 / 图标库里没有想要的图标 / 设计稿要不要给
> 用户选几套 / AI 自己定风格算不算越界」→ 本文。
>
> **适用**：FlyThings / EasyUI 一类「控件 + json 布局 + 无现成图形资源库」的嵌入式触屏项目
> （480×800、800×480、1024×600 这类小屏）。不适用有完整设计规范与设计稿的产品。
>
> **定位**：知识库里 UI 的**实现层**（`uicontrols/*-fields.md` 控件字段、`ui-asset-rules.md` 图片铁律）
> 与**流程层**（`prototype-flow.md` 线框→风格→验收）都已成文，**唯独"设计层"是空白** ——
> 本文补这一层：把设计决策变成**可复述、可验收的定数**，而不是每次靠现场发挥。
>
> **来源**：480×800 竖屏掌机项目（8 游戏 + 4 工具 + 1 系统页，13 个应用）全流程实测
> （2026-09-11 ~ 2026-09-13），全部数值取自真机验收过的 `ui/*.html` 源稿。
>
> ⚠️ **优先级**：客户有设计稿/品牌规范 → 以客户稿为准。本文是"**没有设计稿时的兜底基线**"。
> ⚠️ **提交到 MCP open 版时**：删掉 §附 一节（工程实例），并按 `knowledge/README.md` 去工程化。

## 0. 一句话

没有设计稿时，**先把"设计自由度"收窄成几组定数**（3 档底色 + 4 档文字色 + 3 色强调 + 5 档字号 + 2 档按钮高），
再在这些定数内排列组合。这样多页面/多轮迭代才不会走形，用户也能一眼看出偏差。

**反过来说**：设计层不设规范时，多个页面的视觉会各自漂移 —— 这不是理论风险，是实测结论。

## 1. 先定基调：深底还是浅底

| 场景 | 基调 | 理由 |
|---|---|---|
| **游戏 / 影音 / 车载 / 工业** | **深底亮字** | 长时间注视不刺眼；深底能让彩色内容（游戏画面、视频）自然融入；高对比在小屏上更清晰 |
| 医疗 / 办公 / 阅读类 | 浅底深字 | 强调"干净、专业、可信"；打印/截图更适合汇报 |

本文基线按**深底**给（掌机/影音类项目通用）。深底的铁律是**层次必须靠"底色的深浅"拉开，不能靠描边** ——
小屏上 1px 描边会被抗锯齿糊掉。

**底色阶梯（4 档，全部取自实测）**：

| 档 | 色值 | 用在哪 |
|---|---|---|
| L0 页面底 | `#0B0F14` | 所有整屏页背景 |
| L1 顶/底栏 | `#16202C` | 标题栏、键位提示条、底栏 |
| L2 浮层面板 | `#1E2A38` | 弹窗、OSD、悬浮卡片 |
| L3 控件底 | `#1A222E` / `#25313F` / `#26313F` / `#2A3B4F` | 未激活 tab / 激活 tab / 次级按钮 / 卡片图标块 |

> 规律：L3 这一档是最常被滥用的 —— **同一个页面里最多用 2 个 L3 值**，否则界面会"脏"。

---

## 2. 文字：4 档灰度 + 3 色强调

**4 档文字色（按信息重要性，不是按"好看"）**：

| 档 | 色值 | 对比度 | 用在哪 |
|---|---|---|---|
| T1 主文字 | `#EEF2F6` | 最高 | 页面标题、卡片名、按钮文字 |
| T2 次要 | `#7C8DA3` | 中 | 标签、说明、单位 |
| T3 提示 | `#55637A` | 低 | 操作提示、辅助说明 |
| T4 最弱 | `#3A4757` | 最低 | 版本号、版权这类"存在但不需要读"的信息 |

> ⚠️ 深底上**不要用纯白 `#FFFFFF`**：小字号会发光发胀。用 `#EEF2F6` 这类"有温度的近白"。
> 大字（≥48px）可以用更亮的 `#F5F5FA` / `#F0FAFA`，因为大字号不会糊。

**3 色强调（语义固定，全工程不许串用）**：

| 语义 | 色值 | 用在哪 |
|---|---|---|
| **主强调 / 数据** | `#F2B33D` 琥珀 | 得分、充电中、需要被看见的数值 |
| **次强调 / 链接性** | `#4FC3F7` 青蓝 | 最高分、百分比、可交互指示 |
| **主行动按钮** | `#2E7D5B` 绿 | 弹窗里的"继续/确认"（**一屏只能有一个**） |
| 危险 | `#E4574C` / `#4A3038` | 低电、删除、"返回列表"这类破坏性动作 |

> **红线**：一屏内**最多 2 个强调色同时出现**。三色齐上会让人找不到重点。
> 危险按钮用**暗红底**（`#4A3038`）而不是亮红 —— 亮红会抢走主按钮的注意力。

---

## 3. 字号阶梯（小屏 5 档就够）

实测使用过的字号，收敛成 5 档：

| 档 | 字号 | 用途 | 备注 |
|---|---|---|---|
| 显示级 | **48 ~ 88** | 只能有一个：时钟 `88`、计算器结果 `64` | 这是"主角"，一屏只能有一个 |
| 数值级 | **32** | 游戏得分 | |
| 标题级 | **22 ~ 26** | 页面标题 26、窗口标题 22 | |
| 正文级 | **15 ~ 18** | 按钮文字 18、卡片名 24、tab 15 | |
| 辅助级 | **11 ~ 13** | 标签 13、卡片描述 13、最弱提示 12、脚注 11 | **下限 11，再小设备上会糊** |

**比例关系（比绝对值更重要）**：
- 标题 : 正文 : 辅助 ≈ **26 : 13 : 11**（约 2.4 : 1.2 : 1）
- **主数值必须是它标签的 2 倍以上**（得分 32 vs 标签 13；时间 88 vs 状态 20）
- 同一页里**相邻两档之间至少差 2px**，否则看起来像"没对齐"而不是"有层次"

## 4. 控件尺寸与热区（触屏可用性硬指标）

| 控件 | 尺寸（实测） | 说明 |
|---|---|---|
| 底部 tab | 152 × 58 | 等宽三分，间隙 4 |
| 列表卡片行 | 高 **108** | 88×96 图标块 + 两行文字 + 右侧数值 |
| 主行动按钮 | 280 × **56** | 弹窗内按钮 |
| 破坏性按钮 | 280 × 48 | 比主按钮矮一档，视觉降权 |
| 小开关（音效等） | 122 × **38** | ⚠️ **这是实测下限** |
| 数字键盘键 | 106 × 68 | 5 行 × 4 列 |
| 工具功能键 | 108 × 80 | 2 行 × 4 列 |

**热区规则**：
- **可点击控件高度 ≥ 38px**，推荐 **≥ 44px**（38 是"能用"，44 是"好用"）
- **同一行按钮之间间隙 ≥ 8px**；不同组之间 ≥ 16px
- 纯文字按钮（无底色）**必须加大热区**，或者干脆给它一个 `data-bg` —— 视觉上像按钮，用户才敢点

> ⚠️ 实测教训：`122×38` 的音效开关在真机上"能点但偶尔点不中"。如果重做，会做到 44 高。

---

## 5. 间距与栅格

- **页边距（左右）统一 8px**（480 宽 → 内容宽 464）
- **卡片内边距 6px**（图标块距卡片边）
- **列表行间距 8px**（主列表）；信息密集的列表（WiFi/设备列表）用 6px
- **竖向分区**：顶部状态区（0~106）→ 内容区（106~676）→ 提示区（688~746）→ 脚注（752~782）

> 规律：**间距只用 6 / 8 / 16 三个值**。混用 5/7/10/12 会让界面看起来"没对齐"但说不出哪里错。

## 6. 列表卡片的信息结构（最常被问到）

一个卡片 = **图标块 + 主标题 + 一行描述 + 右侧数值 + 数值标签**：

```
[ 88×96 图标块 ]  主标题 24px (#EEF2F6)         最高分 15px (#F2B33D, 右对齐)
                  一行描述 13px (#7C8DA3)       「最高分」标签 11px (#55637A)
```

**四条规则**：
1. **一行描述只能一行** —— 写不下就砍内容，不要换行（卡片高度是定数，换行会顶破）
2. **右侧数值必须有单位标签** —— 光有数字用户不知道是什么；标签用最小字号 + 最弱色
3. **图标块有自己的底色**（`#2A3B4F`），不要用图片 —— 没有图标库时，色块 + 首字/符号足够了
4. **描述文字写给"没玩过的人"** —— 一句话说清怎么玩/干什么，不是复述名称

## 7. 纯图形状态指示：不写字，用色块拼

**场景**：电量、信号、容量这类"需要实时变化"的状态。

**用户明确要求过："不要打字上去"** —— 数值型状态用**图形**，不要用 `85%` 这种文字。

**没有图标资源时的标准做法（电池为实例）**：用**分层色块**拼出来，宽度动态改：

| 层 | 尺寸 | 颜色 | 作用 |
|---|---|---|---|
| 外壳 | 46×26 | `#8FA0B5` | 电池轮廓 |
| 挖空 | 42×22（内缩 2） | **页面底色** `#0B0F14` | 制造"边框感"（不是描边！） |
| 电量条 | 40×20（内缩 3） | 按电量变色 | **宽度 = 40 × 百分比** ← 唯一动态项 |
| 闪电 | 3 块小色块 | `#EEF2F6` | 仅充电/充满时 `visible=true` |
| 正极头 | 5×12 | `#8FA0B5` | 贴在右侧 |

**颜色语义**：未充电蓝 `#5CA8E2` / 低电红 `#E4574C` / 充电·充满琥珀 `#F2B33D`。

**关键技巧**：
- **"挖空"用页面底色而不是真透明** —— 嵌入式控件多数不支持透明，用底色模拟边框是零成本且像素可靠的
- **闪电初始必须 `visible=false`** —— 否则开机瞬间会闪一下（生成器里要打补丁，见 §10）
- 动态改的是**宽度**，不是图片 —— 一个 `setPosition` 就够，零资源、零开销

## 8. 渲染路径决定视觉语言（本层最重要的判断）

**同一个工程里应该允许存在两套视觉语言，分界线就是渲染路径**：

| 内容类型 | 渲染路径 | 视觉语言 |
|---|---|---|
| 游戏画面 / 实时变化的图形 / 帧率敏感 | **自绘软渲染帧缓冲**（`setBackgroundBmp`） | **像素风**：点阵字体、纯色块、无抗锯齿 |
| 界面型页面（时钟、计算器、设置、表单） | **原生控件**（ZKTextView/ZKButton） | **扁平卡片风**：矢量字库、任意字号清晰 |

**怎么选**：
- 需要**逐帧变化**、**自己控制每个像素**、**跑得快** → 画布
- 只需要**显示文字/数值**、**要求任意字号清晰** → **必须用原生控件**

> ⚠️ 实测教训：工具页最初也想用画布画大字时间，结果 16×16 点阵放大到 88px 后锯齿严重。
> **中文字（≥48px）绝不能用点阵字体**，一定要走原生控件 + 矢量字库。

**但"点阵大字"有一条例外 —— 数字**（2026-09-13 实测推翻了上面规则的"一刀切"版）：

| 场景 | 做法 | 依据 |
|---|---|---|
| 中文大字（≥48px） | **必须**原生控件 + 矢量字库 | 工程只有 16×16 中文点阵，放大 4 倍以上就糊 |
| **数字 32~51px** | 可以用画布 `bigText()` | 另烘了一档 **16×24 大号数字点阵**，同尺寸只需放大 2~3 倍，台阶 2~3px |
| 数字 >60px | 走原生控件 | 点阵再大也顶不住 |

关键不是"点阵不行"，而是**点阵的原始分辨率够不够**：放大倍数 ≤3 时肉眼基本看不出台阶，
4 倍以上才开始糊。所以要么**放大倍数小**（原生点阵够大），要么**字号小**。

> 换算捷径：`bigText(scale=2)` 的显示尺寸 == `text(scale=4)`，宽度也一致（16×1 == 8×2）
> —— **同样的显示大小，前者只放大 2 倍、后者 4 倍**。凡是原来写 `text(..., 4, ...)` 画数字的
> 地方，都该换成 `bigText(..., 2, ...)`；更好的做法是用 `fitBigText(w, h, s, maxScale)` 自动选档。

**"像素风"不是风格选择，是技术结果**：软渲染 + 点阵字体 + 单色位 → 天然像素感。
如果项目有矢量字库和图形资源，硬做像素风是**自找麻烦**（要手工烘字体、画色块）。

## 9. 交互手感基线

| 交互 | 基线值 | 说明 |
|---|---|---|
| **长按判定** | **≥ 700ms**（DOWN→UP 时长） | ⚠️ 不要依赖框架的长按事件 —— 见 `hardware` 相关文档：部分板子 gpio-keys **无 autorepeat**，框架长按永远不触发，必须在应用层按时长判定 |
| 弹窗自动消失 | **~1.6s** | 音量 OSD 这类"操作反馈"型浮层 |
| 列表越界拖拽 | `dragMaxDis` 取 `min(round(scale×50), 控件高/3, 一行高)`；`scale = 屏高/600` → 1024×600 为 50、**480×800 = 67** | 见 `uicontrols/scroll-drag-interaction-spec.md`，**禁止填列表高度量级**（它是「越界拖拽上限」，不是「能滚多远」）。⚠️ 该文档没给竖屏实例 —— **"屏高"取屏的第二维**（由它的例子反推：800×480→40、1280×800→67），所以竖屏 480×800 用 **800**。⚠️ 小区块列表再取 `控件高/3` 兜一道（实测 remote 小列表控件高 108 → 用 36）|
| 按钮按下反馈 | 必须有**两态**（正常/按下），色差 ≥ 15% | 用 `picTab` 两态图或 `bgColorTab` 变色 |
| 页面切换 | 整屏 `window` + `showWnd/hideWnd`，**不用 modal 当页面** | modal 会吞输入 |

## 10. 交付流程里的三条设计红线

1. **多套风格方案**（来源 `devflow/prototype-flow.md` §⑤）：
   没有设计稿时，**必须给用户 ≥3 套风格方案选择**，不要自己拍板一套直接做。
   ⚠️ 本文档的由来之一就是**跳过这一步**的教训。
2. **预览稿确认后才开工**：
   `ui/*.html`（源稿） → 生成 json → **出 `*.preview.html` 给用户确认** → 确认后才 pack ftu / 写逻辑 / 上机。
   **未确认禁止开工。**
   ⚠️ 源稿 HTML 里一行 CSS 都没有，**不能当预览交付**（浏览器打开是一坨没排版的文字）。
3. **文案改动要跑两套字体**：
   - 画布点阵字体（自绘用）
   - 设备矢量字库子集（原生控件用）
   **少跑一个，就是某处中文不显示**。
   且字库子集里 **ASCII 必须全量（0x20~0x7E）** —— 运行时 `snprintf` 拼出来的分数/等级不在任何字面量里，
   漏了会**静默不画**（不是方框，是直接不显示）。

## 11. 反例清单（设计层最容易犯的错）

| 反例 | 后果 | 正确做法 |
|---|---|---|
| 一屏用 3 个以上强调色 | 找不到重点 | ≤2 个 |
| 用纯白 `#FFFFFF` 做深底文字 | 小字号发光发胀 | 用 `#EEF2F6` |
| 靠 1px 描边分层 | 小屏上被抗锯齿糊掉 | 靠底色深浅分层 |
| 同一页混用 5/7/10/12 间距 | "说不出的没对齐" | 只用 6/8/16 |
| 数值状态写文字（`85%`） | 用户明确不要 | 图形化（§7） |
| 卡片描述写两行 | 顶破定高卡片 | 砍内容 |
| **中文**大字用点阵字体 | 锯齿严重（16×16 放大 4 倍以上） | 原生控件 + 矢量字库 |
| 数字大字用 `text(scale=4)` | 8×12 放大 4 倍，台阶 4px | 改 `bigText(scale=2)` 或 `fitBigText()`（见 §9 的例外说明） |
| 列表 `dragMaxDis` 填列表高度 | 一次拖拽拽出整屏 | ≤ 一行高 |
| 用 modal 当页面容器 | 吞掉返回/暂停输入 | 整屏 window + showWnd |
| 开机闪一下状态图标 | 视觉噪声 | 动态元素初始 `visible=false` |

## 12. 自测清单（交付前打勾）

- [ ] 底色只用 §1 的 4 档；同页 L3 值 ≤2 个
- [ ] 文字色只用 §2 的 4 档；无纯白
- [ ] 强调色同屏 ≤2 个；主行动按钮唯一
- [ ] 字号只用 §3 的 5 档；最小值 ≥11；主数值 ≥ 标签 2 倍
- [ ] 所有可点控件高 ≥38px（推荐 ≥44）
- [ ] 间距只用 6/8/16
- [ ] 卡片描述单行；数值有单位标签
- [ ] 数值型状态是图形，不是文字
- [ ] **中文**大字（≥48px）走原生控件，不走点阵
- [ ] 画布上的数字：放大倍数 ≤3（用 `bigText()` / `fitBigText()`，不要 `text(scale=4)` 画数字）
- [ ] 列表 `dragMaxDis` ≤ 一行高
- [ ] 长按用应用层时长判定（≥700ms），不依赖框架长按事件
- [ ] 动态状态元素初始 `visible=false`
- [ ] 风格给过用户 ≥3 套选择
- [ ] 预览稿经用户确认后才 pack
- [ ] 改过文案 → 两套字体都重跑 + 查 cmap 确认覆盖
- [ ] **几何只有一处真值**：布局（html/json）与运行时 `setPosition` **不许各写一份**
      —— 实测踩坑（2026-09-14 屏保）：代码里的 `SAVER_Y` 会覆盖 json，只改 html 时
      "静态图跟着动、运行时定位的控件不动"，屏面上就是**整体错位**。
      做法：要么运行时**从控件读回位置**（`getPosition()`）当基准，要么彻底不写死
- [ ] **像素验收要逐块量"中心"，不能只量"高度"**：每个文字/图形的墨迹 bbox 中心应 ≈ 屏宽/2
- [ ] **Activity 的触摸回调里不许用"坐标白名单"吞触摸**：键盘/OSD/弹窗都是**独立
      SysApp 或整屏浮层**，但它们的触摸**要经过当前 Activity 的触摸回调** ——
      回调返回 `true` = 上层 UI 全废。血案（2026-09-14）：wifi 页白名单只到 y=394，
      键盘在 y=424..800 ⇒ 键位全被吞，**界面上一切正常、就是点不动、且一条日志都没有**。
      要挡就挡在"**真正发起动作的地方**"（列表点击/按钮回调）。
      判别口诀：**同一坐标"时而可用时而不可用"⇒ 不是坐标问题，是谁在吞。**
- [ ] **独立 ftu 页必须自己管屏保**：主界面不在前台时 `tickScreensaverPolicy` 的
      定时器**不跑** ⇒ 屏保保持"开"，30 秒后整屏盖上来（连键盘一起盖）。
      做法：`onUI_show` 关 + `onUI_quit` 恢复；**别在 `onUI_hide` 恢复**（键盘弹出会 hide）。
- [ ] **开关类策略要跟"实际状态"收敛，不要缓存"模式"**：缓存模式下别人改过开关
      自己就纠不回来（实测：屏保 `enable=0` 再也回不到 1）
- [ ] **长按类交互必须在定时器里轮询，"按满就动作"，不许只在 `E_KEY_UP` 判**：
      本板 gpio-keys **无 autorepeat** ⇒ 长按期间内核一个事件都不发；只在抬起时判长按的话，
      用户按满阈值后**还得一直按到松手**页面才动 —— 手感是"按了不动、松手才跳"（用户报过）。
      做法：`DOWN` 记时间戳 + 定时器每拍查 `now - downMs >= 阈值 && !已触发` ⇒ 立刻执行动作
      （并置"已触发"标记，抬起时不再重复）。
- [ ] **轮询周期要与阈值匹配**：阈值 700ms 时，用页面自身的 300~400ms 状态轮询去查，
      实际会飘到 1.0~1.1s（等于没改善）⇒ 需要另开一个 **100ms** 级的按键定时器。
- [ ] **列表/表格里的子控件要显式写 `data-align`**：不写时框架按**居中**排
      （实测：墨迹中心正好落在控件区中心），看起来像"缩进乱"。列表行一律 `left`。
- [ ] **`# 实测 …` 这类"行内注释"必须写在它所修饰的那行**（`#EXTINF`）**上面**：
      解析器是"遇到目标行时用累积的注释"，写在下面会**整体错位一条**（IPTV 频道表踩过）。
- [ ] **有生成脚本的数据文件，脚本的"输入解析"必须能吃自己的输出**（幂等）：
     否则重跑一次就把自己加的东西洗掉（频道表的实测数据、`tvg-note` 两次踩到）。
- [ ] **墨迹横向跨度要合理**：某带的跨度超过该文本理论宽度 ⇒ 那是**图形压上来了**
      （判据：日期 10 字符 28px ≈ 133px；16 字 20px 诗行 ≈ 320px）
